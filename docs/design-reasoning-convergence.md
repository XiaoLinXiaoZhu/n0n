# 推理收敛与待决问题通道 — 方案报告（草案）

> 状态：草案，待评审。本文只提出方案，尚未实现，也不构成对现行 Self-Function 标准的修订。
> 事实基线来自一次真实会话日志：`.temp/n0n-conversation-20260917-013834.json`（工作区 `D:\unity-program\TethernautEx`，Unity + URP 2D，4 个用户订单，92 轮 LLM 调用）。
> 文中 `idx=N` 表示该日志 `history` 数组的下标。

---

## 0. 一句话结论

这次会话的真正浪费不是"推理太长"，而是**存在一类未决事项在系统里没有任何容身之处，只能住在推理文本里**。

证据：单轮最贵的一次推理（`idx=255`，12.6k tok）在文本 **3.9%** 处就写出了正确答案，之后用 96% 的篇幅把它推翻、重建、再推翻；整轮 47 次 "Let me …"，决定性的 `read the shader` 在 **4.5%** 处已经出现，直到 **100%** 才执行。

因此结论是两条：

1. **推理需要一个出口**：一个"内部、可写、可持久、不计入交付"的通道，让未决问题离开推理流而保持未决。这是"疏"。
2. **出口必须附带承诺**：每条记录必须绑定**一个可执行动作**或**一个客户待办**，否则通道会退化成第二个推理转储。

## 1. 起因

### 1.1 现象

一次"给当前关卡画一个绿框 + 一个过渡动画"的任务，消耗了：

| 指标 | 实测 |
|---|---|
| LLM 调用轮数 | 92 |
| 工具调用数 | 139（observe 112 / act 23 / reason 4 / show 4） |
| 末轮上下文 | **326,949 tok** |
| 累计 prompt 读取 | 428,299（新）+ 13,526,016（缓存命中） |
| 输出总量 | 191,769 tok |
| 其中模型推理（reasoning） | **148,620 tok ≈ 末轮上下文的 49%** |

### 1.2 已有的处理：空转提示（idle_nudge）

n0n 已有一层针对"模型输出但不动作"的机制，实现位置如下：

- 编排层：`packages/core/src/agent/loop.ts`。`classifyRound` 把一轮结果分为 `exit / idle / retry_truncated / execute_tools`；`idle` 时注入 `idle_nudge`，并在 `idleCount >= max_idle_rounds`（默认 5，`AgentOptions.max_idle_rounds`）时终止。
- 领域消息类型：`packages/types/src/messages/base.ts` 的 `IdleNudgeMessage`。
- 提示词生成：`packages/format-prompt/src/format-idle-nudge.ts`，措辞为"你的文本输出用户看不到，请用 show 提交"，并带 anti-few-shot 变体。

所以**"一轮里该动作而不动作"已经有对应通道**。它作用于"整轮没有工具调用"，而推理长度本身没有任何通道、也没有任何上限。

**这就是本次失效的入口**：模型不空转，它**一直在动作**——每一轮都发起了工具调用，因此 `idleCount` 永远被清零。它的问题是**在同一轮里反复推翻自己**，而这类行为没有任何结构去承载、也没有任何结构去终止。

### 1.3 失效的放大机制（三个结构性原因）

**原因一：推理是上下文的一等公民。**

- `packages/types/src/client.ts` 的 `PromptMessage` 中，assistant 消息带 `reasoning?: string`。
- `packages/types/src/messages/assistant.ts` 中，`AssistantTextMessage` / `AssistantToolCallMessage` 都携带 `reasoning: ReasoningResult`，进入 `DomainMessage` 联合并持久化到会话日志。
- `packages/llm/src/deepseek-client/format.ts` 明确"reasoning_content 始终保留（当存在时）"，把历史推理重新写回请求。

也就是说：**推理占用上下文，而且随之后每一轮被重复读取**。这不是缺陷——保留推理是刻意的设计——但它意味着"推理中解一半的问题"会和"已经解决的结论"一样贵。

**原因二：未决事项没有状态表示。**

日志中全部领域消息类型只有：`system_with_skill`、`user_input`、`assistant_tool_call`、`tool_result`、`token_usage`、`cache_breakpoint`。会话里 92 轮、143 次工具调用，**没有任何一次调用是在记录一个未决问题**——因为不存在这种工具。于是"记住一个未决问题"的唯一手段就是**在推理里把它再写一遍**。

**原因三：完成条件只有"文本回答"，没有"推理可以合法结束"。**

循环在以下情况结束：模型调用 `show`；或整轮没有工具调用（idle，上限 5 轮）。没有一种结束方式是"我把问题挂起，因为我有别的事先做"。模型只有两个选择：**现在把问题想清楚**，或者**放弃它**。

### 1.4 因果链（本次会话的具体形态）

```
用户报告与模型结论矛盾的观察（"预览里是绿的"）
  →  模型无法在不重新解释该观察的前提下继续
  →  它只能用推理重新解释（而不是更新观察）
  →  每解释一次就翻一次结论：建立(A) → 因预览绿色推翻(A) → 回到(A) → 再动摇
  →  该现象伴随整轮 reasoning 体量失控，且不触发 idle（因为它一直在调工具）
  →  最终结论虽然正确，但代价是多轮重复推导
```

`idx=255` 原文（位置：3.9% / 9.7% / 31.1% / 32.9%）：

| 位置 | 原文要点 |
|---|---|
| 3.9% | "**Therefore the culprit must be hypothesis (A)**: the bars are rendered with URP's **lit** default material (`Sprite-Lit-Default`) … the light texture is black → `albedo × black = black` ✓✓✓" |
| 9.7% | 开始用"但预览是绿的"反推，怀疑 (A) |
| 12.6% | "So under (A), the preview should be black. The user reports green. So **maybe (A) is WRONG**…" |
| 31.1% | "The root cause I'm most confident about (from hard evidence): `m_DefaultMaterialType: Lit`…" |
| 32.9% | 又因预览绿色动摇："Let me **VERIFY** what the unlit branch does…" |
| 100% | 才去读 shader（`idx=262` 之后） |

同一结论被建立、推翻、再建立循环 3 次，期间**没有获得任何新事实**（该轮工具输出总量 1.5k tok）。

### 1.5 定量基线（可作验收判据）

|---|---|---|
| 总 reasoning | 148,620 tok | 92 轮累计 |
| 单轮 reasoning 中位数 / 均值 | 636 / 1,615 tok | 分布极度右偏 |

| "出口计划"首现位置 | Top-10 轮中：0.8% / 1.5% / 1.7% / 1.8% / 4.5% | **决定早；执行晚** |

### 1.6 一个更具决定性的旁证：一个事实被读到两次、用得太晚

`idx=210` 的读取结果已经直接给出了根因所需的全部事实：

```csharp
Renderer2DDefaultMaterialType m_DefaultMaterialType = Renderer2DDefaultMaterialType.Lit;
[SerializeField, Reload("Runtime/Materials/Sprite-Lit-Default.mat")]
Material m_DefaultCustomMaterial = null;
[SerializeField, Reload("Runtime/Materials/Sprite-Lit-Default.mat")]
Material m_DefaultLitMaterial = null;
```

即：该工程的 2D 渲染器默认 sprite 材质是 **lit** 的 `Sprite-Lit-Default`，而不是内置的 unlit `Sprites/Default`。

而更早的 `idx=136` 已经读到 `internal enum Renderer2DDefaultMaterialType` 这一定义；模型在 `idx=138` 的推理里仍在问"枚举 0 到底是 Lit 还是 Custom"，并最终按内置 unlit 材质处理，导致下一个订单的整段返工。

**这条旁证说明：本次的核心问题不是"没有外部动作可用"，而是"读到的事实没有进入判断，并作为未决事项被显式关闭"。** 一个"待决事实"的登记位（"默认材质=？已验证/待验证"）可以直接消除它。

## 2. 策略

### 2.1 被否决的替代方案

| 方案 | 内容 | 否决理由 |
|---|---|---|
| **A. 加闸门** | 对单轮 reasoning 设长度/时间上限；超限强制停止并输出结论 | 只压低文本长度，不改变结论的形成方式。日志证据：`idx=255` 的问题不是"写得太长"，而是同一结论被推翻两次；缩短文字不会消除这次推翻。属于"堵"，且会误伤真正需要的内部推理（如 `idx=285` 的过渡动画几何推导——该订单只用 8 轮就交付） |
| **B. 关闭推理回传** | 不再把历史 reasoning 写回请求，直接省掉 ~49% 上下文 | 会破坏现有设计意图（`deepseek-client/format.ts` 注释明确"始终保留"），且推理回传本身有价值：它让后续轮次能复用已有推导。这是"砍功能"不是"改结构"。可作为**独立议题**评估，见 §4.7 |
| **C. 只改提示词** | 在系统提示里写"不要反复推理""有结论就行动" | 属于"准则复述"。`docs/ie` 中的历史记录（`thinking-spec.md` 的 F0-F5 体系）已经走过这条路并已被重建，说明按历史失效点追加孤立规则不是稳定输入 |
| **D. 给模型一个自由文本的"记事本"** | 加一个可写入的描述字段 | 会变成第二个推理转储，只会增加 token。这是我们唯一担心的"疏"的错误形态 |

### 2.2 采用的策略：**疏**

> **让未决事项离开推理流，并在那里保持未决。**

判定这个策略是否成立的依据不是"听起来更好"，而是日志里的一个可测事实：**决定出现得很早（0.8%–4.5%），执行得很晚（100%）**。

如果模型知道该做什么却不做，那缺的不是能力，而是**"允许现在先不做"的结构**——而它之所以不能"先不做"，是因为问题一旦离开推理就没有地方待着。

### 2.3 与"堵"的关键差别

| | 堵（闸门） | 疏（通道） |
|---|---|---|
| 作用对象 | 推理的**长度** | 推理的**内容归属**：什么留在推理里，什么搬出去 |
| 结束条件 | 到达字数上限 | 未决事项被**用掉或关闭** |
| 对模型的要求 | 写短一点 | 把"待决"和"已决"分开 |
| 副作用 | 压缩真正的设计推理 | 需要存储纪律，否则变成第二个转储 |

两者不互斥，但**只有"疏"改变结论的形成方式**。

## 3. 建议措施

按依赖顺序排列。M1–M3 是核心，M4–M6 是配套。

### M1 — 新增"待决台账"这一内部状态（核心）

在领域层增加两类一等公民的条目，作为**内部状态**而非用户可见消息：

| 类型 | 含义 | 消解动作的形状 | 本次会话对应 |
|---|---|---|---|
| `question` | 通往当前目标的一个未知事实 | 一次读取 / 一次实验（可编程判定） | `idx=138` 默认材质枚举取值 |
| `anomaly` | 与当前结论冲突的一条观察 | **更新观察本身**（重测、换视角、补证据） | `idx=255` "预览绿 vs Game view 黑" |

台账条目**不进入** `show` 通道，不作为对客户的交付；但它进入下一轮的上下文（这是它取代推理缓冲的关键）。

### M2 — 每条条目必须承诺一个动作（核心）

契约三条，是通道自身的形式约束，不是额外禁令：

1. 每条条目必须携带**恰好一个** `next_action`（一个可执行的工具调用意图），或标记 `owner: customer`（该问题的消解权在客户）。
2. 本轮若产生条目，则本轮必须**消费掉或关闭**至少一条（执行其 `next_action`）。
3. 关闭必须显式：`resolved`（附证据）或 `rejected`（附理由）。禁止静默消失——本次会话中 `idx=138` 的枚举问题正是用了 74 轮才被动"消失"。

### M3 — 把"反差观察"升级为观察更新请求（核心）

当模型遇到与用户报告或既有结论矛盾的观察时，**禁止用推理重新解释它**；必须挂为 `anomaly`，并将其消解动作限定为"更新观察"（重测、换视角、采集新证据），或升级为客户信息请求。

理由：`idx=255` 的全部振荡都源于一个未更新的观察。用推理消化矛盾观察，就是本次会话最贵的一类浪费。

### M4 — 直接取证优先（配套）

当推理中出现"我记得 / 大概是 / I recall / IIRC / perhaps"且对象在可读范围内时，注入与 `idle_nudge` 同形的提示：**先读当前资产再继续**。

本次会话该一条即可消除 `idx=138` 的 18.0k tok，以及由它引发的整个订单 2 返工。这类提示应复用 `format-idle-nudge.ts` 的 anti-few-shot 变体机制，不要写成固定句式。

### M5 — 台账的存储纪律（配套，防止 M1 变成 M-D）

1. 每条目**单行**，不得散文；有长度上限。
2. 条目总数上限（建议 ≤7）；满时禁止新增，必须先消费或关闭。
3. 台账在每轮开头**重新可见**（否则"忘记"会重新回到推理里）。
4. 同一问题第二次进入台账时，必须带上一次的结论或证据引用，不得允许重新描述一遍。

### M6 — 采用可证伪的验证方式（配套）

见 §5。三个指标已在本日志上取到基线（重推理轮数 20/92、单轮 reasoning 中位数 636、同题重复 ≥4 轮/33k tok），可直接用于前后对比。

### M7 — 观察手段的补强（配套，独立议题）

本次 92 轮里**从未运行过一次 Unity / Play / 截图**，而唯一的验收点（框是否真的是绿色）本质只能由渲染结果回答。这不是提示词问题，是工具能力问题（缺少可编程的渲染验证手段）。建议单独立项。

## 4. 方案草案

### 4.1 领域层：新增消息类型

`packages/types/src/messages/` 下新增（命名与边界待评审）：

```ts
/** 台账条目的种类 */
type OpenItemKind = "question" | "anomaly";

/** 台账条目 — 内部状态，不是用户可见消息 */
interface OpenItem {
  id: string;
  kind: OpenItemKind;
  /** 单行陈述，长度受限 */
  statement: string;
  /** 命中该条目所对应的证据位置（文件/行/日志 idx），可为空 */
  evidence?: string;
  /** 恰好一个下一步动作；与 owner 互斥 */
  nextAction?: { tool: "observe" | "reason" | "act"; intent: string };
  /** 该条目的消解权在客户时使用 */
  owner?: "customer";
}

/** 台账快照 — 随轮次注入，供下一轮读取 */
interface OpenItemLedgerMessage {
  type: "open_items";
  items: OpenItem[];
  /** 本轮新增条目数，用于 M2 的消费约束 */
  addedThisRound: number;
}
```

**边界**：该消息不参与 `show` 的交付判定；是否进入 `format-prompt` 的输出需要显式设计（见 4.3）。

### 4.2 工具层：台账的三个操作

在 `ToolMap`（`packages/types/src/messages/tools/registry.ts`）中新增：

```ts
interface LedgerArgs {
  op: "add" | "close" | "list";
  kind?: OpenItemKind;
  statement?: string;
  evidence?: string;
  nextAction?: { tool: string; intent: string };
  owner?: "customer";
  id?: string;
  resolution?: { status: "resolved"; evidence: string } | { status: "rejected"; reason: string };
}
```

- `add`：新增条目；受 M5 的上限与单行约束。
- `close`：`resolved` 必须带证据；`rejected` 必须带理由。
- `list`：回读（**可选**——若台账已随每轮注入，则 `list` 冗余，建议不提供，避免多一条"回想起来"的路径）。

**关键设计判断**：台账**不做成"模型可选调用的工具"就够**。仅提供工具不改变行为——模型本来就"可以"记录，只是没有地方记。必须同时有 4.3 的注入与 4.4 的收束条件，通道才成立。

### 4.3 提示词组织层：台账的呈现

在 `packages/format-prompt/` 增加 `format-open-items.ts`，要点：

1. **固定形状**：每条一行，只包含 `kind / statement / next_action | owner`，不允许自由文本段。
2. **位置稳定**：台账注入位置固定（建议置于最新 `tool_result` 之后、下一轮开始之前），以保持 prompt 缓存前缀稳定。
3. **不与 idle_nudge 抢位**：两者措辞必须可区分——`idle_nudge` 是"你什么都没做"，台账提示是"你有未结项，本轮消费一条"。
4. **变体机制**：沿用 `pick()` 与 anti-few-shot 变体（见 `format-idle-nudge.ts`），避免固定句式被当成模板填空。

### 4.4 编排层：收束条件

在 `packages/core/src/agent/loop.ts` 中扩展现有 `classifyRound` 的分支，而不是新增一层控制：

| 现状 | 扩展后 |
|---|---|
| 无工具调用 → `idle`，注入 `idle_nudge`，5 轮后终止 | 无工具调用 → `idle`（不变） |
| — | **有活跃台账条目，且本轮既未消费也未关闭** → 注入"未结项"提示（与 idle_nudge 同形，但语义不同）；连续 N 轮未消费则视为停滞，进入终态判定 |
| 有工具调用 → `execute_tools` | `execute_tools`（不变），但在结果收集后**更新台账快照**并注入下一轮 |

要点：

- **不新增终止条件**。台账不清空**不是**失败，而是"本周期未完成"——它应当流入既有的质量终态判定，而不是成为新的机械终止。
- **不改变 `max_idle_rounds` 语义**。台账停滞的阈值是独立配置项（建议 `max_stalled_ledger_rounds`，默认 3）。
- 若条目 `owner: customer`，其正确出口是既有的客户请求消息类型（信息请求 / 决定请求 / 操作请求），由 `show` 通道的现有判定负责。

### 4.5 与现行 Self-Function 标准的关系：**不动标准**

台账条目是**运行时状态**，不是用户可见消息，因此不改变第八类判定的任何一条，也**不要求**质量标准新增措辞。

依据是标准自身的职责划分（标准的"约束来源与单一职责"节）：质量标准的唯一职责是生产责任、阶段、风险控制、证据与合格终态；运行时的上下文标签与状态注入属于**运行时协议**的职责。把"台账条目"写进质量标准，正好是标准 §9.5 所禁止的"向标准追加补丁"，也与"标准自包含、不依赖运行时概念"相冲突。

因此本方案：

- 不修改质量标准，不为它新增消息类型或阶段产物要求；
- 未来若需要"未决事项属于阶段产物"这一表述，应由标准维护流程独立提出工程记录后再改正文，并在其中说明**非台账实现如何满足该条**；
- 台账条目对外不可见；客户需要的只是它的**结论**，那些走既有的交付 / 请求类型。

### 4.6 不做的事（范围边界）

- 不设 reasoning 长度上限（否决方案 A）。
- 不改 reasoning 回传策略（方案 B 独立议题，见 4.7）。
- 不引入"压缩历史"或"摘要替换"（那是另一个议题：`docs/design-exec-output-budget.md` 处理的是 exec 输出预算，与推理预算不是同一问题）。
- 不把台账暴露给客户（它不是交付物；客户需要的是它的**结论**，那些走既有的交付/请求类型）。

### 4.7 独立议题：reasoning 是否应当始终回传

`packages/llm/src/deepseek-client/format.ts` 当前"始终保留 reasoning_content"，而 `packages/llm/src/deepseek-client/utils.ts` 提供一个默认关闭的 `rewriteParagraphs`（"Let me" → "We need to"）。

- `rewriteParagraphs` 只改措辞、不改结构：它不解决"未决事项无处安放"，因此**不能替代本方案**；但它是同类问题的另一个观察点（措辞改写属于"堵"的近亲）。
- 是否回传历史 reasoning 是一个独立的经济学问题（省 ~49% 上下文 vs 失去后续轮次复用推导的能力），建议单独立项评估，不要与本方案捆绑定稿。

### 5.2 验证方法

1. **回放实验**：用本日志的前 N 轮作为上下文，在"有台账"与"无台账"两种配置下重放，比较 §5.1 的指标。样本小，但足以判定机制是否生效。
2. **机制验证**：新增消息类型与工具参数走既有测试路径（`bun test`）；`format-prompt` 的台账渲染沿用 anti-few-shot 变体的快照测试（`scripts/preview-output/`）。
3. **反悔标准**：若指标全部不变 → 判定"出口"假设不成立，转方案 C'（补强根因取证与可编程渲染验证），不再扩复杂结构。

### 5.3 判定归属（不得混用）

本方案的效果验证属于**实际生产质量评价**（用真实会话前后对比）。`bun test` 只证明**程序机制**成立，**不能**用来声称推理收敛度改善。

## 6. 风险分析

沿用本项目 `docs/ie/methodology.md` 的 S/O/D 口径（S 决定"命中后是否必须重来"，O 与 D 是措施能改善的部分）。

| 失效模式 | 影响 | S | O | D | 预防 / 检测 |
|---|---|---|---|---|---|
| 台账退化为自由文本转储 | 增加 token，反而恶化 | 4 | **7**（模型天然倾向于把状态写成叙述） | 6 | 单行 + 长度上限 + 条数上限；快照测试校验形状 |
| 台账条目只增不关 | 未决项堆积成新噪声 | 5 | 6 | 7 | M2 的"本轮消费一条"约束；`问`与`关`计数比对 |
| 模型把台账当成交付物写给客户 | 客户看到内部状态 | 6 | 4 | 4 | 台账不进 `show` 通道；`show` 类型判定不变 |
| 挂起后真正需要解决的设计问题被推迟 | 交付质量下降 | 7 | 4 | 7 | 只允许 `question/anomaly` 两类；设计取舍类（`idx=285` 型）**禁止**入库，必须留在推理内 |
| 未结项被当作"机械失败"终止 | 掩盖真实状态 | 6 | 5 | 5 | 台账未清空不得作为终止条件；只能流入既有质量终态判定 |
| 提示词模板化（few-shot 陷阱） | 模型按模板填空，失去判断 | 4 | 5 | 6 | 沿用 anti-few-shot 变体机制 |
| 注入位置破坏 prompt 缓存前缀 | 每轮全价重算（本次已发生一次 281k 全价轮） | 8 | 4 | 3 | 台账固定位置注入；变更后核对 `cacheReadTokens` 序列 |

> 补充观察：本次会话 `idx=286` 出现一次 **281,124 tok 全额未缓存输入**，说明缓存失配的代价量级与一次订单相当。任何新增注入点都必须服从缓存前缀稳定性。

## 附录 B：术语

- **推理（reasoning）**：模型在本轮工具调用或回答之前产生的思考文本，随消息持久化并回传给模型。
- **待决台账（open-item ledger）**：本方案提出的内部状态，登记未决问题与未解释矛盾观察。
- **消解动作（next_action）**：与一条台账条目绑定的、恰好一个可执行动作；或标记为"消解权在客户"。
- **出口计划**：推理文本中"我接下来要去做 X"的自述句；本文用它计量"决定出现的位置"。
- **S/O/D**：严重度 / 频度 / 探测度，沿用 `docs/ie/methodology.md` 的评分锚点。
