# VOC 分析：用户对 n0n Agent 的不满

> 状态：历史工程输入。本文保留旧方案的 VOC 分析，不定义当前规范或运行时行为。

## 数据来源

1. **用户口头反馈**：从对话中提取的核心不满
2. **现有 skill 的"禁止"模式反推**：从 ~40+ 个 init skill 中提取"不要/禁止/避免"等否定句式
3. **网络搜索**：通过 metaso 搜索 AI coding agent 相关抱怨，覆盖 Stack Overflow 调查（90,000+ 开发者）、学术论文、Hacker News/Snyk/dev.to 等社区讨论
4. **deepseek-alignment 项目文档**：AGENTS.md、target.md
5. **skill-reviews 历史记录**：`docs/archived/skills/skill-reviews/`

## 核心发现：AI 编码助手的"70% 陷阱"

网络搜索揭示了一个反复出现的模式，在多个独立来源中得到印证：

> **"AI 能快速把你带到 70%，然后剩下的 30% 才是真正的工程——而 AI 在这里不仅帮不上忙，还制造额外的工作。"**

具体表现为五个相互关联的症状：

### 症状 1：快速到达 70%，然后在困难部分溃败

AI 能快速写出 happy path 代码。Demo 跑起来很漂亮。但一旦真实用户开始使用，边缘情况崩溃、错误信息不可理解、隐式假设被打破。团队用 AI 快速构建了令人印象深刻的演示，然后在真实使用场景下坍塌。

### 症状 2："几乎正确但还不够"——最危险的状态

Stack Overflow 2026 年对 9 万开发者的调查：66% 表示最大的挫折是 AI 代码"差不多对但不够对"。45% 说调试 AI 生成的代码比手工编写更费时。出现了三年前不存在的新 bug 类型：**看起来像正确代码的 bug**——通过编译、通过类型检查、看起来合理，但微妙地不对。

### 症状 3：修正循环退化为噪音

多次纠正后 AI 越来越错，对话退化为无法修复的纯噪音。根因是 AI 不理解它写的代码——每次纠正是在**表面打补丁**而非**理解为什么错了并修复根因**。补丁叠补丁，复杂性非线性增长。

### 症状 4：用户陷入"无助"状态

AI 构建了用户不理解的系统。一旦出错，用户无法自行修复——因为他们没有真正理解 AI 生成的代码。用户从"我需要帮助"变成了"我被 AI 绑架了"。

### 症状 5：AI 对代价没有体感

这是根因中的根因。LLM 的每次调用都是独立的、无状态的、零代价的。模型不会因为写了一个"差不多"的代码而承受返工痛苦。它不会因为用户后来发现 bug 而"后悔"。**对模型而言，"差不多"和"完美"的成本一样——都是零。**

## VOC 九组分类

### A 组：用户直接抱怨——毛毛躁躁

> "模型总是毛毛躁躁的" | "没有充分理解我的意思" | "模型总是认为这是一个简单的任务，不需要花费精力" | "认为这个任务没有后果，仅仅是写了一堆不怎么好的代码而已" | "没有积极和我对齐"

**深层问题**：这不是"偶尔的疏忽"，而是**结构性行为**。LLM 的训练分布中，"看起来能跑的浅层代码"比"处理了所有边缘情况的深层代码"更常见。模型不是在偷懒——它是在做它认为最自然的事。这种行为模式如果不被结构性对抗，就一定会出现。

### B 组：70% 陷阱——结构性的捷径偏好

> "AI 能快速写出看似正确的代码，但一旦需要处理边缘情况、错误恢复、并发安全、跨模块一致性，就开始制造问题" | "代码不是完全不工作，而是微妙地不对——这是最危险的" | "每次我指出一个错误，它修好了这个但引入了新的" | "修了三次之后，代码变得比从头写还要乱"

**深层问题**：LLM 的"最小阻力路径"不是模型的选择——是训练分布的产物。在训练数据中，乐观的、假设一切正常的代码远比防御性的、处理了所有失败模式的代码更常见。因此，除非显式地迫使模型面对"如果这个假设不成立会怎样"，否则模型默认输出就是乐观的、浅层的。

**影响**：这是一个**根本性的激励错位**。模型优化的是"在统计学上看起来像是好代码"，而不是"实际上是正确的代码"。两者之间的差距就是 70% 和 100% 的距离。

### C 组：不主动追问——默认猜测

对应 B 组的症状 3 和 4，但聚焦在交互层面：

> 用户需求模糊时，模型按自己的理解直接动手而不追问 | 遇到多种可行方案时自己选了就开始做 | 做了关键决策后不告知用户 | 用户纠正后表面接受但后续行为照旧

**深层问题**：追问意味着承认不确定性，承认不确定性意味着当前的置信度不够高。但 LLM 的训练目标（下一个 token 的最大似然）天然鼓励它输出最可能的那个 token——而不是说"我不确定"。"我不确定"在训练分布中出现的频率远低于直接给答案。

### D 组：技能反推——操作安全侵犯

从以下 skill 的"禁止"模式反推：

- `safety-dangerous-ops`：需要用户确认的操作类型
- `safety-no-sudo`：不使用 sudo
- `safety-no-shortcut`：不走捷径绕过安全检查
- `safety-bun-process`：不 killall bun
- `safety-reversibility`：可逆操作自由执行，不可逆操作先确认
- `safety-temp-dir`：不删除 .temp/

### E 组：技能反推——代码质量侵犯

从以下 skill 的"禁止"模式反推：

- `coding-style`：不用不可变数据、原地修改
- `write-*`、`no-search-and-replace`：不用基于文本匹配的编辑方式
- `test-standard/core-constraints`：禁止修改测试来修复失败、禁止浅层断言、禁止无效测试
- `file-organization/*`：不要创建大文件、不要深层嵌套
- `code-comment/*`：不要解释代码做什么、不要记录谁在什么时候改了什么

### F 组：技能反推——沟通侵犯

从以下 skill 的"禁止"模式反推：

- `communication-no-emoji`：不使用 emoji
- `communication-plain-language`：不使用专业术语/修辞（除非用户主动使用）
- `communication-progressive-disclosure`：不在一个 show 中堆太多内容
- `communication-feedback`：收到用户反馈时先分类再回应，不默认服从
- `communication-reference`：引用格式规范
- `communication-language`：使用中文
- `show-usage`：show 的四种 type 各有规范

### G 组：技能反推——工具使用侵犯

从以下 skill 的"禁止"模式反推：

- `exec/observe`、`exec/reason`、`exec/act`：三个工具各有边界
- `exec/batch`：可以批量调用但需理解并行安全性
- `exec/grep`：优先用 rg 而非 grep
- `exec/data-processing`：在脚本内处理输出而非倾倒原始输出
- `exec/isolated-install`：第三方库隔离安装

### H 组：技能反推——流程侵犯

从以下 skill 的"禁止"模式反推：

- `workflow`：复杂目标必须拆分，不能一次性解决
- `git/workflow`：标准开发流程（分支 → commit → 询问是否推送/PR）
- `git/commit-from-file`：从文件创建 commit
- `test-standard/*`：测试必须有用、必须独立、必须能检测错误

### I 组：deepseek-alignment target.md 中的期望

用户在 target.md 中描述了对 agent 思考流程的期望：

> 预期中，模型应该：1) 先进行 DFMEA 分析（按照表格分析，分析每一个功能/用户偏好要求，可能的失效方式并且提出预防方法，这一步一定要遍历，且充分考虑——因为一旦我展示给用户就已经无法撤回了）；2) 完成草案；3) 自主按照 DFMEA 给出的检测方式和监测度完成自检，发现问题并且纠正；4) 最后才结束思考，并且撰写正式的文本内容。

## VOC 到功能的映射方向

| VOC 组 | 核心不满 | 指向的功能 |
|--------|---------|-----------|
| A+B（毛毛躁躁 + 70%陷阱） | 模型的默认行为就是走捷径——浅层代码、跳过思考、不面对后果 | F1：对抗概率分布中的捷径偏好 |
| C（不追问） | 模型默认猜测而非承认不确定性 | F2：主动暴露不确定性并追问 |
| D（操作安全） | 操作后果被忽视 | F3：安全执行操作 |
| E+H（代码质量+流程） | 代码差不多对但不够对 | F4：产出正确的产物 |
| F+G（沟通+工具） | 工具和通信规范被违反 | F5：规范使用工具与通信 |

## 方法论说明

VOC B 组（70% 陷阱）来自网络搜索，覆盖 Stack Overflow 9 万开发者调查、学术论文、社区讨论等多个独立来源。其余各组来自用户反馈和现有 skill 的"禁止"模式反推。

核心洞察：**"模型偷懒"不是偶发的失效模式——它是 LLM 训练分布的产物，是默认行为。** 这意味着措施不能停留在"提醒模型注意"，必须结构性地强制模型面对自己的假设和行动的后果。这是整个 DFMEA 体系的设计锚点。
