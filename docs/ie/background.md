# 背景：为什么需要 IE 驱动体系

## 现有系统的结构

n0n 的提示词/skill 系统由以下层次组成：

1. **系统提示词基座**：定义 agent 身份、工具集、基本行为约束
2. **init skills（~40+ 个）**：启动时自动加载的规则，覆盖安全、编码风格、测试规范、通信规范、文件组织、执行工具使用等
3. **task/directive skills**：用户通过 @name 或上下文触发的任务型/指令型 skill
4. **agent loop**：流式解析 → 工具调度 → 结果收集 → show 检测 → 循环

init skills 按 order 字段排序后，以 `<skill name="xxx">` XML 标签包裹注入 system prompt。每个 skill 是独立的 SKILL.md 文件，含 frontmatter 和 markdown body。

## 现有系统的问题诊断

从 IE 的视角，当前系统存在五个结构性问题。这些问题与 share-ie 案例中"传统提示词的五个缺陷"高度对应，但因为 n0n 是编码 agent 而非创意写作 agent，具体表现有所不同。

### 问题一：措施堆叠，无法溯源到功能

当前 ~40+ 个 init skill 本质上是**措施集合**。"不要用 search-and-replace"（no-search-and-replace）、"不使用 sudo"（safety-no-sudo）、"不使用 emoji"（communication-no-emoji）——这些都是措施，但它们各自保护的**功能**是什么？没有显式记录。

后果与 share-ie 案例相同：无法判断覆盖性（有没有遗漏的风险？），两条 skill 之间是否冲突无法检查，只能"出问题再加一条"。skill 数量只增不减。

### 问题二：碎片化导致注意力稀释

`data/skills/TODO.md` 已经诊断了这个问题：14 个 init skill 低于 64 tokens，在 DeepSeek V4 的稀疏注意力（DSA）下，一个 128-token HCA 压缩块内混杂了来自不同主题的内容，导致粗粒度向量语义模糊，indexer 检索精度下降。

这不仅是工程优化问题，更是**设计问题**——为什么会有这么多碎片 skill？因为没有功能层级来组织它们。如果先定义"安全操作"是一个功能，它的子功能自然会把 no-sudo、no-shortcut、dangerous-ops 等组织在一起，不会散落为碎片。

### 问题三：无失效模型，规则无法自校验

当前 skill 的内容是声明式的规则（"你应该 X""不要 Y"），但没有任何机制让模型在输出前**检查自己是否遵守了规则**。

唯一的探测手段是：
- `show` 工具暂停循环等待用户确认
- tool result 中的 `system-hint` 提供操作建议
- `idle_nudge` 推动模型继续

这些都是**粗粒度的**探测——它们检测的是"模型是否卡住了"或"模型是否完成了任务"，而非"模型的输出是否遵守了某条具体规则"。

以 `safety-dangerous-ops` 为例：它列出了需要用户确认的操作类型。但模型是否在每次执行危险操作前都确认了？没有任何自检机制。如果模型"忘记"了这条规则（O 高 + D 高），失效就会发生。

### 问题四：order 字段承载了不该承载的职责

当前 init skills 的排序靠 `order` 字段。`order` 试图用一个数字同时表达：
- 这条规则比那条规则更重要（优先级）
- 这条规则应该先被读到（注意力顺序）
- 相关规则应该放在一起（主题分组）

这三个维度并不总是对齐的。结果：order 变成了直觉分配的"大概重要程度"，没有量化依据。

### 问题五：不可验证，因此不可回归

改了 skill 之后，怎么知道变好了？当前做法的回答是"跑几轮看感觉"。这意味着：
- 无法判断改动是修好了问题还是碰巧没触发
- 无法确认修 A 时没有弄坏 B
- 接手的人不知道为什么有这条规则，不敢删——skill 只增不减

## 已知的相关工作

`deepseek-alignment` 项目已经对创意写作 agent 完成了 IE 驱动的提示词重设计，产出了 5 功能 × 24 子功能 × 27 失效链的 DFMEA 体系。n0n 是编码 agent，场景不同（返工特征、失效模式、VOC 来源均不同），但方法论和文档结构可以复用。

## IE 驱动的改进方向

1. 从 VOC（用户抱怨 + 现有 skill 的"禁止"模式反推）定义功能需求
2. 为每个功能拆分可校验的子功能
3. 对每个子功能分析失效模式，标注 O（频度）和 D（探测度）
4. 基于 O×D 排序设计预防措施（起草前）和探测方式（起草后）
5. 将 skill 系统从"措施堆叠"重构为"功能-失效-措施"的三层映射
