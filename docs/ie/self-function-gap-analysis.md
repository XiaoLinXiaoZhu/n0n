本文只做诊断，不提出改造方案，也不修改任何标准文件。

## 三、差距清单

### G1 正文形态错位：FMEA 表格充当标准正文

现象：6 个文件的主体章节都是「子功能与失效模式」表格（`F0:33`、`F1:21`、`F2:23`、`F3:15`、`F4:15`、`F5:17`），列为「子功能 / 失效模式 / O / D / 预防措施 / 探测方式」。

GT 第四节要求标准正文由「范围 + 术语与定义 + 要求条款 + 合格判据」构成，失效模式的位置是「要求的依据」而非正文形态。

影响：读者（模型）拿到的是分析过程而非规范条款，验收时无法指认"违反了哪一条要求"。

### G2 工程记录内容混入标准

现象：25 条 O/D 评分直接写在标准正文表格中（例 `F1:25` 的 `9 | 8`）。

GT 第五节把 FMEA 分析、S/O/D/AP 评估划归工程记录层，标准层只放要求与合格判据。

影响：契约条款与评估数据耦合，评分调整会触发标准变更，违反受控修订的分层意图。

### G3 缺失「范围」节

现象：`rg '^## (范围|术语|定义)' data/skills/self-function` 无匹配，6/6 文件均无范围声明，最接近的是「功能定义」（如 `F1:11`），内容是动机而非适用边界。

GT 第四节明列「范围（这个标准约束什么）」为标准要素。

影响：无法判断某条要求是否适用于当前场景，助长「本轮不适用」的主观跳过。

### G4 缺失「术语与定义」，关键术语无定义

现象：`F1:31-33` 直接使用评分锚点「O >= 7」「D >= 7」，但注入内容中没有任何位置定义 O、D、S 的量表；`F0:13,15,21,30` 四处使用「DFMEA」，同样无定义。定义实际在 `docs/ie/methodology.md`，该文件不注入。

GT 第四节要求「术语与定义（自包含——标准不引用模型看不到的外部概念）」。

影响：条款依赖模型看不到的外部文档，自包含性不成立。

### G5 悬空引用未注入的流程规格

现象：`F1:35`「预防措施（在 DFMEA 遍历阶段执行）」、`F1:41`「在自检阶段执行」、`F1:43`「探测方式（在自检阶段执行）」、`F0:25-31`「运作方式」引用「thinking 第 0 步」。这些阶段的定义在 `docs/ie/thinking-spec.md`，不注入运行时。

影响：与 G4 同源。标准要求模型在某个"阶段"执行动作，而该阶段在模型可见范围内从未定义。

### G6 编号粒度不一致，单个编号混装多条要求

现象：25 个 `Fx.y` 编号绑定的是「子功能」而非「要求条款」。典型 `F4:27-35`（F4.1 不破坏既有契约）在一个编号下混装了 6 条彼此独立的要求：编码前列调用方、跑类型检查、跑测试、跑格式化、纯函数优先、不可变数据结构、Parse-Don't-Validate。

GT 第四节要求「要求条款（规范语言、稳定编号——条款是体系的契约条款）」。

影响：条款不可逐条验收；违反其中一条时无法精确定位；后续增删要求会破坏编号稳定性。

### G7 合格判据不客观

现象：探测方式列多数写成自问句，例：`F2:27`「自检：我的理解是唯一的吗？」、`F1:27`「自检追问：我是否回避了觉得"可能有问题"的部分？」、`F4:22`「自检：这个测试可能永远通过吗？」。

GT 第四节要求「合格判据（每条要求如何验证）」。自问句无法产生可指认的通过/不通过结论。

影响：自检退化为形式复述，无法作为交付时的质量证据（GT 第七节要求交付附带质量证据）。

### G8 内容三重复述

现象：同一措施在文件内出现两到三次——表格「预防措施」列、独立的「## 预防措施」节、部分还在「各子功能详细措施」节。例 F3 的「## 预防措施」（`F3:50-55`）四条全部是表格内容的原句缩写（"每次写操作前做可逆性检查"）。复述节合计 86 行，占全部内容 18.0%。

影响：非 GT 直接违反，但违反单一来源原则——修订时必须同步多处，且占用注入预算而不增加信息。

### G9 GT 第六节「分阶段推进契约」在标准中无落点

现象：`rg '阶段|确认门|验收'` 在 6 个文件中只命中 `F2:30/37`（final report 自包含）和 F5 的 show type 说明，没有任何条款描述「契约确认 → 风险扫描 → 生产执行 → 验收交付」四阶段及其确认门。

GT 第六节把四阶段确认门列为体系构成之一（GT 第三节第 2 项「分阶段的推进契约」）。

影响：体系的四大构成中有一项在标准层完全缺席。当前只有零散的追问（F2.1）与交付（F2.4）要求，不构成阶段契约，也没有"未通过不得进入下一阶段"的约束力。

### G10 工程记录层未与 GT 对齐

现象：`docs/ie/` 现有 9 份文档（background、goals、methodology、voc-analysis、ctq-and-functions、dfmea-table、coverage-check、thinking-spec、implementation-plan）是产出当前 6 个 SKILL.md 的第一版记录，成文于 GT 之前。其中 `implementation-plan.md` 的阶段 2/3 清单已与现状不符（`self-function` 分类已在 `packages/skills/src/types.ts:22` 落地；`data/skills/standard/` 目录已不存在）。

GT 第五节要求工程记录层承载「FMEA 分析、S/O/D/AP 评估、条款追踪、变更历史」，并规定变更先改工程记录再改标准。当前缺少「要求条款 ↔ 失效模式 ↔ 合格判据」的追踪矩阵，也没有变更历史记录。

影响：受控修订流程缺少载体，任何标准改动都无法溯源。

### G11 残留物

现象：`data/skills/self-function/C0-concepts-and-contracts/` 是空目录（git 不跟踪空目录，故 `git status` 干净），为上一轮撤回的残留。运行时 `~/.n0n/builtin-skills` 中不存在该目录，因此当前不影响注入。

影响：低。但会让下一次 `diff` 持续报差异，属噪声。

## 四、未决问题（需用户裁定，本文不预设答案）

1. **条款体系的骨架**：保留 F0-F5 六分法作为标准的章节划分，还是按 GT 第三节的四大构成（沟通 / 阶段契约 / 标准规范 / 风险扫描）重组？两者对 G6 的编号设计影响不同。
2. **失效模式的呈现方式**：完全移入工程记录（标准只留要求 + 判据），还是每条要求附一行「依据」简述它对抗什么失败？GT 第四节说失效模式是「要求的依据」，两种做法都能满足字面要求。
3. **改造节奏**：先做单个 F 的试点（验证形态后再推广），还是先补齐工程记录层（追踪矩阵 + FMEA）再一次性改标准。
4. **C0-concepts-and-contracts 空目录**：删除，还是保留位置用于承载 GT 第四节要求的「术语与定义」自包含内容（解决 G4/G5）。
