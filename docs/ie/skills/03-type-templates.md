# Skill 编写规范（二）：四类正文骨架

> 状态：历史工程快照。本文依赖的旧 self-function 结构与 show 类型已经被重建；
> 当前分类与加载说明见 `../../../packages/skills/README.md`。

本文用途：规定四个分类各自的正文结构、语气与验收判据。frontmatter、命名、体量等对四类一致的要求见 `02-authoring-spec.md`，本文不重复。

地位：本文是 `00-ground-truth.md` 的下游产物，与它冲突的以它为准。形如 `R9` 的引用指向该文的推论编号。

## T1 先选分类

**T1.1** 分类的判据是**期望模型如何遵守**，不是内容属于哪个技术领域（`R9`）。按下列顺序自问，取首个成立：

| 顺序 | 自问 | 分类 |
|------|------|------|
| 1 | 不遵守它，产出就不合格？ | `self-function` |
| 2 | 它改变的是沟通与呈现方式，而不是任务本身？ | `directive` |
| 3 | 我希望模型现在就照着它把一件事做完？ | `task` |
| 4 | 它提供一种模型可以自行取用的能力或知识？ | `capability` |

**T1.2** 同一主题可能分属不同类。例如关于 git 的内容：作为可选的操作能力属 `capability`，作为必须遵守的提交纪律属 `self-function`。因此不得按"这是 git 的东西"来归类。

**T1.3** 强制性由强到弱依次为 `self-function` > `directive` > `task` > `capability`（`R10`）。分不清时，从最弱的一端反向验证：模型完全不理会它会怎样？后果越严重，类别越靠前。

## T2 对四类都成立的正文要求

**T2.1** 正文首行是一级标题，随后一句话说明它约束什么或提供什么。不写背景故事、不写变更历史。

**T2.2** 读者是 agent。使用祈使句或规范语言，不写面向人类的解释性铺陈。

**T2.3** 关键要求**宜**附依据（这条对抗什么失败）。`self-function` 强制，其余三类推荐。

依据：不写理由的要求在遇到冲突时无法被权衡，agent 只能机械执行或整条忽略。

**T2.4** 不得包含时间敏感信息：日期、版本号、"目前正在重构"这类会过期的状态描述。

**T2.5** 提及工具时使用实际名称——`observe`、`reason`、`act`、`write`、`show`——以及 `show` 的四种类型：工作日志、提问、求助、最终交付。不得杜撰工具名或类型名。

## T3 `self-function` 骨架

```
# <编号> <章名>

## 范围
（约束什么、不约束什么、术语沿用何处）

## <编号>.<节号> <小节名>

**<编号>.<节号>.<条号>** 条款正文。

依据：这条对抗什么失败。

## <编号>.<节号> 验收证据
（交付时应能提供什么）
```

**必备**：范围节、稳定编号的条款、每条的依据、末尾的验收证据清单。

**语气**：规范语言。**应**为强制要求，**不得**为强制禁止，**宜**为推荐，**可**为允许。一个编号下只放一条要求。

**判据**：违反时能指出"违反了第几条"；每条要求都能被第三方独立核对，而不依赖作者在场解释。

**反例**：把分析表格当正文（读者无法指认违反了哪一条）、一个编号装多条独立要求（无法逐条验收）、使用未在本章定义的术语（标准不自包含）。

## T4 `directive` 骨架

```
# <名称> — <协议名>

<一句话：不论执行什么任务，遵循以下节奏。>

## 适用场景

## 约束

### <约束名>
<该约束的具体行为要求>

## 与其他 skill 的关系
（可选）
```

**必备**：适用场景、若干条**有名字**的约束。约束必须有名字，因为它们要被复述和核对。

**语气**：作用于沟通形式与节奏——什么时候发消息、发哪一类、多细、要不要停下等人。

**禁止**：规定任务本身怎么做。一旦开始写"先读哪个文件、再改哪一行"，它就应该是 `task`。

**判据**：**把它删掉，任务仍然能完成，只是沟通方式变了。** 若删掉之后任务无法完成，说明它承载了任务内容，分类错了。

**现有合格样例**：`directive/step`——四条命名约束（每个微操作都声明、显性遍历、零跳步、基于证据），全部作用于节奏与呈现，不涉及任何具体任务。

## T5 `task` 骨架

```
# <任务名>

## 前置条件
（需要什么才能开始；无前置条件时省略）

## 执行步骤

### 1. <动作名>
做什么 / 用哪个工具 / 产出哪一类 show

### 2. <动作名>
...

## 退出条件
（什么时候算完成，以什么形式交付）
```

**必备**：编号步骤、每步关联的工具与 show 类型、退出条件。

**语气**：祈使句，第二人称。步骤之间的顺序是承诺，不是建议。

**判据**：agent 读完能立刻开始第一步，不需要再问"从哪儿开始"；读完最后一步知道自己完成了没有。

**反例**：只有原则没有步骤（那是 `capability` 或 `self-function`）；步骤之间没有顺序依赖却编了号；没有退出条件，导致任务无法判定结束。

## T6 `capability` 骨架

```
# <能力名>

## 它能做什么

## 何时适用

## 怎么用

## 边界与不适用
```

**必备**：何时适用、边界与不适用。这两节是 `capability` 区别于纯文档的地方——模型要据此自行决定用不用。

**语气**：陈述。不得使用"必须"、"一律"这类强制措辞（`R10`）——它是可选能力，用强制语气会让它在不该生效的场合被套用。

**判据**：agent 读完知道"我可以在什么情况下选用它"，同时知道"什么时候不该用它"。只回答了前者的是半份 skill。

**最小形态**：极短也可以合格，只要条件与做法齐备。`capability/git-proxy` 是一句话——"遇到网络问题时尝试代理端口 7897"——条件（遇到网络问题）与做法（代理端口）都在，合格。

## T7 最小合格形态与不合格示例

| 分类 | 最小合格形态 |
|------|------------|
| `self-function` | 一个范围节 + 一条编号条款 + 依据 + 验收证据 |
| `directive` | 适用场景 + 一条命名约束 |
| `task` | 一个前置条件（或声明无）+ 编号步骤 + 退出条件 |
| `capability` | 一句话，含"何时"与"怎么做" |

**当前不合格的例子**：`directive/ask` 正文两句话——"用户希望仅仅进行讨论而非实际修改或者编辑"、"请你在观察和思考后使用 show 与用户继续交流"。缺适用场景节，且它的 `description` 是"简单回复。"，不回答"什么情况下该引用我"（违反 `02-authoring-spec.md` 的 S2.2）。修复方向是补上适用场景，并把 description 改写为触发条件。

## T8 交付前的验收清单

写完一份 skill 后逐条核对，每条给出具体位置而不是"已完成"：

1. 分类按 T1 的顺序选定，且能说出为什么不是相邻的那一类。
2. frontmatter 只含被解析的字段，`activation` 显式写出（S2.1、S2.3）。
3. `description` 回答"什么情况下该引用我"，80 字符内（S2.2）。
4. 非 init skill 的目录名全小写、仅含数字与连字符，可被 `@` 引用（S3.2）。
5. `alias` 不与自身 name 相同，也不与其他 skill 的 name 或 alias 冲突（S2.5）。
6. 正文符合本文对应分类的必备节，并通过该分类的判据。
7. 体量在 S4.4 的上限内；超出的已拆分。
8. 关键要求写在正文，未只放在附属资源里（S5.1）。
9. 若需跨轮生效，已写入自维持机制；否则已声明只约束当前一轮（S6）。
10. 已检索确认没有其他 skill 覆盖同一件事（S4.2）。
