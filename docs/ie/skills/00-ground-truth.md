# Skill 概念体系与心智模型

> 状态：历史工程快照。本文中的 D0-D5、四种 show type 和 init 数量描述对应重建前实现；
> 当前 Self-Function 与 show 契约见 `../rebuild-2/`。

本文是 n0n 中 skill 体系的概念基础（ground truth）。后续一切关于 skill 的规范、分类、格式、写法与变更，必须首先与本文一致；与本文冲突的，以本文为准，并启动本文的受控修订。

本文不规定格式。frontmatter 字段表、正文模板、命名规则都是本文的下游产物，必须能从本文的结论推导出来。

本文的事实性结论有独立证据，见 `01-loading-evidence.md`；本文的口径裁定来自用户，逐条记录于第七节。

## 一、根本事实

**skill 是一段被放置到上下文特定位置的文本。除此之外它什么也不是。**

系统对它的处理只有四步：从目录发现、解析 frontmatter、读取正文、拼装进提示词（`scanner.ts` → `parser.ts` → `loader.ts` → `format-skill.ts`）。没有执行、没有隔离、没有返回值，没有任何一处代码会检查 skill 的内容是否被遵守。

由此拒绝三个错误理解：

1. **"skill 赋予 agent 能力。"** 错。加载任何 skill 后，工具集不变，权限不变，能做的事一件没多。变的只是上下文里多了一段字符串。
2. **"skill 是模块或插件。"** 错。模块有接口、有调用点、有边界。skill 没有——它的内容与用户的话、工具的返回、系统提示词混在同一个 token 流里，唯一的区隔是一对 XML 标签。
3. **"加载了就会被遵守。"** 错。文本不构成强制。它能起作用，靠的是内容本身的可执行性，以及它被放在了哪个位置。

正面结论：**定义 skill 的口径，本质上是定义"什么内容应当被放到哪个位置"。** 这就是为什么剖析必须从加载方式切入——加载方式即位置，位置即语义。

## 二、位置决定语义

同一份 SKILL.md，经不同通道进入上下文，含义完全不同：

| 通道 | 内容落点 | 它对 agent 意味着 |
|------|---------|------------------|
| init | system 之后一条独立 user 消息 | 前提契约：不论你要做什么，这些先成立 |
| `@name` | 该轮 user 消息内、用户请求正上方 | 用户在此处说了这段话 |
| `n0n skill read` | 工具返回 | 情报：你自己查到的资料 |
| auto | 先在 help 列表露出名字，再走 read | 你自己判断需要，于是去查（通道保留，自主边界未定，见第七节） |

前两条是**义务**，后两条是**信息**。这不是措辞差别：写在 SKILL.md 里的同一句祈使句，在 user 消息里是用户下的命令，在工具返回里只是一份文档的内容。一份 skill 若只有作为义务才有意义（例如"每一步都必须等我确认"），它就不适合被 read 通道消费；反之，一份纯粹的知识性材料（例如某个 API 的用法）放进 init 通道，就是在用契约的位置承载情报。

**R1**：写一份 skill 之前必须先确定它走哪条通道，因为通道决定了它该用什么语气、该有多长、该不该包含判据。通道不是写完之后随手填的 `activation` 字段，是设计的起点。

## 三、手动引用（`@name`）的契约

这是当前系统实际使用的主通道，也是唯一由用户主动触发的通道。

### 3.1 `@name` 不是话语，是动作——但用户视角相反

命中的整行会从用户可见文本中删除（`apps/code/src/skill-inject.ts:41-58`）。模型看不到用户"说过"这个词，只看到多出来的一段规则文本。

而在用户那一侧，skill 是他自己组织安装的，内容是他反复说过的要求的提炼（见第六节）。他键入 `@name` 时，主观上就是**在这里说了那段话**，只是没有重复打字。

两侧的落差是这条通道的关键：用户以为自己说了一句话，模型收到的是一段没有署名的规则。

**R2**：agent 不得把被引用的 skill 当作待评估的建议、参考资料或背景材料。它等同于用户在此刻亲口说出的要求，是本轮的活跃约束（术语见 `D0` 第 0.3.10 条），与用户直接下达的指令同级。

### 3.2 规则先于意图

拼装顺序是环境背景 → 被引用的 skill → `<user-request>` → 系统提示（`packages/format-prompt/src/index.ts:78-96`）。该处注释把 skill 位置标注为"规则/约束层"，把用户请求标注为"意图层"。

含义：用户在给出意图之前，先给出了解释这个意图的规则。方向是单向的——**用规则解释意图，不用意图裁剪规则**。当请求本身看起来不需要那么麻烦时，正确的反应不是简化流程，而是意识到用户认为它需要。

### 3.3 引用发生在展开之前

用户对 skill 的内容并不盲——他是全部 skill 的组织者与安装者，知道每一份里写了什么，因此手动触发是精准的。

盲的是另一件事：他键入 `@name` 的时刻，早于 agent 读到请求、早于任何一次调查，**这件事将怎样展开尚不存在**。没有文件被读过，没有障碍暴露过。

**R3**：一份 skill 不得要求"先看看任务是什么，再判断本 skill 是否适用"。引用时刻不具备这个信息。基于任务内容的适用性判断只能由 agent 在调查之后做出，那属于自主发现通道的职责，不能塞进手动引用。

**R4**：`description` 出现在补全菜单（`apps/code/src/multiline-input/mention.ts:32`）与 help 列表中，它服务的动作是"用户回忆自己有哪些 skill 可用"，不是"向陌生人介绍这是什么"。因此它必须写触发场景——什么情况下该引用我。

### 3.4 有效期是一轮，衰减从第二轮开始

被引用的 skill 绑定在那一条用户消息上，永久保留在原位，但不会随对话推进重新前移（`packages/format-prompt/src/index.ts:87` 无轮次判断，对照 `packages/format-prompt/src/index.ts:244-253` 仅对系统提示做轮次剥离）。

含义：它在被引用的那一轮紧邻请求，注意力权重最高；此后每增加一轮工具往返，它就被推远一分。**长任务中被引用的 skill 会衰减失效，这是位置决定的，不是模型不守规矩。**

**R5**：需要跨多轮持续生效的 skill，必须自带自维持机制——要求 agent 在每一轮重新登记、复述或核对它的约束。self-function 的 `D2.2.1`（每轮登记活跃约束）与 `D2.6.2`（纠正应登记为活跃约束并在后续每轮重新登记）正是这种机制。不具备自维持机制的 skill，只适用于单轮任务，规范上应当明示这一点。

### 3.5 引用是承诺，系统不做冲突检测

一次引用可能命中多份 skill（name 与 alias 同时匹配，`packages/skills/src/resolver.ts:21-23`），也可以引用本已常驻的 init skill（`apps/n0n-skill/src/api.ts:45-66` 不过滤 activation，会造成同一份正文出现两遍）。

**R6**：冲突消解的责任在内容本身，不在系统。skill 之间的职责必须互斥——同一件事被两份 skill 分别规定且要求不一致时，系统不会报错，只会让 agent 在两条规则之间随机选一条。这正是 self-function 重建前的失效形态（`docs/ie/rebuild/01-action-objects.md` 第一节 P2）。

## 四、其余三条通道的契约

**init**：每轮必然存在，无人可选，位置在最前端。因此它承担的必须是"不论用户要做什么都成立"的内容，且必须自包含——它不能引用一份 agent 看不到的文档。代价是每轮固定 token 开销，且它离尾部注意力窗口最远，靠篇幅是压不住的，只能靠可核对的判据。

**read**：agent 自己执行命令取回，内容落在工具返回里，是情报不是义务。它的价值在于按需——不占常驻预算。适合承载篇幅大、只在特定任务用得上、且以"知识"而非"纪律"为主的内容。

**auto**：机制完整但当前为空集——43 份 skill 中 0 份标记为 auto（`apps/n0n-skill/src/commands/help.ts:14`）。通道予以保留，但 agent 自主发现的边界尚未确定，在确定之前不新增 auto skill。理由见第七节第 1 条。

## 五、skill 对各工作对象的影响力不同

按 self-function 的动作对象划分，skill 的影响力并不均匀：

| 工作对象 | skill 能改变 | skill 不能改变 |
|---------|------------|--------------|
| D1 用户接收到的信息 | 消息的时机、类型选择、内容要求、语言 | show 工具的四种类型及其暂停行为（代码定义） |
| D2 本轮任务状态 | 阶段划分、确认门、放行判据、返工判定 | 无 |
| D3 认知输入 | 检索方式、输出规模策略、判断的证据要求 | 工具的返回结构与限额 |
| D4 仓库文件 | 变更方式、拆分规则、测试与注释要求 | 文件系统本身 |
| D5 环境与外部系统 | 确认义务、禁止手段、版本控制习惯 | 权限边界 |

两个极端值得单独指出：

**对 D2 的影响力最强。** 任务状态没有任何代码表示——不存在"阶段"这个对象，没有状态机，没有校验。它完全是文本约定的产物。因此 skill 说有四个阶段就有四个阶段，说这道门不放行就不放行。这是 skill 最有效的作用域。

**对 D5 的影响力最弱且不可靠。** skill 不是安全边界。它是文本，无法阻止任何一次实际调用。"执行前必须确认"能起作用，仅仅因为 agent 选择了遵守。

**R7**：需要硬保证的约束不得只写进 skill，必须落到代码（工具层的参数校验、白名单、确认交互）。skill 里的安全条款是提醒，不是护栏，规范中不得把它当作护栏来设计。

## 六、三类参与者眼中的 skill

| 参与者 | skill 是什么 | 他接触的部分 |
|--------|------------|-------------|
| 用户 | 自己重复表达的固化：把常说的话、常提的要求提炼成一个名字，便于引用 | `name`、`alias`、`description` |
| agent | 上下文中的一段文本，权威性取决于它从哪条通道来 | 正文 |
| 系统 | 文件系统上的一个目录，四步流水线的输入 | frontmatter（唯一契约，`packages/skills/src/parser.ts:50-57`） |

用户那一行是本文的定位来源，用户原话：skill "类似于提炼了我常说的一些话和要求等，便于我自己引用"。据此推出：

**R8**：skill 的边界应当贴合"用户会反复说出口的一件事"，而不是贴合某个技术领域或某个模块。一份用户从不会整段说出口的 skill，说明边界划错了——它要么该拆开，要么根本不该是 skill。

三者的接口点不同，因此对同一份文件的要求也不同：`description` 面向用户的选择时刻，正文面向 agent 的执行时刻，frontmatter 面向系统的解析时刻。当前体系的多数矛盾，根源都在于把这三层写混了——例如把"这个 skill 做什么"写进 description（那是正文的事），或把系统不解析的字段写进 frontmatter（那不是契约的一部分）。

## 七、已裁定的口径

以下五条来自用户裁定，是格式规范的直接依据。

### 7.1 auto 通道保留，自主边界未定

保留该通道。但 agent 可以自主决定加载什么、在什么条件下加载，这个边界尚未确定。

依据：全部 skill 由用户自己组织安装，用户知道每一份的内容，因此手动触发已经足够精准——自主发现要解决的不是"用户不知道有什么"，而是别的问题，而那个问题还没有被定义。

规范影响：在边界确定之前不新增 auto skill，也不删除相关代码路径。R3 指出的"基于任务内容的适用性判断"是该通道未来的候选职责，但尚未生效。

### 7.2 分类的判据是"期望模型如何遵守"

四个分类不按内容领域划分，按对待方式划分。用户原话逐条对应：

| 分类 | 期望模型如何遵守 |
|------|----------------|
| `capability` | 可以选择性地使用所提供的能力 |
| `directive` | 进一步约束我们沟通的模式（show） |
| `self-function` | 模型始终需要遵守、以实现相应功能 |
| `task` | 希望模型立即参考或执行的任务 |

**R9**：判断一份 skill 属于哪一类，问的是"我期望模型怎么对待它"，不是"它讲的是什么"。同一个主题的内容可能因期望的遵守方式不同而分属不同类——例如关于 git 的内容，作为可选能力属 `capability`，作为必须遵守的提交纪律属 `self-function`。

**R10**：强制性依次为 `self-function`（始终）> `directive`（约束沟通形式）> `task`（本次立即）> `capability`（可选）。写作语气应与该强度匹配：`capability` 不应使用"必须"，`self-function` 不应使用"可以考虑"。

### 7.3 init 是预留通道，与分类正交

init 的目的是减少约定、完全由配置驱动。它不是某个分类的专属属性——任何分类的 skill 都可以被配置为常驻。

`capability/git-proxy` 走 init 是有意的：它属于补充环境信息，需要在每轮都在场。

**R11**：`activation: init` 是一个配置位，不是一个分类。self-function 七章全部常驻是配置的结果，不是 self-function 的定义。因此规范不得写"init 只允许 self-function"。

### 7.4 多根目录不去重是有意的叠加

`~/.n0n/builtin-skills/` 与 `~/.n0n/skills/` 下的同名 skill 两份都会注入（`packages/skills/src/scanner.ts:73-77`）。这是有意的叠加语义，不是覆盖失败。

**R12**：写 skill 时不得假设自己是该名字下的唯一内容。用户可以在用户目录放置同名 skill 来追加内容，两份会一起出现。

### 7.5 旧 ground truth 的归档是有意的

`docs/ie/self-function-ground-truth.md` 被移入 `docs/archived/ie/` 是用户有意为之：`docs/ie/` 下的第一版文档包含大量在 ground truth 确定之前产生的噪音。清理由用户另行执行，本文不依赖那些文档。

已知副作用：`docs/ie/rebuild/04-handoff.md` 中按原路径引用该文件的位置已经悬空，待清理时一并处理。

## 八、现行体系与本文的偏离

以下八项已核实，是本文成立后待修复的项。逐项证据见 `01-loading-evidence.md` 第七节。

1. `category` 字段写在 8 份 SKILL.md 中，系统不解析，静默丢弃。
2. `function` 字段写在 7 份 self-function SKILL.md 中，同样不解析。
3. `write-a-skill` 声明 activation 为二值且默认 manual，实现是三值且默认 auto。
4. `write-a-skill` 要求附件平铺同级、严禁深层引用，loader 实际无条件递归收集子目录 md。
5. `license`、`compatibility`、`metadata` 三个受支持字段零使用。
6. 4 份 skill 的 alias 与自身 name 相同，属冗余。
7. `@` 补全菜单排除 init，`@` 解析本身不排除，两处口径不一致。
8. `data/skills/TODO.md` 在分类目录之外，永远不会被扫描到，内容已陈旧。
