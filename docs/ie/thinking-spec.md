# thinking 流程规格

> 状态：历史工程记录。本文的 F0-F5 与隐藏 thinking 要求已被重建，不再定义当前生产行为。

本文定义 n0n agent 思考过程的结构与措辞要求。流程覆盖 F0-F5 全部 6 个功能。

## 为什么表格要进上下文

模型无法凭空校准 O=8 与 O=7 的差别。每个 self-function 文档（F0-F5）包含该功能的 DFMEA 片段，模型在 thinking 中直接引用。

锚点写入系统提示词：
- **O（频度）**：O >= 7 = 模型固有倾向，必须在起草前用结构性步骤对抗
- **D（探测度）**：D >= 7 = 读一遍感觉不出来，必须按探测方式逐条量
- **S（严重度）**：S >= 7 = 一旦失效后果严重，命中即暂停或重来

## 流程结构

| 步 | 内容 | 覆盖 F | 不可跳过 |
|----|------|--------|---------|
| 0 输入登记 | 用户请求、任务类型、涉及文件/操作、活跃约束清单、**F0 在场 skill 登记与约束提取** | F0, F2 | 是 |
| 1 假设显式化 | 列出关键假设，标注不成立后果 | F1.1, F1.2 | 是 |
| 2 困难识别 | 识别本轮最可能出错的技术点 | F1.3 | 是 |
| 3 DFMEA 遍历 | 按 F0→F5 顺序遍历在场子功能，给出预防措施 | F1.4, F0.2 | 是 |
| 4 行动草案 | 工具调用序列、文件修改计划、产出描述 | — | 是 |
| 5 自检与纠正 | 逐条探测方式检查草案，命中即修正（含根因） | F1.5 + 各 F 探测方式 | 是 |
| 6 执行 | 输出工具调用或文本响应 | — | 是 |

### 第 0 步：输入登记（含 F0 处理）

登记不可省略。新增 F0 处理：

```
[输入登记]
- 用户请求原文关键部分: "..."
- 任务类型: ...
- 涉及文件: ...
- 不可逆操作: ...
- 活跃约束清单（从前文纠正提取）: [...]

- F0 在场 skill 登记:
  解析用户输入中的 @name:
    @step → directive/step (已加载)
    (无其他 @name)

- F0 约束提取:
  F0.1 [step] 每个操作步骤前展示计划并等待用户确认
  F0.2 [step] 每步输出当前进度和下一步计划
```

约束提取规则：
- 优先使用 skill frontmatter 中的 `f0_constraints` 字段
- 若无此字段，从 body 中提取含"不要/禁止/必须/确保/当 X 时应该 Y"的句子
- 每条约束格式："[skill名] 可检查的具体行为描述"
- 禁止模糊概括（"按照 step 模式""注意流程"）
- 登记为空的项输出"无"，不可省略

### 第 1 步：假设显式化

格式："假设 X（证据 Y）。若 X 不成立 → 后果 Z"

每个关键行动路径至少一个假设。至少覆盖：环境状态、用户意图（含 F0 在场约束的意图）、代码行为。禁止"无特别假设"。

### 第 2 步：困难识别

回答"我最容易在哪个技术点出错？"必须指向具体技术点。禁止"整体比较简单"（如确实简单，解释为什么简单：基于哪些客观指标）。

### 第 3 步：DFMEA 遍历

遍历顺序：F0 → F1 → F2 → F3 → F4 → F5。

对每个在场的子功能：给出失效风险评估 + 具体预防措施（非准则复述）。

区分两种跳过：
- 主观跳过（"这条本轮不重要"）→ 禁止
- 条件不成立（"本轮无代码修改，F4 不适用"）→ 允许，写判定依据

F0 遍历特殊要求：
- F0 中的约束来自用户动态加载的 skill
- 每条约束需要 O/D 估算（标注依据："模型固有倾向 → O>=7" 或 "用户明确指定 → O=3"）
- F0 约束的 O 通常低于 F1 的 O（因为它们是用户主动指定的，不是模型自发会违反的）
- 但 F0 中那些"对抗模型固有倾向"的约束（如 bugfix 的"先诊断根因"）O 仍然高

### 第 4 步：行动草案

粒度足够让第 5 步逐条比对。对 F0 约束，草案中标注"F0.1 满足点：此处将 show(ask user question) 确认"。

### 第 5 步：自检与纠正

逐条探测方式检查。F0 约束的检查标准与 F1-F5 相同：可指认证据。

根因纠正要求（F1.5）：修正含 1) 为什么错（根因）2) 修正策略（消除根因）3) 复检。

### 第 6 步：执行

草案与实际输出必须一致。

## 边界情况裁定

### 1. F0 为空时（用户本轮未加载任何额外 skill）

F0 登记："本轮 F0 在场约束：无"。F0 遍历跳过后三个条件（F0.1-F0.3 均为条件不成立：无加载 skill → 无约束需提取 → 无约束需遵守）。但**登记本身不可跳过**——必须输出"F0 本轮无在场约束"。

### 2. F0 约束与 F1-F5 约束冲突

裁定：F0 约束优先级高于 F1-F5（因为它是用户本轮明确指定的）。冲突处理：
- 识别冲突（在遍历中显式标注）
- 以 F0 为准执行
- 在自检中标注"F0 约束覆盖了 F?.? 的标准行为"

示例：用户 @ask（只讨论不修改），F0 约束"不修改任何文件"与 F4（代码质量）的遍历冲突。处理：F4 登记为"F4 本轮部分适用——F0 约束禁止修改文件，F4 的代码修改子功能（F4.1-F4.3）不适用，仅 F4.4（讨论中的测试策略）和 F4.5（讨论中的注释建议）适用"。

### 3. 简单任务下的 F0 分析

F0 的分析深度与 F1-F5 一致——复杂度评估驱动。简单任务下，F0 约束提取和遍历可加速但不跳过。

### 4. 多个 F0 skill 同时在场

依次登记，逐条提取约束。注意检测不同 skill 之间的约束是否冲突。若冲突，在登记阶段标注，在第 3 步遍历中裁定优先级（优先用户最新加载的 skill）。

## 系统提示词中应包含的 F0-F5 说明

```
你是 n0n agent。你收到的 skill 分为两类：
1. self-function (F0-F5)：产线的核心功能文档。每个包含功能定义和 DFMEA 表格。
   你的职责：在 thinking 中按表格逐条分析、预防、自检。不可跳过。
2. 用户加载的 task/directive/capability skill：作为 F0 的在场约束。
   你的职责：在第 0 步提取约束，在第 3 步遍历分析，在第 5 步逐条自检。

关键规则：
- F1-F5 的功能分析不可跳过（主观跳过 = F1.4 失效）
- F0 每轮重新登记——用户可能加载了不同的 skill
- 预防措施必须是具体决定（非准则复述）
- 自检必须产出可指认证据
- 简单任务仍需走完步骤 0-2（假设、后果、困难识别），步骤 3-5 可加速
```
