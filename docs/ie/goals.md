# 目标

## 总体目标

基于 IE（工业工程）和 DFMEA 方法论，重新设计 n0n agent 系统的提示词与 skill 组织体系。

核心理念：**约束登记 → DFMEA 预防 → 草案 → 自检 → 纠正 → 交付**

模型在采取行动之前，先登记本轮在场的约束和上下文，再对每个功能进行 DFMEA 遍历分析——识别可能的失效方式并提出预防方法，然后规划行动草案，再按照 DFMEA 给出的检测方式进行自检、发现并纠正问题，最后才输出工具调用和正式响应。

## 关键设计原则

### 原则 1：DFMEA 是遍历而非筛选

对每个功能逐一分析，不允许主观跳过。一旦模型自行判断"这条本轮不重要"，DFMEA 的系统性优势将消失。

需要区分两种"不分析"：
- 模型自行判断不重要 → **主观跳过**，禁止。
- 某约束本轮确实不在场 → **条件不成立**，允许，但要写出这个判定结论。空结论也必须输出，否则模型会逐渐连该检查的轮次也一起省略。

### 原则 2：预防优于探测

通过修改提示词结构和思考流程从根本上降低失效发生概率，而非依赖事后修正（如正则后处理、用户手动修复）。

n0n 的很多失效一旦发生就难以逆转：删除文件、推送代码、发送消息。必须在行动**前**建立预防机制。

### 原则 3：功能粒度可校验

每个子功能必须有明确的"正常"与"失效"边界。"安全操作""有效沟通"这类宏大定义无法直接校验，必须拆分为可操作、可观察的子功能。

### 原则 4：VOC 驱动 + 措施反推

所有功能定义优先追溯到真实的用户抱怨。同时，从现有 skill 的"不要/禁止"模式反推它们保护的底层功能需求。

现有 skill 是经验积累的产物——它们的"措施"大多是对的，但需要还原到功能-失效链中才能形成体系。

### 原则 5：S 做二值判断，O×D 做排序

- **S（严重度）**：决定"发现后是否必须重做"。n0n 的操作后果差异极大——删除文件（S=9）和格式不规范（S=4）不应该被同等对待。高 S 的操作命中即重来，不设阈值豁免。
- **O（频度）× D（探测度）**：决定注意力优先级。O×D 高的失效是措施应该重点投入的地方。

不使用 RPN（S×O×D）做阈值门控，原因与 share-ie 案例相同：一条失效如果预防和探测都做得好，即使 S 极高，乘积也会变小。用乘积做门控等于允许"因为我们防得好，所以出了也没关系"。

### 原则 6：产线即产品

n0n 本身是"产线"——提示词组织、skill 注入、工具执行、agent loop 是一个整体。DFMEA 分析的是这条产线生产"合格响应"的能力，不是某个孤立组件的质量。

这意味着：
- 功能的定义要从"产线必须做到什么"出发，而非"skill 写了什么"
- 失效模式要覆盖从输入理解到输出交付的完整链路
- 措施可以落到提示词结构、skill 内容、agent loop 逻辑、工具定义等不同层面

## 成功标准

- 每个现有 init skill 都能在 DFMEA 表格中找到它保护的功能和失效模式
- 模型在 thinking 中能完成完整的 DFMEA 分析循环，且遍历无跳过
- 改善后 O×D 较改善前有明显下降
- 碎片 skill 被合并为功能内聚的单元（每个 >= 128 tokens），解决 DSA 注意力稀释问题
- 新增约束或失效模式时有明确的归属位置，不再是"再加一个 skill"
