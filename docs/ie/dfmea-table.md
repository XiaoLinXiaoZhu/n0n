# DFMEA 完整表格

> 状态：历史工程记录。本文保留旧 F0-F5 方案的失效分析，不再定义当前规范或运行时行为。

## 概览

- 覆盖 6 个功能 × 25 个子功能，共 31 条失效链
- 评分锚点见 `methodology.md`
- F0 为新增——动态容器，每轮从用户加载的 task/directive/capability skill 中提取约束
- S 做二值判断（高 S 命中即暂停/重来），O×D 做排序

## 评分规则

| 项 | 规则 |
|----|------|
| S（严重度） | 基于操作后果的固有属性。高 S（>=7）命中即停止/确认 |
| O（频度） | **关键判断：这是不是模型在没有结构性对抗时的默认行为？** 是 → O>=7 |
| D（探测度） | 模型读一遍自己的输出能发现吗？不能 → D>=7 |

## 核心前提

模型的默认行为是走捷径（乐观代码、不加验证的假设、最小阻力路径）。这不是"偶尔疏忽"——是 LLM 训练分布的产物。因此 F1 的 O 值整体偏高。

## 关键发现

与 v1 相同，但新增 F0 的三个发现：

### 发现一：F0.2（约束模糊化）是一个隐蔽的高风险点

模型天然倾向于把"具体约束"概括为"模糊方向"——因为概括需要的 token 更少、更"自然"。如果约束提取这一步做得不好，后续所有 F0 分析都建立在模糊的基础上。

预防措施中对 F0.2 的要求是"提取时必须写可检查的具体行为"——这和 F1.1（假设显式化）有相同的结构：在源头把模糊变成具体。

### 发现二：F0 让 task/directive/capability skill 不再处于 DFMEA 框架外

这是 F0 的核心价值。在旧体系中，用户加载 @step 后，模型"切换到了逐步模式"——但这种切换不受 DFMEA 监控。F0 将加载的 skill 作为"在场的约束"纳入遍历，确保用户指定的每一个需求都被分析、预防、自检。

### 发现三：F0.1（遗漏登记）的 D=7——模型不会自发检查自己漏了什么

模型天然认为"我处理了所有输入"。如果用户说 @step @bugfix，模型解析了两个 @name，它不会自发问"我有没有漏掉第三个？"F0.1 的探测方式（核对用户输入中的 @name 是否全部有登记）是防止这种遗漏的最后防线。
