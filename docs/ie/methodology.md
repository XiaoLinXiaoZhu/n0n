# 方法论：IE/DFMEA 在编码 Agent 中的应用

> 状态：历史工程输入。本文保留旧方案的方法论记录，不定义当前规范或运行时行为。

## IE 核心方法

IE 的方法论用于处理"输入不完整、返工成本高、失效滞后显现"的生产场景：

1. **VOC（Voice of Customer）** — 系统性地收集客户声音，而非凭空假设
2. **CTQ（Critical to Quality）** — 将模糊的客户抱怨转换为可测量的关键质量特性
3. **功能分析** — 定义产品/服务需要实现哪些功能来满足 CTQ
4. **DFMEA** — 对每个功能分析失效模式、起因、影响，并在设计层面预防
5. **持续改进** — 基于新 VOC 和新数据迭代更新

## "如果缺失了会如何"

这是 IE 中功能分析的核心追问。定义功能时，必须追问：

> 如果这个功能缺失了，会发生什么？

两个作用：
- **验证功能是否必要** — 缺失了也没事，就不是真正的功能
- **发现被 VOC 遗漏的功能** — 用户不会抱怨"不存在的东西"，但追问能暴露隐性需求

## "措施还是需求"

面对一条既有约束时追问：

> 这是需求本身，还是解决某个需求的手段之一？

如果是手段，继续追问它保护的需求是什么。两条措施可以互斥，但它们背后的需求往往不冲突。

例如当前 n0n skill 中，`safety-no-sudo`（不使用 sudo）和 `safety-no-shortcut`（不走捷径）是两条措施。追问它们背后的需求：两者都保护"操作安全性与可逆性"这一功能（F2），但前者预防的是权限越界（O 低、S 高——后果严重但模型天然不会 sudo），后者预防的是遇到障碍时投机取巧（O 中高、S 中高——模型在遇到阻力时倾向于绕过）。

## 编码 Agent vs 创意写作 Agent 的关键差异

虽然方法论相同，但两个场景在失效特征上有本质差异：

| 维度 | 创意写作 Agent | 编码 Agent（n0n） |
|------|---------------|-------------------|
| 返工形式 | 正文展示后无法撤回 | 代码合并/消息发送后需修复 |
| 失效即时性 | 几乎所有失效都是滞后的 | 编译错误立即可见（D 低），逻辑错误滞后（D 高） |
| 工具使用 | 单一（生成文本） | 多样（exec/show/write/observe/reason/act） |
| 安全边界 | 内容合规 | 文件系统、网络、git 操作 |
| 与用户的交互 | 单向输出为主 | 双向：沟通确认 + 执行操作 |
| S 分布 | 集中在 8-9（高严重度） | 分布更广：从不规范（S=4）到删除文件（S=9） |

最关键的差异：**D（探测度）分布在两端**。编译错误、语法错误、工具调用格式错误——这些 D 很低，一跑就报。而逻辑错误、设计缺陷、安全违规——这些 D 很高，可能数周后才在线上暴露。

因此 DFMEA 的重点不是那些 D 低的失效（现有工具链已经覆盖），而是 D 中高的失效——那些"看起来能跑，但实际上有问题的"输出。

## DFMEA 七步法在本项目中的应用

| DFMEA 标准步骤 | 在 n0n 场景中的对应 |
|---------------|-------------------|
| 1. 策划和准备 | 确定分析范围：从用户输入到 agent 输出的完整链路 |
| 2. 结构分析 | 将 agent 的核心能力分解为可校验的功能和子功能 |
| 3. 功能分析 | 为每个子功能定义正常状态和失效状态 |
| 4. 失效分析 | 识别每个子功能可能的失效模式及其起因 |
| 5. 风险分析 | 评估 S、O、D，计算 O×D 排序 |
| 6. 优化 | 基于 O 和 D 设计提示词中的预防与自检措施 |
| 7. 结果文件化 | 本文档集即为文件化输出 |

## 措施只能作用于 O 和 D

这个约束来自 DFMEA 标准流程的"优化"节：建议措施旨在克服失效的起因和机理。这意味着措施降低的是 O（起因不再频繁发生）和 D（失效更容易被发现），而非 S。

S 是后果的固有属性。删除文件就是会丢数据，无论你做了多少预防。所以：
- **S** 用于决定"发现后是否必须重来"——高 S 命中即停止，等待用户确认
- **O** 和 **D** 才是措施能改善的部分——预防降低 O，自检降低 D

## S/O/D 评分锚点

评分不需要精确，但需要一致的锚点来确保相对排序可靠。

### S（严重度）锚点

| 分值 | 含义 | n0n 场景示例 |
|------|------|-------------|
| 9 | 不可逆损失 | rm -rf、force-push、删除分支、发送消息到外部 |
| 7-8 | 需人工修复 | 错误代码合并、破坏既有接口、覆盖未提交的修改 |
| 5-6 | 返工成本中 | 生成不符合规范的代码、遗漏错误处理 |
| 3-4 | 小修小补 | 格式不规范、注释不完整 |
| 1-2 | 几乎无影响 | 无 |

### O（频度）锚点

| 分值 | 含义 | n0n 场景示例 |
|------|------|-------------|
| 8-9 | 几乎必然发生 | 模型跳过思考直接行动、模型不主动对齐理解 |
| 6-7 | 高频 | 模型忽略某些约束、生成"看起来完整"的代码 |
| 4-5 | 中等 | 特定场景下触发 |
| 2-3 | 低频 | 需特定条件组合 |
| 1 | 极罕见 | 几乎不可能自然发生 |

关键判断：**它是不是模型的固有倾向？** 模型倾向于快速行动而非充分思考——这是训练分布决定的，不主动对抗就一定会出现。O 高。

### D（探测度）锚点

| 分值 | 含义 | n0n 场景示例 |
|------|------|-------------|
| 9 | 几乎不可能在交付前发现 | 跨模块的隐含假设被破坏、微妙的安全漏洞 |
| 7-8 | 需要系统化检查才能发现 | 未遵守某条约束、输出与用户真实意图偏差 |
| 5-6 | 仔细阅读可能发现 | 代码风格不一致、缺少某些边缘处理 |
| 3-4 | 容易发现 | 工具调用格式错误（工具系统会报错） |
| 1-2 | 自动检测 | 编译错误、语法错误 |

关键判断：**模型读一遍自己的输出能发现吗？** 格式错误能（D 低）；安全违规不能（D 高，模型天然认为"我的操作是安全的"）；理解偏差不能（D 极高，模型天然认为"我的理解是对的"）。
