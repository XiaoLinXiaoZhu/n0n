# 重建 06：消息的可审查性与可响应性

本文记录 D1 的第二轮重构。它处理的不是措辞润色，而是一个新的失效模式：`show` 报告包含了事实，却仍然难以审查、难以回复。

生效条款位于 `docs/ie/rebuild/draft/01-dialogue.md`，同步副本位于 `data/skills/self-function/D1-dialogue/SKILL.md`。

## 一、问题边界

原 D1 已经规定消息类型、发送时机、每类消息应包含的字段、证据和语言，但没有规定读者收到消息后要完成什么。由此产生四类失效：

| 失效 | 表现 | 缺失的契约 |
|------|------|------------|
| 材料齐全但难审 | 按调查顺序罗列文件、判断与操作，结论藏在中间 | 消息的主要读者任务 |
| 开头结论不稳定 | 先宣布完成，后文再补充未验证或未完成部分 | 结论、范围与实际状态必须一次给出 |
| 工作日志过密 | 每次工具调用、每个内部推理步骤都成为一条报告 | 哪些变化值得让用户知道 |
| 提问难回复 | 给出背景和选项，但用户仍要猜怎样回答才足够 | 最小充分回复接口 |

此前在生效 D1 中增加“操作性主张”的尝试识别到了第一个症状：消息需要一个中心。但它仍有三个问题：

1. “主张”只描述生产方要说什么，没有描述读者要完成的动作。
2. 它没有修改 D1.2.3“每个独立推理步骤都应有对应记录”，报告噪音的主要来源仍在。
3. 它把完成、查明、更正、建议、决策混在一个条款中，没有与四种消息类型及其系统行为建立稳定映射。

因此本轮不继续扩写“主张”，改用“读者任务”作为上位概念。

## 二、设计模型

一条消息的生产顺序固定为：

1. **确定读者任务**：了解进展、审查交付、做出决定、执行操作，四者取一。
2. **确定核心结论**：结论连同对象或范围、实际状态一次给出。
3. **选择内容结构**：按读者完成该任务时自然会问的问题组织，不按调查时间线组织。
4. **绑定证据**：证据紧邻所支持的事实，不在末尾集中堆放。
5. **定义响应接口**：需要回复时，明确最小充分的选择、字段、确认或动作。
6. **做一致性核对**：标题数量、清单数量、结论与边界逐项对账。

该模型没有引入新的消息类型。`working log`、`ask user question`、`request user assistance`、`final report` 仍由工具接口定义；本轮只补齐每类消息内部的信息组织。

## 三、条款变更

| 位置 | 变更 | 对抗的失效 |
|------|------|------------|
| D1.2.3 | 只即时记录会改变方案、范围、权限需求或完成状态的判断；排除例行调用和逐步推理转录 | 工作日志淹没关键变化 |
| D1.2.5 | 首次执行前给简短日志，之后只在阶段转换、方案改变或形成独立结果时更新 | 无节制的“关键节点”解释 |
| D1.3.1 | 工作日志只承载一个具体进展 | 一条消息包含多个互相竞争的结论 |
| D1.3.2、D1.3.3 | 提问与求助增加最小回复接口 | 用户必须猜怎样回答 |
| D1.3.5 | 最终交付开头明确结论、范围、状态，部分完成单列边界 | 先宣布完成再撤回 |
| D1.4.1 | 证据与事实相邻 | 读者自行建立证据映射 |
| D1.5.4 | 散文、列表、表格按关系选择 | 为统一格式牺牲扫描性 |
| D1.6 | 用“读者任务与信息组织”替换“操作性主张”尝试 | 从生产方材料中心转向读者任务中心 |

`apps/code/src/show-config.ts` 同步了四种 `show` 类型的接口描述。这样即使 D1 在长上下文中衰减，模型在准备调用工具时仍能看到同一份最低内容契约。

`data/skills/directive/research/SKILL.md` 原先要求每个独立推理步骤都发送工作日志，会在手动启用研究模式时直接覆盖 D1.2.3。本轮将它改为按可独立审查的研究结论设置检查点；研究模式仍比普通任务透明，但不再用消息数量证明投入程度。

## 四、边界与取舍

### 4.1 不要求每条消息只有一句结论

限制的是一个**主要读者任务**，不是一句话。最终交付可以同时包含变更、验证与决策，因为它们共同服务于“审查交付”；一个消息同时要求用户审查交付并执行外部操作，则应拆分。

### 4.2 不把全部内部排除过程交给用户

被否决的替代方案在公示和决策中是必要证据，D1.3.4 与 D2.3.5 继续要求提供。普通调查中的内部假设若不影响用户判断，则不输出；否则报告会重新退化为过程转录。

### 4.3 不规定固定报告模板

固定模板会让简单消息填充空字段，也会让复杂消息把重要关系塞进不合适的栏位。本轮规定的是读者问题与信息关系，具体使用段落、列表还是表格由 D1.5.4 决定。

## 五、行为探针

后续实测重点观察：

- 工作日志是否只在首次执行、阶段转换、方案改变或独立结果形成时出现。
- 最终交付的第一段能否直接回答“完成了什么、范围是什么、有没有未完成”。
- 事实与证据是否能就近一一对应，而不是从末尾证据清单反查。
- 提问是否能用一个编号、一句确认或一组明确字段直接回复。
- 被否决方案是否只出现在用户需要审查决定的场合。

若这些探针仍失败，应先判断是条款内容不充分、`show` 工具描述衰减、还是模型能力差异，不再直接追加写作口号。
