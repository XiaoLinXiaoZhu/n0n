# 重建 03：审查发现的分级与处置建议（工程记录）

本文是工程记录层文档，不注入运行时。它记录用户对草案（`docs/ie/rebuild/draft/`）的审查发现，按缺失后的严重程度分档，供决定哪些恢复、哪些移除。

分档依据是**缺失后会发生什么**，不是条目本身的篇幅或"重要感"：

- **一档**：缺失会导致不可逆损害、越权决策，或使质量失效无法被探测。
- **二档**：缺失会导致质量下降或返工，但后果可探测、可恢复。
- **三档**：缺失导致表述不一致或效率损失，不影响产出正确性。

来源列中，"旧位置"指现行 `data/skills/self-function/` 中的行号。

## 规范性附录的引入

第 18、27、28 条与"标准正文不含具体工具命令"的原则冲突。分析后认为冲突的范围比原先判断的小：

审查中被归为"简化"的条目实际分属三类：

| 类别 | 例子 | 是否与原则冲突 |
|------|------|--------------|
| 方法性具体化 | AAA 三段式、命名模板、拆分维度、`XXX` 标记 | **不冲突**。它们不涉及任何工具，属方法规范，本就该在正文 |
| 环境事实 | 输出预算含 stderr、执行产物路径与结构 | 冲突。它们是环境的属性，不是要求 |
| 工具口径 | `git apply`、`uv`、`bun`、类型检查命令 | 冲突。它们随环境与项目变化 |

因此原先的简化判断中，方法性具体化那一类是误判——它们被简化没有原则依据，应直接恢复正文。真正的摩擦只存在于后两类。

处置：设立**规范性附录 A：环境与工具口径**，与标准正文一同注入运行时。正文条款保持工具无关，需要具体口径时以规范性引用指向附录（例："按附录 A 规定的类型检查命令执行"）。

原则相应精确化为：**标准正文不含具体工具命令；具体口径集中于规范性附录，由附录作为唯一来源统一给出。**

这样处理的理由：

- 契约稳定性得以保持——环境或工具变更时只修订附录，不触动要求条款，符合 ground truth 第五节的受控修订。
- 口径统一——附录是唯一来源，不会出现同一命令在多章各写一遍且逐渐不一致（这正是旧体系的问题之一）。
- 可执行性不损失——附录随每次请求注入，模型读到条款即可读到口径。

代价：多一份文件，且正文与附录之间存在引用关系，附录条目被删除时正文引用会悬空。缓解方式是附录条目使用稳定编号，并在工程记录中维护正文引用点。

## 附录 A 拟收录内容

- 类型检查、测试、格式化与静态检查的具体命令。
- 补丁应用的具体方式（unified diff + `git apply`）。
- 隔离安装的具体方式（临时目录；Python 用 `uv`）。
- 复杂数据处理与简单命令的运行时选择（脚本用 `bun`；`git status`、`ls` 一类直接用默认 shell）。
- 输出预算的语义（覆盖 stdout 与 stderr 合计）。
- 执行产物的位置与结构（`result.json` 为状态元数据，`stdout.txt`/`stderr.txt` 为追加的原始输出）。
- 提交信息的创建方式（先写入文件再由文件创建提交）。
