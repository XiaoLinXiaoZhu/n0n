# 重建 01：动作对象划分与边界规则（工程记录）

本文是工程记录层文档，不注入运行时。它定义新 self-function 标准的章节骨架——按动作对象划分——以及判定动作归属的边界规则。

上游依据：
- `docs/ie/self-function-ground-truth.md`（GT）：唯一基准。
- 用户裁定：按动作对象划分；状态流程维护本身视为一个动作对象，以此承载 GT 第六节的阶段与确认门。
- 活跃约束 C1：禁止从旧 F0-F5 的分类、编号、组织倒推。旧文件仅作素材库。

本文不写条款正文。条款草案在 `docs/ie/rebuild/draft/`。

## 一、划分原则

P1 **一个动作只在一处被规定。** 某个动作的全部义务——执行时机、前置确认、执行方式、完成判据——写在它所属对象的章节内，不拆散到多章。

P2 **章节由作用对象定义，不由失效类型定义。** 旧体系按失效倾向切分（捷径偏好/不确定性/安全/质量/通信），导致"删除文件"这一个动作被 `F3:19`、`F3:29`、`F2:52` 三处规定且义务强度不一致。新体系以模型动作所改变的东西作为切分依据。

P3 **义务归属于被约束的动作，不归属于它调用的手段。**

P4 **跨切面清单必须消解。** 旧体系的"关键决策清单"（`F2:46-54`）和"危险操作清单"（`F3:24-38`）把分属不同对象的动作聚在一起，再要求读者反向查找。新体系中确认义务、告知义务直接写进各动作自己的条款。

P5 **要求与口径分层。** 正文条款规定要求（长期契约），规范性附录规定当前环境下的具体口径（随环境修订）。能由工具接口自身说明的内容，两者都不收录。

## 三、边界规则

按顺序适用，取首个命中：

R1 动作产出面向用户的消息 → D1。
R2 动作作用于任务状态本身（登记、扫描、放行、自检、返工判定）→ D2。
R3 动作不改变任何状态 → D3。
R4 动作改变仓库内被版本控制的文件内容 → D4。
R5 其余状态变更动作 → D5。

R6 一个义务同时涉及多个对象时，按 P3 归属于被约束的动作，而非被调用的手段。

R7 R1-R6 无法唯一判定时，查第四节的已裁定案例；仍无法判定的，作为新案例提交裁定并追加到该表——不得由起草人临时判断。

R8 内容属于"要求"还是"口径"：不随环境变化的归正文；随项目或运行环境变化的归附录 A；由工具接口自身声明的（参数语义、返回结构、限额、产物位置）两者都不收录。

## 四、已裁定的边界案例

| 动作 | 归属 | 裁定依据 |
|------|------|---------|
| 发起澄清提问 | D1 | R1。时机与形式同属发消息动作，按 P1 不拆分 |
| 公示某项决定 | D1 形式 + 触发条件由动作章规定 | R1；触发条件写在 D2.3.6、D4.3、D5.1 |
| 删除仓库内文件 | D4 | R4。确认义务写在 D4 该条款内 |
| 本地 git 提交、重置、分支操作 | D5 | 改变的是版本历史与工作区状态，非文件内容本身 |
| 推送、开 PR、发布 | D5 | 对象是外部系统 |
| 执行测试命令 | D5 管执行方式；D4 管"变更后必须执行"这条义务 | R6/P3 |
| 安装或移除依赖 | D5 | 本质是环境与供应链变更；`package.json` 变动只是其记录 |
| 读取执行产物 | D3 | R3 |
| 为获取更多输出而重跑有副作用的命令 | D5 禁止条款 | R3 反面：它改变状态 |
| 登记用户加载的临时指令并提取约束 | D2 | R2。旧 F0 的容器职责在此消解 |
| 具体工具命令、补丁方式、隔离安装方式 | 附录 A | R8 |
| 输出预算语义、执行产物位置与结构 | 不收录 | R8：由工具定义与运行时提示承载 |

## 六、变更记录

| 编号 | 变更 | 原因 |
|------|------|------|
| 001 | 消息的发出时机由 D2 改归 D1 | 初版把发消息动作的时机与形式分置两章，违反 P1。起草 D1 时暴露：D1 若不含时机，"提问前先自行调查"这类要求无处安放 |
| 002 | 引入规范性附录 A，正文不含具体工具命令 | 正文写命令会使环境变化直接触动契约条款，违反 GT 第五节的受控修订；口径散落多章则会随修订逐渐不一致 |
| 003 | 方案选型由"必须交用户选择"改为"默认公示、命中特定条件才待答复" | 用户指出该要求的实质是透明而非决定权转移。强制暂停会把常规判断推回客户，并使确认贬值。改为两级：D2.3.5 公示，D2.3.6 三类情形待答复 |
| 004 | 附录移除输出预算与执行产物结构两节 | 用户指出这些属工具接口自述范围。据此确立 R8 |
| 005 | 修正"批量提交"的表述 | 原表述"同批调用之间不得存在依赖关系"错误。核实 `packages/core/src/agent/scheduler.ts`：按 enqueue 顺序取队首、队首满足 canStart 才启动，即严格保序。根因是沿用旧文件 `F5:62` 的措辞未核实实现；据此新增 D3.5.2（对系统行为的描述应以实现或运行结果为依据） |
| 006 | 附录 A.2 增加实测耗时列与"显式设置等待上限"要求 | 默认等待值降至 20 秒后，`bun test` 实测 15.3 秒已接近该值，不显式设置会频繁转入后台 |
| 007 | 附录 A.3 补充 hunk 需含前后上下文 | 实测：缺少后置上下文行的 hunk 被 `git apply` 拒绝并报 `patch does not apply`，补上后置上下文行后 `--check` 通过 |
