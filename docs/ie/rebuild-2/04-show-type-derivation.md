# show 类型关系推导

状态：非规范性工程推导

本文从 `docs/ie/self-function-ground-truth.md` 推导用户可见生产消息的最小协议结构。
规范要求仍只由 `data/skills/self-function/production-quality/SKILL.md` 定义；具体枚举、渲染和循环行为由
show 工具接口与运行时实现定义。

## 1. 推导输入

ground truth 给出四个与 show 类型直接有关的事实：

1. 用户是客户，模型是承担生产和质量责任的受托生产方；每次请求形成订单，每轮工作形成生产周期
   （`docs/ie/self-function-ground-truth.md:21-27`）。
2. 客户与生产方之间的信息传递必须有规范和确认
   （`docs/ie/self-function-ground-truth.md:28-35`）。
3. 生产按确认门推进，只有完成验收并附带质量证据才可交付
   （`docs/ie/self-function-ground-truth.md:63-70`）。
4. 客户 review 是依据质量证据验收，不是替生产方发现返工
   （`docs/ie/self-function-ground-truth.md:72-76`）。

由此可知，一条用户可见生产消息不是任意文本，而是生产方提交给客户和运行时的一次协议动作。它必须同时回答：

- 当前生产周期是否继续；
- 客户是否需要承担下一步任务；
- 若生产终止，是否形成可验收交付；
- 运行时接下来应继续、等待还是结束。

## 2. `{type, content}` 的职责分离

show 只有两个字段：

- `type`：机器可辨的协议动作；
- `content`：该次动作的事实、范围、证据、理由和客户所需信息。

二者不能互相替代。运行时必须在读取自由文本之前就能决定继续、等待或终止；客户界面也必须知道是在查看记录、
提供信息、作出决定、执行操作，还是验收一个终止结果。因此生命周期和客户责任必须进入 `type`。

`content` 负责表达本次实例，不负责改变类型。例如正文中写“请确认”不能把生产记录变成 `customer decision required`；
正文中写“部分完成”也不能把不满足基线的产物变成合格交付。

## 3. 四类最小协议核

先忽略当前接口需要机器区分的具体客户责任和终止处置，只看客户、生产方与生产周期之间的最小关系，可得到四类协议核：

| 协议核 | 是否终止当前周期 | 客户下一步 | 产物与验收关系 | 运行时动作 |
|---|---|---|---|---|
| **record** | 否 | 无需立即响应 | 尚不作交付判定 | 显示、持久化并继续 |
| **request** | 否 | 履行一项客户责任 | 尚不能继续受影响的生产 | 显示、提醒并等待 |
| **delivery** | 是 | 验收交付 | 当前验收基线已经满足 | 显示、持久化并结束 |
| **non-delivery** | 是 | 处理未交付的终止结果 | 当前验收基线没有形成可验收交付 | 显示、持久化并结束 |

这四类由两个判定维度产生：

1. 当前生产周期是否结束；
2. 若结束，是否形成可验收交付；若不结束，是否需要客户立即履责。

它们是协议的最小内核。再合并会丢失运行时必须执行的继续、等待或终止动作；在这一层继续增加类别，则没有产生新的客户—
生产方关系。

## 4. 为什么四个核要展开为八个叶子

如果 show 使用结构化的嵌套字段，例如 `{ core, customerResponsibility, terminationDisposition, content }`，四个核可以直接作为
顶层类型。但现有接口固定为 `{ type, content }`，且运行时不能从 `content` 猜测客户责任或终止处置。因此所有会改变系统动作、
回复接口或终止解释的差异都必须成为 `type` 的叶子。

### 4.1 record 只有一个叶子

record 的系统关系始终相同：客户无需立即响应，运行时显示并持久化后继续同一生产周期。记录可以承载进展、关键决定公示、
风险变化或可复查证据，但这些是正文内容差异，不改变客户任务或生命周期。

| 协议核 | 叶子枚举 |
|---|---|
| record | `production record` |

继续拆分“进展记录”“风险记录”“决定记录”只会把内容主题误写成协议类型，不能增加机器可执行信息。

### 4.2 request 必须按三种客户责任展开

客户介入不是一种无差别的“回复”。根据委托责任，客户可能需要完成三种不同任务：

| 客户责任 | 判定边界 | 叶子枚举 |
|---|---|---|
| 提供信息 | 提供只有客户掌握、生产方无法自行取得的事实、材料或字段；不要求客户作取舍 | `customer information required` |
| 作出决定 | 决定结果、范围、约束、权限或由客户承担的重大风险 | `customer decision required` |
| 执行操作 | 完成生产方在当前能力或权限内无法代做的外部操作 | `customer action required` |

三者都等待客户，但回复接口不同：

- `customer information required` 等待事实或材料；
- `customer decision required` 等待选择、确认或授权；
- `customer action required` 等待动作完成及其结果。

若只保留一个 request 类型，系统和客户必须从正文猜测责任，生产方也容易把内部调查或专业判断伪装成一般提问转交客户。
三分后，运行时可以选择与客户责任相符的提示、回复界面和恢复路径，而不必先解释正文。

### 4.3 delivery 只有一个叶子

delivery 表示生产方正在提交满足**当前验收基线**的产物供客户验收。只要当前基线仍有一项必交条件未满足，就不存在交付协议核，
只能进入 non-delivery。

| 协议核 | 叶子枚举 |
|---|---|
| delivery | `qualified delivery` |

交付物的种类、数量、工作项构成和基线修订历史都写入 `content` 及质量证据，不产生新的 delivery 叶子。

### 4.4 non-delivery 必须按三种终止处置展开

没有形成可验收交付时，客户下一步和后续恢复责任取决于订单为何终止：

| 终止处置 | 判定边界 | 叶子枚举 |
|---|---|---|
| 生产暂停 | 存在明确、可解除的等待条件；条件改变后能够恢复生产 | `production suspended` |
| 生产失败 | 当前基线未满足，且没有有效恢复路径，或已确认无法在当前订单边界内完成 | `production failed` |
| 客户取消 | 客户明确撤回订单，且不要求把现有产物作为交付验收 | `customer cancelled` |

这三种终止都不是交付，但不能合并：

- 暂停需要保存恢复条件和恢复位置；
- 失败需要记录未交付原因、影响和已发生后果；
- 客户取消需要记录客户取消决定和必要收尾，不能被统计为生产失败。

系统需要直接区分它们，才能决定恢复入口、结果统计和客户下一步，而不能依赖正文关键词。

## 5. 八叶子总表

| 协议核 | `type` | 客户任务 | 生命周期 |
|---|---|---|---|
| record | `production record` | 按需复查，不需立即响应 | 继续 |
| request | `customer information required` | 提供缺失的客户专有信息或材料 | 等待 |
| request | `customer decision required` | 作出决定、确认或授权 | 等待 |
| request | `customer action required` | 完成生产方无法代做的操作 | 等待 |
| delivery | `qualified delivery` | 依据证据验收当前完整基线 | 终止 |
| non-delivery | `production suspended` | 了解等待条件；条件改变后另行恢复 | 终止 |
| non-delivery | `production failed` | 处理未交付原因、影响和后果 | 终止 |
| non-delivery | `customer cancelled` | 确认取消后的产物与收尾状态 | 终止 |

## 6. 判定树

对每条准备提交的用户可见生产消息，按以下顺序判定：

1. **这条消息是否结束当前生产周期？**
   - 否 → 进入第 2 步。
   - 是 → 进入第 4 步。
2. **受影响的生产是否必须等待客户立即履责？**
   - 否 → `production record`。
   - 是 → 进入第 3 步。
3. **客户必须完成什么责任？**
   - 只需提供生产方无法自行取得的信息或材料 → `customer information required`。
   - 必须决定结果、范围、约束、权限或重大风险 → `customer decision required`。
   - 必须完成生产方无法代做的操作 → `customer action required`。
4. **客户是否明确撤回订单且不要求验收现有产物？**
   - 是 → `customer cancelled`。
   - 否 → 进入第 5 步。
5. **是否正在提交满足当前完整验收基线的产物？**
   - 是 → `qualified delivery`。
   - 否 → 进入第 6 步。
6. **是否存在明确、可解除且解除后能恢复生产的等待条件？**
   - 是 → `production suspended`。
   - 否 → `production failed`。

若一条消息似乎同时命中两个请求叶子，说明客户有两个不同任务，应拆成两条等待消息；不得选择一个宽泛类型把另一个任务藏入正文。

## 7. 互斥、穷尽与最小性

### 7.1 互斥

- record/request 不终止，delivery/non-delivery 终止，因此两组互斥。
- record 不等待客户，request 等待客户，因此二者互斥。
- delivery 满足当前基线，non-delivery 不形成可验收交付，因此二者互斥。
- 三个 request 叶子按客户提供事实、作出决定、执行操作区分；一条消息只允许一个主要客户任务。
- 三个 non-delivery 叶子按可恢复暂停、无有效恢复路径、客户主动取消区分。

### 7.2 穷尽

穷尽范围是**生产方成功形成并准备通过 show 提交的用户可见生产消息**。任何这类消息要么继续当前周期，要么终止当前周期：

- 继续时，要么无需客户立即响应，要么必须等待客户履责；
- 等待时，客户只能提供信息、作出决定或执行操作；
- 终止时，要么形成满足当前基线的交付，要么没有形成交付；
- 没有交付时，要么客户取消，要么生产方仍有可恢复等待条件，要么没有有效恢复路径。

因此八叶子在该范围内穷尽。

### 7.3 最小性

删除任一分裂都会丢失机器需要的信息：

- 合并 record 与 request，会丢失继续或等待；
- 合并三种 request，会丢失客户责任及回复接口；
- 合并 delivery 与 non-delivery，会把未交付结果混入成功交付；
- 合并三种 non-delivery，会丢失恢复路径、失败责任或客户取消决定。

继续增加类型则必须证明产生了新的客户任务、生命周期或终止处置。仅有不同主题、阶段、产物数量、范围修订历史或机械错误来源，
不足以产生新叶子。

## 8. 为什么范围修订不是独立交付类型

客户可以显式修订订单结果、范围或验收条件。修订发生时，生产方必须更新当前验收基线并保留修订决定及前后差异。
终止时只判断产物是否满足**当前基线**：

- 满足当前基线 → `qualified delivery`；
- 不满足当前基线 → 根据恢复条件进入 `production suspended` 或 `production failed`。

因此范围修订是契约历史和验收证据，不是另一种客户任务或运行时生命周期。为它设置独立 type 会造成两个问题：

1. 同一份当前基线合格产物因历史路径不同得到不同成功类型，破坏交付判据的单一性；
2. 容易把交付前没有得到客户明确修订的未完成内容，在终止时追认为“修订范围”。

交付正文仍必须在验收相关时说明原范围、修订决定、当前基线和被移除内容，但 type 统一为 `qualified delivery`。

## 9. 多工作项不是 show type

复杂订单可以包含多个可独立验收工作项，且各工作项可处于不同阶段。这是订单内部生产状态，不是单条客户消息的协议动作。

- 若订单仍继续，消息按客户是否需要立即履责选择 record 或 request 叶子，并在正文说明相关工作项。
- 若订单终止，必须依据订单当前完整基线形成一个订单级 delivery 或 non-delivery 叶子。
- 已完成工作项不能把仍属必交范围的暂停或失败工作项遮蔽为合格交付。

为“部分工作项完成”“多个工作项暂停”建立 show type，会把任意工作项组合扩张成枚举，并迫使运行时理解订单内部结构。
工作项状态应留在验收基线、内部质量档案和 `content` 的证据映射中。

## 10. 运行时异常不是 show type

运行时异常包括进程崩溃、超时、连接中断、工具框架异常或 agent loop 未形成 show 就退出。它们是机制状态，不是生产方已经完成的
客户沟通动作：

- 异常可能发生在生产方尚未取得足够证据判断订单终态之前；
- 运行时不能替生产方编造质量判断或客户可验收正文；
- 机制错误可能导致生产暂停或生产失败，但必须在生产方恢复控制并完成质量判定后，才能提交对应 show。

因此运行时应在独立的错误通道记录异常。若能够恢复模型执行，生产方再根据当前基线和恢复条件选择
`production suspended` 或 `production failed`；若不能恢复，则保留为“未形成 show 的运行时异常”，不得伪造成八叶子之一。
