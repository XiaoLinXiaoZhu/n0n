# Self-Function 重建 2：推导与工程记录

状态：供审查的非规范性工程记录

日期：2026-08-22

本文只回答“草稿为什么这样组织”。规范要求只有
`data/skills/self-function/production-quality/SKILL.md` 一份来源；本文不独立规定生产行为，也不应被注入为第二份标准。

## 1. 输入边界

本轮设计只把 `docs/ie/self-function-ground-truth.md` 作为上位概念基准。现行
`data/skills/self-function/**/SKILL.md` 只用于确认生产活动覆盖面；`docs/ie/rebuild/`
只用于发现历史需求和需复核的实现事实。两者的章节、术语、编号和既有结论都不是新模型的前提。

现行文本涉及的生产活动可归纳为：沟通与交付、订单状态推进、信息获取、仓库产物修改、环境及外部影响、工具和项目口径。新草稿覆盖这些活动，但不沿用“动作对象首个命中”的组织方法。

## 2. 根本事实

以下事实直接来自唯一上位基准，后续关系均以编号引用它们。

- **G1 投产事实**：agent 每一轮工作都是撤回成本极大的生产活动
  （`docs/ie/self-function-ground-truth.md:5-7`）。
- **G2 反面边界**：质量不能因生产方是 AI 而降低，错误和返工会把真实成本留给客户，
  最终 review 不能无契约地转嫁给客户
  （`docs/ie/self-function-ground-truth.md:9-19`）。
- **G3 委托模型**：用户是客户，模型是受委托并承担生产与质量责任的生产方；每次请求是订单，
  每轮工作是生产周期（`docs/ie/self-function-ground-truth.md:21-27`）。
- **G4 质量组织**：体系由有效沟通、分阶段推进及确认门、行业标准和系统风险扫描共同构成
  （`docs/ie/self-function-ground-truth.md:28-35`）。
- **G5 标准地位**：self-function 是随生产开始生效的质量契约，不是生产方自行选择读取的工具
  （`docs/ie/self-function-ground-truth.md:37-42`）。
- **G6 标准形态**：标准应自包含，并包含范围、定义、要求和合格判据；失效模式只是要求的依据，
  不是正文组织方式（`docs/ie/self-function-ground-truth.md:43-49`）。
- **G7 文档分层**：标准规定合格生产，工程记录解释标准为何如此；变更先形成工程记录，再受控修订标准
  （`docs/ie/self-function-ground-truth.md:51-58`）。
- **G8 生产阶段**：订单生产依次经过契约确认、风险扫描、生产执行和验收交付，阶段之间存在确认门
  （`docs/ie/self-function-ground-truth.md:60-67`）。
- **G9 质量目标**：目标是一次做对、交付即合格；客户 review 是确认质量证据，返工责任属于生产方
  （`docs/ie/self-function-ground-truth.md:69-73`）。

## 3. 经实现核实的运行边界

这些事实只限制草稿如何与当前产品协作，不构成上位设计理由。

### I1. init 标准的发现与装载

- 当前实现扫描 builtin 和 user 两个 skill 根目录，两个目录的结果都会保留
  （`apps/n0n-skill/src/paths.ts:30-32`；`packages/skills/src/scanner.ts:73-88`）。
- 所有 `activation: init` 的 skill 按 `order` 和名称排序后加载
  （`apps/n0n-skill/src/api.ts:68-86`）。

### I2. 新会话中的注入位置

- 交互模式在启动时加载 init skills，并建立一个 `system_with_skill` 历史消息
  （`apps/code/src/repl/index.ts:96-108`）。
- 格式化时主提示词成为 system 消息，init skills 成为紧随其后的独立 user 消息
  （`packages/format-prompt/src/index.ts:157-175`）。
- skill 正文、脚本和资源以统一 `<skill>` 块格式化
  （`packages/format-prompt/src/format-skill.ts:17-42`）。

所以“随订单生效”在当前实现中的物理形式是会话历史中的稳定前缀，不是每条真实用户消息都复制一遍正文。

### I3. 后续真实请求与运行时协议

- 交互模式只在首次真实输入附带环境上下文；每条真实输入都会附带 tail runtime protocol
  （`apps/code/src/repl/index.ts:230-254`）。
- 历史请求的 hint 默认被剥离，当前请求的 hint 保留；init skill 前缀不受此机制替换
  （`packages/format-prompt/src/index.ts:244-253`）。
- runtime protocol 解释标签和 skill 冲突提示，属于运行时协议
  （`apps/code/src/tail-anchor.ts:1-12`）。

因此标准只应规定长期质量关系，不应复制标签名称、拼装位置等运行时协议。

### I4. 恢复会话延续既有质量契约

- 启动时虽会先加载当前 init skills，但成功恢复后 `history` 被日志中的完整历史直接替换，
  新建的 `systemMessage` 不会写入恢复历史
  （`apps/code/src/repl/index.ts:97-108`、`apps/code/src/repl/index.ts:152-164`）。
- 保存操作序列化完整 `DomainMessage[]`
  （`packages/shared/src/conversation-log/conversation-log.ts:41-70`），而
  `system_with_skill` 本身持有 skill 正文
  （`packages/types/src/messages/user.ts:17-32`）。

恢复同一生产周期时，原有质量契约随完整历史一起延续。用户已决定恢复不刷新契约；
这不是兼容性选择，而是“同一生产周期继续受原契约约束”的关系。

### I5. show 的可见性和循环行为

- show 工具自述为用户唯一可见的结构化输出；每次 show 都终止一次 agent loop
  （`packages/tools/src/show.ts:1-6`、`packages/tools/src/show.ts:45-84`；
  `packages/core/src/agent/loop.ts:241-251`）。
- 交互模式会把每种 show 写入 session；`production record` 会向用户渲染后自动续跑，
  三种客户责任请求会等待下一次真实用户输入，四种订单终态会结束当前生产周期
  （`apps/code/src/repl/handle-result.ts:35-101`；
  `apps/code/src/show-writer.ts:21-40`）。
- 当前工具配置说明 `production record` 用户可见并持久化，不提醒、不等待，系统会自动继续
  （`apps/code/src/show-types.ts:11-17`；`apps/code/src/show-config.ts:13-23`）。
- 自动续跑提示使用同一语义，并明确客户沉默不构成决定
  （`apps/code/src/production-record-nudge.ts:8-10`）。

生产记录可见并持久化，供后续复查和追踪关键决定；它不提醒客户，也不等待客户互动。
“可见”与“要求客户立即响应”是两个不同关系。生产记录结束一次 agent loop，但自动继续同一生产周期。

### I6. show 类型的当前表达能力

- show 的程序接口由 `type` 和 `content` 两个必填字段组成，`type` 的可选值由配置提供
  （`packages/tools/src/show.ts:45-84`）。
- 当前代码在一份结构化定义中声明四类协议核展开的八个叶子及其运行时生命周期；
  schema 和 app 工具配置均从该定义导出
  （`apps/code/src/show-types.ts:11-77`；`apps/code/src/schema.ts:12-17`；
  `apps/code/src/show-config.ts:13-32`）。

八个叶子为：`production record`、`customer information required`、`customer decision required`、
`customer action required`、`qualified delivery`、`production suspended`、`production failed`、
`customer cancelled`。接口类型直接表达客户责任或终止处置，系统不从 `content` 猜测控制状态。
四类协议核、叶子展开及边界的完整推导见 `04-show-type-derivation.md`。

### I7. 项目口径的当前注入

- 新会话首次输入的环境上下文来自 `n0n scan global`、`n0n scan project` 和 `n0n skill`
  （`apps/code/src/context-env.ts:31-44`）。
- `scan project` 的输出包含工作区、git 状态、项目指令和代码结构
  （`apps/n0n-scan/src/commands/project.ts:14-23`）。

标准只规定生产方怎样使用已生效的项目口径；项目上下文如何采集和传递仍由运行时负责。

## 4. 从事实建立关系

本节先定义关系，再说明草稿为何需要相应结构。编号 `R` 是设计关系，不是规范条款。

### R1. 委托与责任关系

由 G2、G3、G9 推出：

1. 客户拥有期望结果、约束、验收边界和由其承担的重大风险的决定权。
2. 生产方拥有并承担调查、技术方案、过程控制、自检和真实报告的责任。
3. “客户决定什么”与“生产方负责怎么保证质量”是两个同时成立的关系，不是一方把全部决定推给另一方。
4. 生产方内部的分类、检索和质量组织问题不属于客户输入，不能用提问转嫁。

### R2. 订单与验收基线关系

由 G3、G4、G9 推出：

订单只有形成可验收基线后才能投产。基线连接四类信息：客户要得到的结果、生产范围与产物、约束和权限、
可观察的验收条件。字面动作若不能稳定指向这些信息，只能作为候选手段，不能代替订单结果。

这不是要求客户逐项签字。生产方能够用证据唯一确定的内容由生产方确认；只有会改变结果、约束、权限或重大风险承担的
不确定性才需要客户参与。

生产周期从生产方取得一条真实客户请求开始，包含生产记录后的自动继续，直到形成质量终态、
等待客户提供信息、作出决定或执行操作，或被运行时异常终止。生产记录不结束生产周期，也不产生新的客户订单。
客户的真实后续消息是一份新订单和新的生产周期，可以延续或修订上一订单；客户的新决定必须更新验收基线，
不能被当作无状态续写。

### R3. 客户参与可用性是订单条件

由 G3、G4 和 R1、R2 推出：

客户是否会在本周期后续追加要求、作出决定或提供协助，是契约确认时应确定的订单条件，不是另一套生产模式。
生产方始终适用同一套阶段、风险、证据和验收关系。

当订单声明客户不再参与时，生产方使用周期开始时已给出的结果、约束、权限和输入自主履约；
这种安排不增加授权，也不把本应由客户明确承担的风险转给生产方猜测。若已有订单条件足以完成，就正常验收；
若缺少完成所必需的客户决定、权限或输入，就以生产暂停或生产失败终态记录退出，不发出等待客户回复的消息，
也不虚构客户决定。

### R4. 阶段是时间关系，不是对象分类

由 G4、G8 推出：

四阶段描述同一订单产物从“尚未定义”到“可验收”的时间关系。仓库修改、外部操作、沟通和信息获取可以在同一阶段同时发生，
不应被强塞进一棵互斥章节树。

复杂订单可以拆成若干可独立验收的工作项。每个工作项按相同次序通过确认门；互不依赖的工作项可以并行，
所以订单整体允许同时存在不同阶段的工作项。该关系避免用“全局阶段”阻塞无关工作，也避免跳过任一工作项的质量门。

### R5. 阶段产物形成证据链

由 G4、G6、G8、G9 推出：

每次向下一阶段转换，都需要前一阶段的可观察产物：

1. 契约确认形成验收基线。
2. 风险扫描形成方案、风险控制、权限和验证设计。
3. 生产执行形成目标产物、实际动作记录和偏差记录。
4. 验收形成判据到证据的对应关系以及真实终态。

下一阶段消费上一阶段产物；观察推翻上位产物时，转换方向必须返回相应阶段修订，而不是继续向前。
若某阶段无法形成放行产物，该事实成为终止证据，只能进入验收阶段记录客户取消、生产暂停或生产失败，
不能被当作已经通过缺失的确认门。

### R6. 记录的三种可见性义务是正交关系

由 G2、G4、G9 推出：

- 生产方需要足够的内部质量档案来控制过程。
- 需要客户决定时，要形成客户参与记录。
- 最终要提供客户验收所需的质量证据。

这三者不是互斥文档类型。同一证据可以先存在于内部档案，后来被选入决策记录或验收记录；但“内部完整”
不推出“全部轨迹都交给客户”。是否对外提供只看它是否帮助客户关闭不确定性、确认责任或验收结果。

### R7. 用户可见消息由四类协议核展开为八个叶子

由 G4 的有效沟通和 R1、R3、R6、R11 推出：

用户可见生产消息先形成四类最小协议核：

1. **record**：不终止，不等待客户，显示和持久化后继续；
2. **request**：不终止，等待客户履行一项责任；
3. **delivery**：终止，并提交满足当前验收基线的产物；
4. **non-delivery**：终止，但没有形成可验收交付。

由于当前接口只有 `{type, content}`，而系统必须直接辨认客户提供信息、作决定、执行操作三种责任，
以及生产暂停、生产失败、客户取消三种不交付处置，四个核展开为八个叶子：

| 协议核 | 接口枚举 |
|---|---|
| record | `production record` |
| request：客户提供信息 | `customer information required` |
| request：客户作出决定 | `customer decision required` |
| request：客户执行操作 | `customer action required` |
| delivery | `qualified delivery` |
| non-delivery：存在恢复条件 | `production suspended` |
| non-delivery：没有有效恢复路径 | `production failed` |
| non-delivery：客户撤回订单 | `customer cancelled` |

枚举字符串和生命周期属于工具接口；生产关系和合格判据以标准第 6、8 章为准。
互斥、穷尽和最小性的证明见 `04-show-type-derivation.md`。

### R8. 信息价值由减少的不确定性决定

由 G2、G9 和 R5、R6 推出：

有价值的信息至少完成一项：关闭一个影响后续动作的不确定性、确认一项责任或决定、提供一项验收证据。
带检查范围、依据和结果的阴性记录能够排除候选原因，因此有信息价值；“已遵守”“无问题”或复述条款不能区分是否实际检查，
没有证据价值。固定日志数量、固定假设数量和逐步思考转录都不能从该关系推出。

### R9. 风险关系由多个正交维度共同决定

由 G1、G3、G4 推出：

风险至少涉及影响范围、可恢复性、外部可见性、敏感性、权限、可检测性和恢复代价。这些维度可以同时成立，
不能用“首个命中”把一个动作只归入一类。客户承担且未在订单中授权的重大后果触发客户决定；
普通技术选择仍由生产方负责。

在“是否改变相关状态”这一单一维度上，计划动作可穷尽地分为观察动作与状态变更动作。该二分只用于确定执行前义务，
不替代上述风险维度；例如外部查询可能同时是状态变更、对外可见并涉及敏感信息。

### R10. 验证分为三个不同对象

由 G6、G7、G9 推出：

1. 程序机制验证检查注入、排序、持久化、工具 schema 和状态转换。
2. 标准语义审查检查概念推导、责任、覆盖、冲突和可验收性。
3. 实际生产质量评价检查真实订单是否一次做对、证据是否有效、客户是否需要返工。

三者的被验证对象不同，不能相互替代。关键词、snapshot 或 schema 测试可以证明机制输出，却不能证明规范语义正确；
语义 review 也不能代替真实生产评价。

### R11. 订单终态按交付关系与不交付处置判定

由 G2、G8、G9 推出一个互斥且穷尽的判定序列：

1. 客户是否明确撤回订单且不要求验收现有产物？是，则为客户取消。
2. 是否提交满足当前完整验收基线的产物？是，则为合格交付。
3. 若没有交付，是否存在明确、可解除并可恢复生产的等待条件？有，是生产暂停。
4. 其余没有形成交付且没有有效恢复路径的结束，是生产失败。

该维度只判定质量终态。运行时是否停止、工具是否返回 success、是否附带中间产物都是其他关系，不能改变质量终态。
客户显式修订范围时先更新当前验收基线；修订后基线得到满足仍属于合格交付，不产生另一种终态。

### R12. 多类规范来源按职责协作

由 G3、G5、G6、G7，并受 I2、I3、I7 限制，得到六个单一职责：

- 客户订单定义结果、范围、业务约束、客户输入和客户承担风险的决定。
- self-function 标准定义生产责任、阶段、用户可见消息的语义、证据和合格终态。
- 运行时协议定义消息标签、上下文位置、恢复、继续和等待行为。
- 工具接口定义具体工具名、枚举标识、参数、返回、可见性和执行机制。
- 项目口径定义当前仓库的命令、目录、代码风格和本地操作方式。
- 系统权限与安全边界定义当前生产不可越过的能力边界。

这些来源常常同时适用，不使用“首个命中”消除关系。某层不应复制另一层可独立修订的内容。

### R13. 恢复生产周期延续既有质量契约

由 G3、G5、G7 和 I4 推出：

恢复不是一份新订单，也不是重新开始契约确认。恢复同一生产周期时，延续该周期开始时已经生效的质量契约、
验收基线、客户决定和阶段状态；恢复动作不把它们刷新成恢复时的其他内容。

### R14. 可索引性是标准的可用性要求

由 G5、G6、G7 推出：

标准随生产生效，生产方必须能在工作中定位和反查具体关系与条款。因此规范需要稳定编号和内部索引。
物理上保持单文档或拆成多文档都可以；只要索引稳定、语义不重复、修订仍有唯一规范来源，物理组织就不是原则性决定。

## 6. 关键取舍

### 6.1 不沿用动作对象树

仓库文件修改可能同时改变执行环境、公共接口和外部系统；沟通也可能同时承担风险决定和阶段转换证据。
把它们归入唯一章节会丢失正交义务。新草稿以委托关系和阶段证据链为主干，在具体生产活动处让所有相关要求同时生效。

### 6.2 以可索引性而非物理文件数为目标

当前草稿保持为一个连续文档，并用稳定编号和内部索引支持定位与反思。未来可以为检索效率拆分物理文件，
也可以继续单文档；只要规范内容仍有唯一来源、不产生同步副本，两种方式都符合关系模型。

### 6.3 不规定仪式化数量

草稿没有固定日志间隔、固定选项数、非空假设清单、至少一个替代方案、每阶段必须输出给用户等数量要求。
它们不能从信息价值或责任关系推出。需要多少项由尚未关闭的不确定性和验收风险决定。

### 6.4 不要求公开完整内部轨迹

生产方仍需内部质量档案，但只把客户决策和验收所需的部分交给客户。内部推理语言、chain-of-thought 格式、
逐步排除过程和仪式化自述不是可验收产物，草稿不作要求。

### 6.5 不把具体工具和代码风格固化为通用质量关系

批量调用方式、具体命令、文件行数、编辑工具、测试命名、注释标记和某种运行时的选择会随工具或项目变化。
草稿只规定选择方法应控制什么风险、应产生什么证据；确切口径由工具接口和项目指令承担。

### 6.6 范围修订更新验收基线，不产生新的交付类型

客户可以在终止前显式修改范围或验收基线。修订决定发生后，终态按当前基线统一判断：
满足是 `qualified delivery`，不满足则是 `production suspended` 或 `production failed`。
原范围、修订决定和差异属于契约历史及验收证据，必须保留，但不改变交付协议。

## 7. 未进入草稿的历史性具体规则

以下类别在现行标准中存在，但不能直接由新关系模型推出，因此未作为通用 self-function 条款照搬：

- 固定输出语言、禁止 emoji、固定标题或消息模板。
- 提问固定为 2 至 4 个选项、每次至少列一个被否决方案。
- 每阶段产物必须非空、假设清单必须非空等“空集必须表演”的要求。
- 固定文件行数、目录深度、整体重写优先、禁止文本替换。
- 所有新测试都做故意破坏、固定测试命名和注释标记全集。
- 特定包管理器、格式化命令、脚本语言、补丁方式和提交信息写入方式。
- 用批次数量、工具调用顺序或生产记录频率证明工作充分。
- 对隐藏思考的语言、开头词或展示方式提出要求。

其中有些可能适合作为特定项目口径、工具安全策略或专项生产规范；没有上位关系支持时，不进入通用标准。

## 8. 用户 Review 后的正式设计决定

本节记录决定怎样改变关系模型，不产生独立规范要求。

1. **一次性、无后续参与的委托归入订单关系。** 客户参与可用性进入验收基线，形成 R3。
   它不产生专门生产模式，不改变 R1 的授权边界，也不分叉四阶段；输入或权限不足时直接由 R11 判定生产暂停或生产失败。
2. **恢复延续既有契约。** 恢复同一生产周期时不刷新质量契约，形成 R13；草稿只规定连续性，不引入身份或迁移机制。
3. **用户可见输出需要机器可辨类型。** R7 先形成 record、request、delivery、non-delivery 四类协议核，
   再因 `{type, content}` 接口必须直接表达三种客户责任和三种不交付处置而展开为八个叶子。
4. **init 分发细节不进入标准关系。** 标准只依赖“质量契约随生产生效”这一事实，不为分发实现增加额外治理义务。
5. **项目上下文采集不进入标准关系。** 运行时负责传递项目口径；标准只规定生产方怎样使用已生效的口径。
6. **可索引性取代物理组织偏好。** R14 要求稳定定位；单文档或多文档只是实现选择。当前运行时保留一份连续标准。
7. **生产记录语义已确定。** 它是可见、持久化、无提醒、无阻塞的记录类型，用于后续复查和关键决定追踪。
8. **自动化执行机制不扩大委托。** 授权只来自订单条件；生产方不从某种运行机制推导额外客户授权。

## 10. 旧工具链与思考附录的分层迁移

现行工具链附录和思考附录把稳定质量关系、当前实现事实、项目约定、操作偏好和模型适配偏好放在同一规范性层级。
这会使工具调度、命令、编辑方式或模型适配发生变化时，看起来像是“合格生产”的定义也发生了变化，与 G6、G7 和 R12
要求的单一职责不一致。

本次迁移采用四类去向：

1. 能从根本事实推出的稳定质量要求，只由
   `data/skills/self-function/production-quality/SKILL.md` 定义。
2. 工具或运行时的当前事实由真实接口和实现定义；跨项目的效率偏好放入运行时提示。
3. 只在特定仓库成立的命令和流程放入项目上下文。
4. 只为特定模型改善生成过程的隐藏格式偏好放入模型适配层。

前三类具体实现偏好和第四类模型适配偏好集中记录在
`03-implementation-preferences.md`。该文件不定义生产合格性，不能覆盖客户订单、Self-Function 标准、系统权限与安全边界
或真实工具接口。实现事实改变时，应更新负责该事实的接口、运行时、项目上下文、模型适配器和该偏好记录，
而不是修改质量标准来追随实现。

### 10.1 当前调度事实对迁移的影响

当前 scheduler 把调用放入有序队列，只检查队首是否满足该工具的 `canStart` 条件；
调用按入队顺序开始，但允许的调用可以并行，完成事件可以乱序
（`packages/core/src/agent/scheduler.ts:75-100`、`packages/core/src/agent/scheduler.ts:127-178`；
`packages/core/src/agent/__tests__/pipeline.test.ts:398-431`）。

默认工具只有在没有活动调用时才能开始；具体工具可以覆盖这一条件
（`packages/tools/src/session.ts:42-43`、`packages/tools/src/session.ts:95-105`）。
当前 exec 工具定义直接向模型说明同一响应内的提交顺序和分批条件
（`packages/tools/src/exec/definition.ts:40-47`），write 则声明不同路径可并行、相同路径串行
（`packages/tools/src/write.ts:33-45`）。

因此，旧附录中关于调度的事实不应成为长期标准。真实执行语义留在工具接口；
“条件成立时合并调用、需要先看结果再决定时分轮”只保留为运行时效率偏好。
