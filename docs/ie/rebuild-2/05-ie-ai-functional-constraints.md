# IE 用在 AI 交互约束上：从表面功夫到真实工作

状态：非规范性分享报告  
日期：2026-08-24

这不是一篇“如何再写一套更完整提示词”的文章。

它要回答的是另一个问题：

> 为什么一套看起来很像 IE 的 AI 约束体系，仍然可能只是表面功夫？
> 真正有效的 IE 思考，究竟发生在哪里？

本文以本仓库旧版 F0–F5 方案为反例材料。旧方案已经归档，当前规范入口是
[`production-quality/SKILL.md`](../../../data/skills/self-function/production-quality/SKILL.md)。
本文不替当前规范增加要求，也不要求其他项目复制当前的八种 show type。
旧版材料可参阅
[`CTQ 与功能定义`](../ctq-and-functions.md)、
[`DFMEA 表格`](../dfmea-table.md) 和
[`thinking-spec`](../thinking-spec.md)。

## 一、旧版为什么“像 IE”，却没有真正做 IE

旧版确实使用了不少 IE 词汇和形式：

- VOC → CTQ → Function → Sub-function；
- DFMEA；
- S/O/D 评分；
- 预防措施与探测方式；
- 阶段、确认门、放行判据；
- 术语和定义；
- 统一的 thinking 流程。

这些东西本身都不是错。问题在于，旧版把 IE 的产物形式当成了 IE 的核心，
却没有持续回答生产现场真正需要回答的问题：

1. 这次生产究竟要保证什么结果？
2. 哪个失效会让谁承担什么损失？
3. 失效发生前，哪一个控制点能够改变结果？
4. 这个控制由谁承担，依靠什么证据判断它生效？
5. 如果控制没有生效，下一步是返工、暂停、终止，还是更新契约？

如果这些问题没有被回答，再多的表格、定义和编号也只是在描述“我们很重视质量”。

## 二、表面功夫一：把不同关系平铺成 F0–F5

旧版把约束组织为六个功能：

| 旧功能 | 表面含义 |
|---|---|
| F0 | 用户动态约束容器 |
| F1 | 对抗模型捷径 |
| F2 | 暴露不确定性并追问 |
| F3 | 安全执行操作 |
| F4 | 代码正确且可维护 |
| F5 | 工具与通信规范 |

这看起来完整，但这些项目不在同一分类轴上：

- F0 是“约束从哪里来”；
- F1 是“模型可能怎样失败”；
- F2 是“客户沟通关系”；
- F3 是“风险和操作后果”；
- F4 是“产物质量”；
- F5 是“工具和表达方式”。

同一个生产动作可能同时涉及六个方面。例如修改一个公共接口：

- 它可能改变客户结果；
- 需要重新确认验收基线；
- 有跨模块风险；
- 需要修改代码和测试；
- 需要使用仓库工具；
- 可能需要向客户公示。

把它只归到 F4 或 F5，并不能帮助生产方知道这些关系如何共同生效。

真正的 IE 不是先问“这个属于 F 几”，而是先问：

```text
这个动作作用于什么对象？
产生什么状态影响？
影响谁？
当前授权是什么？
必须先形成什么证据？
什么条件满足后才能继续？
```

当多个关系都成立时，它们应当同时适用，而不是由一个平铺分类替代其他义务。

## 三、表面功夫二：把定义数量当成概念完整

旧版术语表列出了很多看似精确的定义，例如：

- 轮；
- 动作；
- 动作对象；
- 只读动作；
- 状态变更动作；
- 阶段；
- 确认门；
- 放行判据；
- 返工；
- 活跃约束；
- 证据；
- 不可逆动作；
- 公示；
- 待答复。

问题不在于定义太多，而在于定义之间的关系没有成为结构核心。

例如，“动作、动作对象、动作影响”本来是一个关系：

```text
动作
├─ 作用对象
└─ 产生的影响
   ├─ 不改变相关状态
   └─ 改变相关状态
```

如果把这些概念平铺，读者会得到一串名词，却不知道：

- 哪些是父概念和子概念；
- 哪些是同一关系中的不同角色；
- 哪些是互斥二分；
- 哪些定义可以由一个更高层关系推出。

真正有效的做法不是继续增加定义，而是先画出关系，再决定哪些关系需要稳定命名。

如果一个词只在一条规则中出现，而且没有独立的契约效果，就应该直接写清楚它的含义。
例如，与其写“每道门都要通过”，不如写：

> 阶段一必须形成验收基线，才能进入阶段二；阶段二必须形成风险控制和验证设计，才能进入阶段三。

后者少了一个专有名词，却增加了可执行性。

## 四、表面功夫三：把 DFMEA 表格当成生产动作

旧版的 CTQ 与功能定义把 9 组 VOC 转为 7 个 CTQ，再转为 F0–F5、25 个子功能和 31 条失效链。
这类表格适合做覆盖性盘点，却不自动构成有效控制。

表格化之后很容易出现三个错觉：

### 4.1 “列出来”被当成“控制住了”

例如写下：

```text
F1.1 假设显式化
预防：行动前列出假设
探测：自检时逐条核对
```

这只说明设计者知道“假设可能出错”，并没有说明：

- 哪些假设会改变本次订单结果；
- 哪些假设已有证据；
- 哪些假设一旦为假必须返回上游；
- 哪些低价值假设不值得单独公开。

IE 的控制不是把风险写进表格，而是让某个控制点在失效发生前改变生产路径。

### 4.2 S/O/D 数字被当成思考结果

旧版要求为很多子功能评估严重度、频度和探测度。数字如果不能改变行动，就只是精确的外观。

真正有用的风险判断应直接连接到处置：

```text
如果错误会覆盖客户未提交修改，
则执行前需要确认目标和恢复方式；
如果无法完整恢复，
则不能把它当作普通技术选择；
如果客户参与不可用，
则进入真实的暂停或失败处置。
```

这里没有 S=8 还是 S=9，但已经明确了控制方式、责任边界和终止路径。

### 4.3 覆盖率被当成质量

“25 个子功能都遍历了”不能证明订单做对。
一个真实订单中，如果最关键的验收条件没有证据，全部遍历仍然没有意义。

IE 的目标不是让每个表格单元格都非空，而是让高后果失效在正确的控制点被拦截。

## 五、表面功夫四：把思考格式当成质量控制

旧版 `thinking-spec.md` 要求固定六步：

1. 输入登记；
2. 假设显式化；
3. 困难识别；
4. DFMEA 遍历；
5. 行动草案；
6. 自检与执行。

附录 B 甚至规定分析必须以 `We need to` 开头并使用英文。

这类要求的问题是：它们控制的是文本外观，不是生产结果。

模型可以生成一份完整的：

```text
输入登记 → 假设 → 风险 → 预防措施 → 自检
```

但仍然可能：

- 读错了真实文件；
- 把客户未授权的假设当成事实；
- 没有覆盖真正的调用方；
- 把失败信号改写成“验证通过”；
- 在交付时遗漏关键边界。

反过来，一个模型不输出固定分析格式，也可能通过实际观察、正确修改和有效验证完成生产。

因此，真正应该约束的是可观察的工作产物：

- 验收基线；
- 风险和授权判断；
- 阶段产物；
- 变更记录；
- 验证证据；
- 终态记录。

隐藏思考格式最多只能是模型适配偏好，不能成为质量判据。

## 六、表面功夫五：把“透明”变成无信息汇报

旧版一度把工作日志定位为高频、可审计的判断日志，并要求首次执行前就发送日志。
这容易导致一种仪式：

```text
我将先读取文件。
接下来我会检查配置。
然后我会运行测试。
```

这些句子可能完全没有关闭任何不确定性，也没有形成任何新证据。
它们增加了消息数量，却没有增加客户对生产状态的理解。

有效的透明不是“让所有中间步骤都可见”，而是让有决策价值的变化可追溯：

```text
结论：token 过期的根因是刷新窗口与过期时间重叠。
证据：日志中的过期时间与刷新调用时间存在固定偏差。
影响：继续修改过期配置只会延后症状，因此改为修复刷新并发控制。
```

可以使用一个简单判据：

> 删除这条记录后，客户是否会失去一个重要结论、证据、决定或验收边界？

如果不会，它很可能只是过程噪声。

## 七、表面功夫六：把所有不确定性都问回客户

旧版 F2 把“歧义追问”作为通用功能，并在旧版消息规范中要求问题包含选项、后果和建议。
这解决了“模型盲猜”的一部分问题，却可能制造另一个问题：
生产方把自己应该完成的判断也交给客户。

真正需要先区分三种不确定性：

| 不确定性 | 谁负责关闭 |
|---|---|
| 生产方可以通过读取、搜索、运行或比较取得的事实 | 生产方 |
| 只有客户掌握的要求、背景、材料或外部状态 | 客户提供信息 |
| 结果、范围、授权、重大风险或契约取舍 | 客户作出决定 |

还有第四类常被误判：

| 情况 | 正确处置 |
|---|---|
| 生产方无法代做的外部操作 | 请求客户执行操作 |
| 生产方内部技术方案选择 | 生产方调查后自行决定 |

所以“遇到不确定性就问”不是完整规则。
更好的规则是：

```text
先关闭生产方能够自行关闭的不确定性；
只有客户独占的信息、客户责任决定或生产方无法代做的操作，
才形成客户请求；
一条请求只承担一种客户责任。
```

这也是为什么“需要客户确认”不能自动等于“需要客户决定”。

## 八、表面功夫七：把客户参与做成“标准强制制造无信息产物”

在委托生产关系中，客户不参与后续互动并不表示生产方可以停止报告。
客户不在线、不能继续参与或一次性给完要求，只改变了客户参与条件，
不改变生产方的质量责任。

旧式设计容易出现两个极端：

- 有客户参与：频繁提问、制造候选、等待确认；
- 无客户参与：自动猜测、代替客户批准、只在最后输出一个结果。

真正的判断是：

1. 生产方是否已经拥有完成订单所需的结果、约束、权限和输入？
2. 如果缺少信息、决定或外部操作，谁能够提供？
3. 在客户不可参与时，是否存在不依赖猜测的完成路径？

因此：

- 有价值的生产记录仍应可见并持久化；
- 需要客户责任时不能假装客户已经同意；
- 客户不可参与时不能用等待消息制造“无效等待”；
- 也不能用自动猜测把未授权风险写成成功。

这不是 headless 专用规则，而是同一委托关系在不同参与条件下的正常应用。

## 九、真正有效的 IE：不是写更多，而是改变工作方式

真正有效的 IE 思考，可以压缩成下面这条工作循环：

```text
观察真实对象
  → 建立当前订单和验收基线
    → 识别会改变结果的风险和责任
      → 在控制点形成证据
        → 执行并对比实际结果
          → 偏差返回上游修订
            → 依据证据验收或真实终止
```

它的每一步都对应实际工作，而不是必须输出的格式。

### 9.1 观察真实对象

不要先从规则猜系统是什么样。

- 判断文件内容，就读取当前文件；
- 判断程序行为，就检查实现或运行结果；
- 判断项目口径，就读取当前指令、配置和自动化；
- 判断外部事实，就取得满足时效要求的来源。

旧版 D3 中“不要用记忆代替观察”是有价值的，但它的价值来自真实调查，
不是来自要求模型写出“我已经观察过”的句子。

### 9.2 建立订单和验收基线

先弄清楚：

- 客户要得到或改变什么；
- 交付范围是什么；
- 哪些内容不在范围内；
- 产物是什么；
- 何时算完成；
- 哪些事实会改变结果、范围、权限或风险。

没有验收基线，就无法区分“已经完成”“只是有进展”“受阻”与“失败”。

### 9.3 识别责任，而不是识别话题

“风险”“架构”“问题”“进度”都是话题，不是责任分类。

要问的是：

- 这是生产方应完成的调查？
- 是客户必须提供的信息？
- 是客户必须作出的决定？
- 是客户必须执行的外部操作？
- 还是当前订单已经终止？

责任分类比主题分类更能决定下一步行为。

### 9.4 在控制点形成证据

证据不是最后才补写的报告，而是在控制点形成：

- 阶段一形成验收基线；
- 阶段二形成方案、授权和风险控制；
- 阶段三形成实际产物和偏差记录；
- 阶段四形成验收条件与证据的对应关系。

如果观察推翻了阶段一或阶段二的判断，就回到相应阶段修订。
不要等到最后用一段总结掩盖上游判断已经失效。

### 9.5 让控制改变路径

控制只有在会改变后续动作时才有价值：

- 发现缺少客户独占信息 → 请求信息，暂停受影响工作；
- 发现需要客户承担重大风险 → 请求决定，不先执行；
- 发现外部状态生产方无法改变 → 请求客户操作；
- 发现当前基线无法满足但有恢复条件 → 生产暂停；
- 发现没有有效路径 → 生产失败；
- 发现客户已撤回且不验收现有产物 → 客户取消。

如果一条规则只要求“记录一下”“提醒一下”“分析一下”，却不改变任何路径，
它很可能还没有成为真正的控制。

## 十、把旧版条款改造成真实工作

下面是几类典型转换：

| 表面规则 | 真实工作规则 |
|---|---|
| 每轮必须登记所有约束 | 先确认本轮生效的结果、范围、责任和外部条件，并把它们落到验收基线 |
| 每个任务都要列假设 | 只识别会改变当前路径、结果或恢复成本的关键前提，并用观察验证 |
| 每个阶段都要输出日志 | 只在阶段产物、重要结论或证据改变后续动作时记录 |
| 不确定时向用户提问 | 先判断不确定性由谁负责关闭，再请求客户承担的那一类责任 |
| 每个方案都公示并列出否决方案 | 只有会改变客户范围、公共契约、授权或风险的选择才需要客户决定；内部选择由生产方承担 |
| 所有条款都必须逐条遍历 | 按当前订单风险决定检查深度，并对适用的控制点提供证据 |
| 测试必须证明规范被遵守 | 测试证明机制；语义由审查判断；真实质量由订单评价 |
| 文件超过固定行数就拆分 | 当职责、依赖或变更边界已经混杂时拆分，行数只是信号 |
| 默认生成固定数量候选 | 由真实可行分歧决定是否生成多个候选 |

## 十一、如何判断一个约束是否真的有用

可以用五个问题审查任何新规则：

1. **它保护了哪个客户结果或生产责任？**
2. **它对应哪个具体失效后果？**
3. **它会在什么时候改变生产路径？**
4. **谁负责执行，谁负责提供证据？**
5. **如果删除它，哪个真实控制会消失？**

如果回答只能是：

- “这样看起来更规范”；
- “这样模型更像在认真思考”；
- “这样表格更完整”；
- “这样每个案例都有对应条款”；

那么它大概率是格式要求，不是功能性约束。

## 十二、给使用 IE 的 AI 设计者的工作顺序

建议按以下顺序工作，而不是先建目录、起名词、列功能：

### 1. 选一个真实生产问题

例如：错误交付、无效追问、未授权状态变更、失败后继续执行。
不要一开始就试图覆盖所有 AI 行为。

### 2. 观察实际失效

记录发生了什么、影响了谁、什么证据能够证明它发生、当时哪个控制点没有生效。
不要先把它归入 F1、F2 或 F3。

### 3. 找到可以解释多个案例的关系

例如“无效追问”和“自动猜测”可能都来自同一个责任划分问题；
“错误交付”和“部分产物冒充成功”可能都来自验收基线没有被直接表达。

### 4. 写最小约束

只写能够改变路径的条件、义务、禁止行为和证据。
不要为了覆盖率把所有可能句式都收进标准。

### 5. 把约束放入正确层

质量关系进标准；工具事实进接口；运行时行为进运行时；任务步骤进 task；
表达节奏进 directive；项目命令进项目口径。

### 6. 用机制实现，再用语义审查

先确保系统能机械执行继续、等待、终止、持久化和恢复；
再由人审查分类是否合理，不能反过来用机械测试证明概念正确。

### 7. 用真实订单评价

观察客户是否需要返工、是否被不必要地打断、是否承担了生产方责任，
以及终态和证据是否真实。

## 结语

旧版 IE 组织的问题，不是“表格太多”这么简单，而是把 IE 的记录工具误当成了生产控制本身。

真正有效的 IE 工作不要求模型看起来像一名认真填写表格的工程师。
它要求系统在真实生产中：

- 认清委托关系；
- 让责任落到正确的一方；
- 在正确阶段形成正确证据；
- 在风险真正发生前改变路径；
- 只让客户处理客户必须处理的事情；
- 把机制状态和质量判断分开；
- 在交付前发现并修复自己的问题。

因此，面对一个新失效，最有价值的问题通常不是：

> “我们应该再加一条什么规则？”

而是：

> “哪个稳定关系没有被表达？哪个控制点没有形成证据？谁本来应该承担这项责任？”

这三个问题，才是把 IE 从文档外观转化为 AI 生产能力的起点。
