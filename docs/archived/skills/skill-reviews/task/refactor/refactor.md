# refactor

> 来源：builtin | 激活：auto

## A. 类型组成

**Methodology**（主要）。6 个步骤的线性 SOP，结构与 bugfix 一致：每步有退出条件和 progress 格式模板。

## B. 作用与核心思想

确保重构不引入行为变更。

6 步流程：理解现状 → 定义目标 → 建立安全网 → 执行重构 → 验证等价 → 检查遗漏。

核心思想有三层：
1. **重构 ≠ 改善**——必须先验证动机有效（消除重复、解耦、接口简化、类型安全），排除无效动机（"看起来不够干净"、"未来可能需要"）
2. **安全网先行**——没有测试覆盖就不重构
3. **行为等价**——重构前后外部行为必须一致，typecheck + 测试 + diff 检查三重验证

与 bugfix 共享同一种"报告驱动的步骤推进"机制。

## C. 与执行工具和 progress 的结合潜力

**已深度结合**，模式与 bugfix 一致。

工具映射：
- 理解现状 → observe（读代码、搜引用、查 git log）
- 定义目标、建立安全网 → reason（分析动机、评估测试覆盖）
- 执行重构 → write/edit + act（修改代码 + typecheck）
- 验证等价 → act + observe（运行测试、检查 diff）
- 检查遗漏 → observe（检查文档、注释、TODO）

progress 使用与 bugfix 相同的模式：每步 working，最终 completed。

## 人类评价

嗯，这个还有一个很重要的概念：
- 显性遍历而不是宽范围评估和总结。
- 因为我们的处理能力（不论是人还是模型）（或者叫处理野）是有限的，应该每次观察3~4次就简单总结一下。

## AI 回应

"显性遍历而不是宽范围评估和总结"——这个概念很重要，值得在 refactor skill 中显式化。

具体含义：模型在"理解现状"步骤中，不应该"读完所有相关代码然后给出总结"，而应该"每读 3-4 个文件就提交一个 progress(working) 小结"。原因：

1. **处理视野有限**——不论人还是模型，一次性处理太多信息会遗漏细节
2. **小结迫使理解**——每 3-4 次观察后写一段小结，相当于自我检验"我理解了吗"
3. **可追踪**——progress(working) 记录了每次小结，用户可以看到模型的理解是否正确，在偏差出现时及时纠正

这可以作为 research directive 的一个原则推广：不只是"高频汇报"，而是"显性遍历——每 N 次观察后小结一次"。
