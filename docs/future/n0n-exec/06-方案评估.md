## F1（阻塞级）：后台化后子进程输出全部丢失

### 缺陷

03-方案设计 §run 行为流程 步骤 10b：

> 若超过 waitfor：写入 bg-procs/<pid>.json ... n0n-exec 退出（exit 0），命令继续在后台运行

同时步骤 7–8 规定子进程 stdout/stderr 用 pipe，由 n0n-exec 转发。

两者组合的后果：n0n-exec 一退出，pipe 的**读取端随进程关闭**。子进程后续每次写 stdout 都会收到 EPIPE。

### 实测证据

让子进程自己记录每次 `echo` 的成败，n0n-exec 模拟在 waitfor 到点后 `process.exit(0)`：

```
wrote 1 OK
wrote 2 FAILED(EPIPE)
wrote 3 FAILED(EPIPE)
...
wrote 10 FAILED(EPIPE)
LOOP_END
```

只有 n0n-exec 退出前的第 1 行成功。**后续输出 100% 丢失，且不可恢复。**

### 影响范围

这不是边缘退化，它否掉方案的核心卖点：

- **DO-1 度量**："启动 dev server → 查看状态 → 终止"。dev server 的编译错误、请求日志全部丢失，"查看状态"退化为只能看到 PID 是否存活。
- **03-方案设计 §status 承诺**："若进程仍在后台运行，额外输出当前 stdout/stderr 的快照"。session dir 中没有任何后台阶段的输出，**该功能无数据来源，无法实现**。
- **P4 无执行历史**：方案声称要解决，但对后台进程恰恰解决不了。

### 与当前架构对比：这是净倒退

当前架构没有这个问题，原因在 `executor.ts:startBackgroundSync`：agent 进程常驻，`pumpStream` 持续读 pipe 进 `stdoutChunks` 桶，每 3s 落盘到 `exec_bg_<pid>.log`。读取端永不消失，因此永不 EPIPE，后台输出完整可回溯。

方案用"架构解耦"换来一个当前不存在的数据丢失缺陷。

### 04-DFMEA 为何漏掉

FM-06 是唯一涉及流式输出的条目，但它只分析"stdout 与 stderr 交织导致乱序"，完全没有触及"读取端消失"。因此 04 结论——

> 所有失效模式在应用缓解措施后 RPN < 50，无阻塞性风险

——不成立。按其自身标度，F1 应为 S=8（数据永久丢失，无 workaround）、O=10（每次后台化必然发生）、D=7（需端到端测试暴露），**RPN = 560**，远超"≥200 必须修改设计"的阈值。

### 修复方案（已实测验证）

**子进程 stdout/stderr 不接 pipe，直接接文件 fd。**

`node:fs.openSync` 取 fd 传给 `Bun.spawn` 的 `stdout`/`stderr`。文件描述符由内核持有，与 n0n-exec 进程生命周期无关。

实测：n0n-exec 在 1s 后退出，子进程 12 行输出全部 `wrote N OK`，日志文件 12 行完整，完成标记 `DONE_ALL` 正常。

实时流式可同时保留——n0n-exec 一边让子进程写文件，一边 tail 该文件转发到自己 stdout：

```
[fwd] OUT 1 ... [fwd] OUT 5
>>> WAITFOR REACHED, n0n-exec exits now
（之后子进程继续写到 OUT 12，文件 12 行完整）
```

附带收益：
- 同一文件天然保序，**FM-06 一并解决**，不需要 `[out]`/`[err]` 行前缀方案
- 比当前架构更强：当前架构 agent 退出后输出同样会断，文件 fd 方案不受影响
- `status` 子命令的输出快照有了真实数据来源

## F2（高）：安全检测迁移是净倒退

### 缺陷

03-方案设计 §安全检测迁移 要求：检测逻辑移入 n0n-exec + 支持 `--force` 跳过。FM-01 缓解措施要求 n0n-exec 在 PATH 上可用（`which n0n-exec`）。

三者组合 = 在 PATH 上提供了一个官方的黑名单绕过器。

### 实测证据

调用真实的 `packages/tools/src/exec/security.ts`：

| script | 提取出的命令名 | 黑名单命中 |
|--------|--------------|-----------|
| `rm -rf /tmp/x` | `["rm"]` | `rm` |
| `n0n-exec run --force --script 'rm -rf /tmp/x'` | `["n0n-exec"]` | **null** |
| `sh -c 'rm -rf /tmp/x'` | `["sh"]` | **null** |

`extractCommandNames` 只看每段首命令，嵌套调用的内层命令不可见。

### 定性

第 3 行说明该类绕过在当前架构下已部分存在（这是既有缺陷，不是方案引入的）。但方案把它从"需要绕路"变成"有专用、有文档、在 PATH 上的工具"，且 `--force` 的设计意图就是跳过检测。

FM-04 讨论了 shell 语法覆盖不全（here-string、process substitution），评 RPN=144，却没有识别自己引入的这条路径。其缓解措施"`--force` 不接受环境变量设置，仅接受显式命令行参数"对此无效——模型写的就是显式命令行参数。

### 建议

安全检测**保留在 agent 侧**（`security.ts` 不迁移）。理由：黑名单是 agent 对模型的约束，不是执行器对调用者的约束。把约束放到被约束者可以直接调用的 CLI 里，是信任边界错置。若坚持迁移，`--force` 必须改为只接受来自 agent 的一次性 token（如环境变量传入随机 nonce，且 nonce 不出现在 argv 中）。

## F3（高）：DO-4 与 DO-5 冲突，tag 无法从 LLM 侧到达

DO-5 依赖 `--tag` 实现"同 tag 旧进程自动替换"。但 `packages/types/src/tool-args.ts:63-72`：

```
ExecParamDefs = [runtime, cwd, waitfor, script]   // 仅 4 项，无 tag
```

而 DO-4 要求"工具参数 schema 保持不变"，度量为 `preview-tool-definitions.ts` 输出前后一致。

- 加 `tag` 参数 → 违反 DO-4，度量失败
- 不加 → 模型永远无法指定 tag，DO-5 落空，`--tag` 成为死代码

两个目标不可同时满足。方案未识别此矛盾。00-术语定义 中 `execute()` 签名列了 `tag?: string`，但没说明模型如何提供它。

**需决策**：放弃 DO-5，或修订 DO-4 允许新增可选参数（新增可选参数对现有调用兼容，代价可控）。

## F4（中）：并发假设的依据是错的

FM-03 将 session 目录并发写入评为 O=2，依据：

> 当前 scheduler 以串行调度为主，并行 exec 场景极少

核对代码：

- `packages/core/src/agent/scheduler.ts:5` 模块注释："有序队列 + 队首条件等待，**并行性自然涌现**"
- `scheduler.ts:117` 按 `canStart` 回调决定并发启动
- `packages/tools/src/index.ts:112-123` `makeExecEntry` **未声明 canStart** → 落到 `scheduler.ts:33` 的 `defaultCanStart`（等 active 清空）

所以 exec 今天确实串行，但**这是默认值的巧合，不是设计保证**。对比：`write` 在 `index.ts:132` 显式声明 `pathExclusiveCanStart`，`show` 在 `index.ts:177` 声明 `() => true`——框架的意图是各工具自主声明并发策略。

而 05-实施计划 恰好要修改 `packages/tools/src/index.ts`。任何人给 exec 加上并发策略，run index 分配立刻撞车。

FM-03 的缓解措施（用 `mkdir` 原子性分配 run index）本身正确，建议**无条件实施**，不要因为 O=2 而降级处理。

## F5（中）：exit code 2 协议撞车

03-方案设计 §安全检测迁移 用 exit code 2 表示"需用户确认"。实测常见命令的 exit 2：

| 命令 | 退出码 |
|------|-------|
| `python3 argparse` 参数错误 | 2 |
| `grep --bogus-flag` | 2 |
| `jq --bogus` | 2 |
| `diff` 文件缺失 | 2 |
| `sh -c 'exit 2'` | 2 |

n0n-exec 需转发子命令退出码（03 步骤 10a："以命令的 exit code 退出"），因此无法区分"我要确认"和"子命令返回了 2"。

**建议**：确认信号走 result.json 的 `status: "needs_confirmation"` 字段，或用保留区退出码（如 120+），不要占用低位常见值。

## F6（低）：FM-05 缓解措施在目标平台不可用

FM-05 缓解措施原文：

> kill 前校验 `/proc/<pid>/stat` 中的启动时间是否匹配

实测：`ls /proc` → `No such file or directory`。macOS 无 procfs，而 01-设计目标 的开发验证环境即 macOS。

替代方案实测可用：`ps -p <pid> -o lstart=` → `Wed Jul 22 20:36:29 2026`。

PID 重用校验的思路正确（防误杀，S=7 合理），仅需替换实现手段。

## F7（低）：性能开销

| 路径 | 10 次平均 |
|------|----------|
| 直接 spawn `sh -c echo`（当前架构） | 3ms |
| 经 bun CLI 中转再 spawn（新架构） | 11ms |

约 3.7 倍，绝对值 +8ms。exec 是最高频工具，但 8ms 相对 LLM 往返可忽略。

05-实施计划 已将此列为风险并计划测量，处理得当。**不构成阻塞**，此处仅提供实测数值供决策。

补充核对：`--script` 走 argv 的长度上限，实测 100KB–1MB 全部通过（`ARG_MAX` = 1048576）。常规脚本无风险，但超大 script（如内联大数据）会在 1MB 处硬失败，且 argv 对同机其他用户可见（`ps` 可读），敏感内容会泄露。建议 script 通过 stdin 传入——01-设计目标 已将 stdin 模式列为 Non-Goal 并指向 `docs/future/exec-stdin.md`，建议提前到本次实施。

## 修订建议

保留：整体架构方向、n0n-exec 无状态 CLI 定位、session dir 结构、05 的三阶段划分。

必须修订：

1. **03 §run 步骤 7–8**：子进程 stdout/stderr 改为文件 fd 重定向，n0n-exec 通过 tail 文件实现流式转发（F1，已验证）
2. **03 §安全检测迁移**：检测保留在 agent 侧；或为 `--force` 设计 argv 之外的 nonce 机制（F2）
3. **01 DO-4/DO-5**：二者取一，或明确 DO-4 允许新增可选参数（F3）
4. **04 FM-03**：原子 run index 分配改为无条件实施，不依据"当前串行"降级（F4）
5. **03 §安全检测迁移**：确认信号改用 result.json 字段或高位退出码（F5）
6. **04 FM-05**：`/proc` 改为 `ps -p <pid> -o lstart=`（F6）
7. **04 结论段**："无阻塞性风险"需在 F1 修订后重新评估

建议补充：script 走 stdin 而非 argv（F7 补充）。
