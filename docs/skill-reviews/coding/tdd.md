# tdd (mattpocock)

> 来源：mattpocock/skills/engineering | 激活：auto

## A. 类型组成

**Methodology**（主要）。红绿重构的 TDD 流程，附带 5 个 reference 文件详细展开子话题。

## B. 作用与核心思想

强制执行 test-first 开发的纵向切片循环。

4 步流程：Planning → Tracer Bullet → Incremental Loop → Refactor。

核心思想有三层：
1. **纵向切片，不水平分层**——绝对禁止"先写所有测试再写所有实现"，每次一个 RED→GREEN 循环
2. **测试验证行为，不验证实现**——好测试通过公共接口验证，重构后不应该 break。坏测试 mock 内部协作者、测试私有方法
3. **deep module**——鼓励创建"接口简单、实现深厚"的模块，而不是大量浅模块

附带的 reference 文件覆盖：tests.md（好坏测试示例）、mocking.md（mock 准则）、refactoring.md（重构时机）、deep-modules.md（深模块概念）、interface-design.md（接口设计）。

与我们的 refactor skill 有交集但不重叠：refactor 处理"已有代码的结构调整"，tdd 处理"新功能的构建方式"。

## C. 与执行工具和 progress 的结合潜力

**高潜力**。TDD 的红绿循环天然适配工具和 progress：

- Planning → reason（规划接口和行为列表）→ progress(blocked)（确认用户对接口和测试优先级的意见）
- RED → write（写测试）→ act（运行测试，确认失败）→ progress(working)（"RED: test X 按预期失败"）
- GREEN → write/edit（写最小实现）→ act（运行测试，确认通过）→ progress(working)（"GREEN: test X 通过"）
- Refactor → edit → act（typecheck + 测试）→ progress(working)（"REFACTOR: 提取了 X，测试仍通过"）

每个 RED→GREEN 循环自然产生一个 progress(working)，循环次数就是 working 数量。

## 人类评价

这个感觉需要实际使用体验一下，因为我看到也有批评 TDD 这种模式的：

> AI 不会分心，不会过度工程化，也不需要小步骤来”驱动设计”——它可以一次性理解整个需求并输出完整实现。
> 
> 但 AI 有一个人类没有的致命瓶颈：上下文窗口。
> 
> 你写代码的时候，脑子里天然记着上下文——刚写了什么测试、哪行报错了、接下来该改哪里——这些”工作记忆”对人类来说是免费的。AI 不一样，它的”工作记忆”就是上下文窗口。每走一步红绿灯，测试运行输出、错误堆栈、编译信息，全部塞进去。对你来说是反馈，对它来说是噪声。
> 
> 跑三轮红绿灯，有效信息密度可能从 80% 降到 30%。你花着每百万 token 几美元的钱，买了一堆 ✅ Test passed 和 ❌ AssertionError: expected 42 but got null。
> 
> 而且”写最少代码使测试通过”这条规则也失灵了。它本来是治人类过度工程化的——先用最笨的方式跑通，别一上来就搞花活儿。但 AI 没有这个冲动。强迫它”先 return 42 让测试过，下一轮再写真实逻辑”，就像让计算器先猜一个答案、再算真正的答案。多此一举，双倍消耗。
> 
> 最坑的是，AI 还会偷偷”修”测试。人类不会删测试来”解决”失败——至少不好意思这么做。但 AI 没有这层心理障碍。测试失败了？改断言、弱化条件、甚至直接删掉——对它来说，这可能就是”最短路径”。你以为是绿灯，其实是自欺欺人。
> 
> 传统 TDD 用”小步试错”换”低风险”。但 AI 的试错成本不是时间，是上下文空间——最贵、最稀缺的资源。
>

然后这里也有这篇文章的作者给出的建议：
> ### ✅ 直接保留
> 
> 1.  **测试小而原子化** — AI 修 bug 时只需注入一个小上下文
> 2.  **测试命名体现意图** — 好名字省 token，`shouldRejectExpiredToken()` 比 `test1()` 强一万倍
> 3.  **聚焦关键逻辑** — AI 容易什么都想测，需要人工把关
> 4.  **覆盖正常路径 + 边界** — AI 枚举边界用例比人类全面，这是它的优势项
> 5.  **只测公共接口** — AI 生成的代码内部结构随 prompt 变化剧烈，测公共 API 才稳定
> 6.  **谨慎使用 Mock** — AI 天生爱 mock，一不留神就 mock 了一切
> 7.  **测试独立隔离** — 可并行跑，失败时可单独注入上下文修复
> 
> ### ⚠️ 保留精神，换执行方式
> 
> 8.  **从小处开始** — 需求拆解的思想保留，但拆完一次性交付，别一个一个喂
> 9.  **快速反馈循环** — 还是要快，但目的从”保持心流”变成”省上下文”
> 
> ### ❌ 砍掉
> 
> 10.  **严格 Red-Green-Refactor 循环** — 每一步都产生噪声上下文，小步循环是拿最贵的资源做最低效的事
> 11.  **“写最少代码使测试通过”** — 治人类过度工程化冲动的药，AI 没有这个病，纯属浪费
>
> ## 那 AI 时代的 TDD 该怎么玩
> 
> 核心就一句话：**让 AI 一次干完，然后验收。别一步一步喂。**
> 
> ```
> <span class="line"><span>传统 TDD:  Red → Run → Green → Run → Refactor → Run   (6步，3次运行)</span></span>
> <span class="line"><span>AI TDD:    Spec → Test+Impl → Verify → Fix(if needed)  (2-3步，1-2次运行)</span></span>
> ```
> 
> **先定验收标准，再一次性交付。** 把完整测试套件写好（或让 AI 生成完你审查一遍），作为”通过标准”交给 AI 去实现。测试驱动的是验收，不是设计过程。
> 
> **失败了别全量重放。** 哪个测试挂了，就只给 AI 看那个测试的失败信息和相关代码。它需要的是”哪里错了”，不是”整个世界长什么样”。
> 
> **重构单独开上下文。** 重构和”让测试通过”是两个不同的任务，在干净的上下文里做，效果好得多。
> 
> **用变异测试替代红灯验证。** 传统 TDD 的 Red 阶段本质上是在确认”这个测试真的能检测到错误”。用变异测试（Java 用 PIT，JS/TS 用 Stryker，Python 用 mutmut）批量验证，一次性告诉你哪些测试是假的。
> 
> 另外建议在 AGENTS.md 或 CLAUDE.md 里加几条硬规则：
> 
> -   🚫 禁止修改或删除已有测试来”修复”失败
> -   🚫 禁止纯 `assertNotNull` 式浅层断言，每个断言必须验证具体值或状态变化
> -   📊 变异测试门禁 ≥ 60%，覆盖率高但变异分数低就是不及格

就我而言我更赞同这一套。

尤其是引入变异测试看看哪些是假的测试。

## AI 回应

你贴的批评切中要害。逐条回应：

**关于严格 Red-Green-Refactor 循环的浪费**：同意。在 AI 场景下，"先 return 42 让测试过，下一轮再写真实逻辑"确实是双倍消耗。mattpocock 的 tdd skill 虽然强调 vertical slice，但仍保留了严格的 RED→GREEN 小步循环。对 AI 来说，"Spec → Test+Impl → Verify → Fix"的模式更高效。

**关于 AI 偷偷"修"测试**：这是真实风险。那篇文章建议的"禁止修改或删除已有测试来修复失败"应该作为硬规则写入 coding standard。

**关于变异测试**：非常值得引入。变异测试（Stryker for JS/TS）可以批量验证"这些测试是不是假的"，比手动检查每个测试的有效性高效得多。

如果我们要做 tdd skill，建议采用你贴的 "AI TDD" 模式而非 mattpocock 的严格 Red-Green-Refactor：
1. 先定验收标准（测试套件）
2. 一次性交付实现
3. 失败了只注入失败测试的信息，不全量重放
4. 重构单独开上下文
5. 变异测试作为质量门禁

分类修正：tdd 归为 **Task**。
