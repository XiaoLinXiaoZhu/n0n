# handoff (mattpocock)

> 来源：mattpocock/skills/productivity | 激活：auto

## A. 类型组成

**Directive**（纯粹，命令型）。命令模型将当前对话压缩为交接文档。

## B. 作用与核心思想

将当前对话的全部上下文压缩为一份交接文档，让另一个 agent 可以接续工作。

关键规则：
1. **不重复已有产物**——PRD、计划、ADR、issue、commit、diff 等已存在的内容只引用路径/URL，不复制
2. **建议后续 skill**——推荐下一个 session 应该使用什么 skill
3. **如果用户提供了参数**——将其视为"下一个 session 要做什么"的描述，据此裁剪文档

核心思想：**对话上下文是消耗品，文档是持久品**。长对话中积累的理解如果不提取出来，session 结束就丢失了。handoff 把隐性知识（对话中的讨论、决策、发现）转化为显性文档。

## C. 与执行工具和 progress 的结合潜力

**高潜力**。在我们的系统中，handoff 可以直接利用 progress 的历史——因为每个 progress(working) 都是一个阶段性发现/决策的记录，这些记录本身就是 handoff 文档的素材。

执行映射：
- 读取对话历史 → 内部处理（不需要工具）
- 生成文档 → write
- 交付 → progress(completed)（文档路径 + 建议的后续 skill）

**值得借鉴的内容**："不重复已有产物"原则——handoff 文档只包含对话中新产生的、其他地方没有记录的内容。这避免了交接文档变成冗余的全量复制。

## 人类评价

其实我觉得最好的交接物就是项目本身，良好的注释和简单的零星几个统筹的文档往往能够包含一切。

但是实际上模型总是会忘记记录这些。这里实际上也和我们的代码作为ssot相符合：
- 代码本身
- 代码周围的注释
- 模块入口的注释
- 文档

优先级从上到下，文档不应该反向被代码或者代码注释引用。

## AI 回应

完全同意"最好的交接物就是项目本身"。你列的优先级链非常清晰：

1. 代码本身
2. 代码周围的注释
3. 模块入口的注释
4. 文档

**文档不应该反向被代码或注释引用**——这是单向依赖原则。代码是 SSOT，文档是代码的"导航地图"，不是反过来。

这意味着 handoff 的最佳实践不是"写一份独立的交接文档"，而是确保代码库本身就是可自解释的——好的命名、必要的注释、模块入口的用途说明。handoff 文档只在项目本身无法自解释时才需要（比如当前正在进行的工作的上下文、尚未落地的决策等）。

分类确认：handoff 归为 **Task**。
