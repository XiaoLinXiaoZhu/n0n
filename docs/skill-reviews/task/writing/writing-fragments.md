# writing-fragments (mattpocock, in-progress)

> 来源：mattpocock/skills/in-progress | 激活：auto

## A. 类型组成

**Directive**（主要，交互调制器）+ **Methodology**（次要）。挖掘式对话 + 持续追加写入。

## B. 作用与核心思想

通过穷举式提问从用户脑中"挖矿"——产出 fragments（异质的写作原料），追加到一个文件中。

fragment 的定义故意宽泛：锐利的句子、带论证的观点、小故事、半成型的想法、引用、对话、抱怨、段子。"小说家日记"是原型——多年不结构化的记录，之后被当作原料。

关键设计：
1. **不施加结构**——禁止阶段、大纲、分类。结构是后续 skill（writing-shape, writing-beats）的事
2. **静默追加**——不问"可以加吗？"，加了就行，提一句"adding that"
3. **尊重用户编辑**——每次写入前重新读取文件，保留用户的修改/删除/重排
4. **fragments 之间用 `---` 分隔**——无标题、无标签、无排序

核心思想：**先发散再收敛**。大多数写作工具从结构开始（大纲→填充），writing-fragments 从碎片开始（发散→后续结构化）。这与创意写作中"先自由书写后编辑"的实践一致。

## C. 与执行工具和 progress 的结合潜力

**中等潜力**。核心是对话 + 文件写入：
- 挖掘提问 → 对话式（不需要工具）
- 追加 fragment → write/edit
- 用户可能编辑文件 → observe（每次写入前重读）

与 progress 的结合不太自然——fragments 是连续流动的对话，不是有明确步骤的流程。强行加 progress(working) 反而会打断节奏。

**值得借鉴的内容**："静默追加"的交互模式——不打断对话流来请求确认，直接做（加了提一句）。在某些低风险场景中这比 progress(blocked) 更高效。

确认可以迁移。writing-fragments 归为 **Task**（任务：从对话中挖掘碎片原料并追加到文件）。

迁移时需要注意的适配点：
- "静默追加"模式在我们的系统中需要用 write 工具，但不需要 progress(blocked) 确认——这是少数可以跳过确认的低风险写入场景
