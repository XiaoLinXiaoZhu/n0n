# 合并条件：remove-edit-tool → mvp

## 背景

`remove-edit-tool` 分支已通过代码审查、类型检查、lint 和测试。剩余的唯一风险是**实际使用中移除 edit 是否有效**——即 agent 在真实编码任务中能否仅凭 write + diff/patch 保持同等或更优的表现。

## 验证方法

### 试用期

在 `remove-edit-tool` 分支上进行日常编码工作，持续 3-5 个独立任务（或 1-2 天常规使用），覆盖以下场景分类：

| 场景 | 示例 | 关注点 |
|------|------|--------|
| 新文件创建 | 新增功能模块 | 基线：不应有任何退化 |
| 小文件修改 | 修 bug、改逻辑 | write 重写是否自然、无遗漏 |
| 多文件协调变更 | 重命名/移动/拆分 | 是否需要 diff，diff 是否顺利 |
| 大文件触碰 | 配置、遗留代码 | 是否自然触发重构或用 diff |
| 外部约束文件 | package.json, tsconfig | 是否正确使用领域工具 |

### 量化指标

#### 必须通过（hard gate）

1. **任务完成率 ≥ 95%**  
   定义：agent 能在合理轮次内完成任务（不因缺少 edit 而卡死或反复失败）。  
   测量：试用期内完成/总数。

2. **无内容丢失**  
   定义：write 重写文件时不会意外丢失代码、注释、或重要逻辑。  
   测量：每次 write 后通过 `git diff` 人工确认变更符合预期。任何一次无法解释的内容丢失即为失败。

3. **diff/patch 可用性**  
   定义：当 agent 选择使用 diff/patch 路径时，`git apply` 成功率 ≥ 90%。  
   测量：记录 diff 使用次数和成功/失败次数。

#### 观察指标（soft signal）

4. **token 成本变化**  
   预期：小文件 write 的额外 token 可忽略。如果观察到 token 用量系统性增加 >30%，需要分析原因。  
   测量：对比几个相似任务在有/无 edit 时的 token 消耗。

5. **代码结构趋势**  
   预期：agent 应自然倾向拆分大文件，输出更模块化的代码。  
   观察：是否出现了"因为 write 不方便所以主动拆分"的行为。

6. **agent 行为异常**  
   关注：agent 是否尝试调用不存在的 edit 工具、是否在大文件面前犹豫/反复重试、是否过度使用 diff/patch 而非 write。

### 退出条件

- **合并**：试用期内 hard gate 全部通过，且未观察到系统性退化。
- **回滚**：出现以下任一情况：
  - 任务完成率 < 90%（严重功能缺失）
  - 发现 2 次以上无法解释的内容丢失
  - diff/patch 成功率 < 70%（降级路径不可靠）
- **暂缓**：soft signal 显示明显退化但 hard gate 通过——需要进一步调查后决定。

## 记录模板

每次使用后简要记录：

```
日期：
任务描述：
场景分类：[新建 / 小改 / 多文件 / 大文件 / 外部约束]
完成情况：[成功 / 失败 / 部分]
使用了 diff/patch：[是/否]，成功：[是/否]
观察到的问题：
```

积累 5+ 条记录后，对照上述指标做最终判断。
