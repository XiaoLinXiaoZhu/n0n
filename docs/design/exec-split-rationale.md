# exec 拆分为 observe / reason / act：价值论证

## 概述

将单一的 `exec` 工具拆分为 `observe`、`reason`、`act` 三个工具，本质上不是功能拆分——三者的底层参数和执行路径完全相同。它的价值在于：**工具名作为围栏标记，重新定义了模型对 script 内容的理解和态度，并在多轮对话中累积形成可感知的认知语境。**

本文档结合 [[从模型注意力理解模型行为]] 中的围栏效应分析，系统性论证这一设计的价值。

---

## 背景：单一 exec 的问题

单一 exec 工具承担四种认知角色（观察、推理、执行、验证），但在上下文中只有一个工具名。这导致两个问题：

1. **模型对 script 内容缺乏明确的"态度"。** 同样是写一条 `rg` 命令，模型不清楚自己是在"收集信息"还是在"执行变更的一部分"。exec 这个名字不包含认知阶段的信号——模型每次都要从 script 内容本身推断意图。

2. **多轮历史中缺乏认知轨迹。** 上下文中出现 `exec × N`，模型回顾时无法从工具名推断"做了什么"。它必须逐个读取 script 内容才能理解历史——这在长上下文中效率很低，且容易丢失结构信息。

---

## 核心论证：围栏效应

### 单轮围栏的启示

围栏效应的核心观察来自一个简单的实验：在用户消息中，用 ``` 包裹引用内容（ref），即使 ref 非常长且包含指令性文本，模型也能正确区分它和后面的真实请求（query）。

关键事实：

- ref 可能有几千 token，query 可能只有几十 token。按注意力的常规行为，query 会被 ref 的注意力总量淹没。
- 但仅仅在 ref 的头尾加上 ```（两个 token），模型就能正确区分。甚至不需要每行加 `>` 标记。
- ``` 没有改变 ref 的任何一个 token。它改变的是模型对 ref 内容的**理解和态度**——同样的文本，从"用户在对我说的话"变成了"被引用的外部内容"。模型不再试图遵从 ref 中的指令，而是把它当作分析/引用的对象。

这不是简单的"标记"或"分类"。围栏重新定义了内容的语用角色——同样的 token 在不同的围栏语境下，被模型当作完全不同的东西来处理。

### 工具名作为围栏

`observe`、`reason`、`act` 做了和 ``` 完全相同的事，但作用在工具调用层面：

- `observe` 重新定义了 script 的语用角色：从"要执行的操作"变成了"要观察的对象"。模型在生成 observe 调用时，先做出了"我在观察"的声明，这个声明在因果注意力中影响后续 script 内容的生成。
- `act` 重新定义了 script 的语用角色：模型明确知道"我在改变环境状态"，这让它更谨慎地考虑副作用和可逆性。
- `reason` 重新定义了 script 的语用角色：从"执行操作"变成了"外化思考过程"。script 内容不再是"做什么"，而是"怎么想"。

这些语用角色的变化不需要语义指令来"告诉"模型。工具名本身——作为训练数据中已建立注意力模式的固定 token 序列——就足以触发不同的处理路径（推测层面：路由到不同的 MoE 专家子网络）。

### 多轮围栏：标记序列累积语境

单轮围栏（如 ```）在一段文本中创造内容的语境。多轮围栏在对话历史中做类似的事：**工具名的序列累积形成对话的认知语境。**

`observe → observe → reason → act` 这个序列在上下文中形成了一条可读的认知轨迹。模型在决定下一步时，注意力回顾这个序列，不需要读取每个 script 的内容就能感知："我已经充分观察了，思考过了，刚执行了一个动作"。这个累积语境影响它接下来的行为选择。

对比 `exec × 4`：模型看到四个相同的工具名，序列不携带任何认知阶段信息。它必须逐个读取 script 内容才能理解自己做了什么——信号被稀释在大量工具调用内容中。

这就是 plan→act 方案"粗糙"的原因：只有两个状态，序列只能是 `plan→act`，不足以累积丰富的语境。而且它是单向的——进了 act 就回不到 plan，围栏的灵活性被限死了。observe/reason/act 作为可自由切换的标签集，它的序列可以表达丰富的认知轨迹（`observe→observe→reason→observe→reason→act→observe...`），而且每个标记都可重复使用、不受前一次约束。

## 实证观察：rg 转义的自纠正

在 unified exec 模式下，模型在 Windows 环境中使用 `rg` 时经常纠结转义问题（`rg "A\|B"` vs `rg "A|B"`），且犯错后反复重蹈覆辙。

切换到 split 模式后，即使第一次犯错，后续也能自纠正。

从围栏效应的角度解释：

- `observe` 模式下，模型回顾历史时，注意力锚定在 `observe` 这个工具名上——所有观察类操作被聚在一起。rg 命令的正确写法更容易从同类历史调用中被注意到。
- 在 `exec × N` 的历史中，rg 调用混在 git、type、bun 等各种操作之间，注意力信号被稀释，正确的 rg 模式更难被检索到。

这和"好的提示词有更均匀的注意力分布"是同一个原理：工具名围栏让注意力在同类操作上分布更集中，减少了无关信号的干扰。

## 与 progress 工具的平行关系

`observe/reason/act` 标注的是**工具调用的语用角色**——模型在做什么。

`progress(working/completed/blocked)` 标注的是**模型输出的语用角色**——输出的功能是什么。

两者是同一设计思想在不同层面的体现：

| 层面 | 围栏方案 | 标注的角色 |
|------|----------|-----------|
| 工具调用 | observe / reason / act | 认知阶段（观察/思考/行动） |
| 模型输出 | working / completed / blocked | 输出功能（推理日志/交付物/决策请求） |

progress(working) 之所以能作为"节点回滚"的恢复点（见 design-progress-tool.md），前提就是它有围栏标注——有身份、有边界，所以可以被独立定位和操作。observe/reason/act 在工具调用层面创造了同样的可追溯性。

---

## 结论

exec 拆分的价值不在于功能差异（三者参数和执行路径完全相同），而在于：

1. **重新定义语用角色**：工具名改变了模型对 script 内容的理解和态度，让模型在生成和解读时激活更匹配的处理路径。

2. **累积认知语境**：工具名序列在多轮历史中形成可回顾的认知轨迹，让模型在任意时刻感知"我做了什么、在哪里、该往哪去"。

3. **提升注意力效率**：同类操作聚在同一工具名下，减少了历史回顾时的注意力稀释，降低了重复犯错率。

这不是"把一个工具拆成三个"这样的功能设计决策。它是上下文工程中"用结构重新定义语用角色"这一原则的实践——和 ``` 包裹 ref、`<check-skills>` 强制元检查、progress 三状态标注，属于同一类设计。
