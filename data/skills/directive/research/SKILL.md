# Research — 交互协议

在执行研究型任务时，模型应遵循以下交互协议。约束的是**沟通节奏和推理呈现方式**，而非研究领域的方法论。

## 适用场景

需要系统性探索和分析的任务：

- 代码库调研（架构逆向、依赖分析、模块职责梳理）
- 问题归因（从现象反推根因，对照多个假设）
- 方案选型（对比多个候选方案，基于证据推导结论）
- 数据驱动的调研（日志分析、性能剖析、输出物对比）
- 文献/技术文档的批判性阅读与分析

不适用于：明确指令式任务（重构、实现功能、修复已知 bug），这类任务应参考 bugfix / refactor skill。

## 核心约束

### 约束一：基于证据/推理链条，而非直觉

每一步声明必须有明确依据。

| ❌ 直觉模式 | ✅ 证据模式 |
|-------------|-------------|
| "这个函数看起来有问题" | "这个函数在 `n=0` 时返回 `undefined`，而调用方期望返回值始终为 `number[]`（见 `consumer.ts:12`）" |
| "我建议用 Redis" | "延迟要求 <10ms，当前 SQL 查询 P99 为 50ms（见压测报告 §2.3），候选方案对比如下..." |
| "可能不是这个原因" | "排除这个假设的理由：如果 X 是根因，那么 Y 应该出现；但日志显示 ¬Y（`checkpoint.log:47`），因此排除 X" |

在得出结论前，用 `reason` 运行思维实验——把假设、预期、实际检查写成可执行的具体逻辑。有时候直接用 `act` 尝试再用 `observe` 看结果比纯推演更高效。

### 约束二：极其高频地使用 `progress(working)` 提供推理阶段声明

不要等到一个完整阶段结束才汇报。每个独立的推理步骤（提出假设、检查证据、排除/确认、转向）都应该通过 `progress(working)` 对外声明。

阶段声明的**必须元素**：
1. 当前假设/探索方向
2. 支持该假设的**具体证据引用**（文件名、行号、时间戳、数值等）
3. 下一步要做什么来验证/推翻

### 约束三：总是使用 `progress(blocked)` 请求人类审阅

当研究产出了**需要人类判断才能继续推进**的文档时，必须用 `progress(blocked)` 请求审阅。

`progress(blocked)` 的**必须元素**：
1. 核心结论（1-3 句话摘要）
2. 自信程度（以及不确定的地方）
3. 需要人类确认的具体决策点（2-4 个选项）

### 约束四：投入足够工作量后才推进

`progress(blocked)` 之间应有若干个 `progress(working)`。在请求人类介入之前，先做完所有自己能做的探索。

## 工作流模板

```
阶段 1: 问题定义
  working → 理解研究目标，列出已知和未知
  working → 形成初始假设列表

阶段 2: 系统性探索
  (working + observe/reason/act) × N 个假设
  对每个假设：检查 → 记录证据 → 确认/排除

阶段 3: 综合与产出
  working → 整合各假设的检查结果
  working → 形成结论/报告草稿
  blocked → 请求人类审阅

阶段 4: 收尾（收到反馈后继续）
```

## 与 bugfix 的协作

research 负责探索和归因阶段，bugfix 负责修复阶段。当研究确认了根因后，blocked 审阅时建议是否切换为 bugfix。
