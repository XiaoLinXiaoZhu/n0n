# 批注处理

处理 wiki 文档中使用 `%%批注内容%%` 格式标记的内联批注。这种批注直接嵌入正文中，与正文一起流转，适合轻量级的审校标记。

## 批注约定

- 格式：`%%批注内容%%`，放在被批注内容之后
- 批注内容可以包含作者标记：`%%@张三：这里需要补充数据%%`
- 批注不渲染为正文，但保留在源文件中供处理
- 处理后的批注应从源文件中移除（或转为正式内容）

## 全局约定

- 链接语法：`[[文件名]]`，文件名不含扩展名
- 除非用户明确确认，**不执行任何实际编辑**
- 所有发现通过 `show` 汇报，附建议和依据

## 执行步骤

### 1. 读取文档

用 `observe` 读取用户指定的文档全文。

### 2. 提取所有批注

用 `reason` 提取所有 `%%...%%` 段落，记录：

- 批注原文
- 所在行号
- 被批注的正文内容（批注前紧邻的段落或句子）

```bash
# 辅助：用 rg 快速定位所有批注行
rg "%%" wiki/xxx.md -n
```

### 3. 分类

将每条批注归入以下类别：

| 类别 | 识别特征 | 建议处理 |
|------|---------|---------|
| **待补充** | "待补充""需要""TODO""缺少" | 补充内容后删除批注 |
| **疑问** | 以"？""是否""还是""确认"结尾，或标记为 question | 回答疑问后删除批注 |
| **待核实** | 标注数据、事实需要验证 | 核实后更正或确认，删除批注 |
| **修改建议** | 提出具体的措辞或结构调整建议 | 采纳或拒绝，删除批注并附决策 |
| **讨论** | 多轮 `%%@某人：...%%` 的对话 | 将结论整合进正文后删除 |
| **已过期** | 内容已过时，批注提出的问题不再存在 | 直接删除 |

### 4. 按类别生成处理方案

用 `reason` 为每条批注生成具体的处理建议：

- 对于"待补充"：默认标记为需要用户提供内容，不猜测填充
- 对于"疑问"：如果能从上下文推断答案，给出建议答案供用户确认
- 对于"待核实"：标记需要用户核实，如果能从其他文档验证则给出验证结果
- 对于"修改建议"：评估建议是否合理，给出采纳/拒绝建议
- 对于"讨论"：总结讨论要点，提出整合方案
- 对于"已过期"：标记为可直接删除

### 5. 汇报

用 `show(ask user question)` 提交完整报告：

```
【文档】xxx.md
【批注总数】N 条

【待补充】（M 条）
1. 第 42 行 — "%%需要补充性能数据%%"
   被批注内容："该方案在大多数场景下表现良好"
   建议：补充具体场景和性能数字后删除此批注
2. ...

【疑问】（M 条）
1. 第 58 行 — "%%这里说的"大部分"是指 80% 还是 95%？%%"
   建议：明确具体比例后删除
2. ...

【待核实】（M 条）
...

【修改建议】（M 条）
1. 第 73 行 — "%%建议把这段拆成两个小节%%"
   评估：合理，该段落确实混合了两个不同主题
   建议：采纳，拆分为"## 安装"和"## 配置"
2. ...

【讨论】（M 条）
...

【已过期】（M 条）
...

【是否需要我执行以上处理？】
```

### 6. 确认后执行

用户确认后，用 `write` 逐处处理：

- 补充内容：在批注位置插入正文，然后删除 `%%...%%`
- 回答疑问：如果疑问导致正文修改，修改正文后删除批注
- 核实数据：更正正文数据后删除批注
- 采纳建议：执行修改后删除批注
- 拒绝建议：在批注后追加 `%%已拒绝：理由%%` 或直接删除
- 过期删除：直接删除

## 自检

- 每条批注都有明确的处理方案，不留"待定"（除非用户要求）
- 被批注的上下文要足够完整，让用户在不打开文件的情况下也能判断
- 讨论类批注的结论提取要准确，不能曲解讨论者的意图
- 不把正文内容误判为批注（比如 `%%` 在代码块中可能是运算符）

## 边界

- 不处理 `.annotations.json` 和 `.ai-annotations.json` 格式的外部批注文件
- 不创建新的批注，只处理已有批注
- 忽略代码块（以 ``` 包裹的区域）内的 `%%`，它们通常是模板语法或运算符
