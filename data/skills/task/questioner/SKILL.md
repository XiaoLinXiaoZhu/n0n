# 起草求教邮件（Questioner）

## 定位

帮用户写一封向外领域专家请教的邮件，让对方愿意回、能快速指出问题。

## 核心原则

**「是不是」优先于「怎么做」**：先把前提暴露给对方纠正，再问方向。

## 流程

### 1. 确认领域 → 定调

用 `progress(blocked)` 确认：

- 对方是什么领域的专家？
- 用户和对方什么关系？（陌生人 / 同事 / 上级 / 社区求助）
- 领域决定邮件的技术背景和术语深度，关系决定语气。

AI 不需要知道具体是谁——「对方是什么领域的专家」足以定调。

### 2. 提取核心怀疑

用 `reason` 分析：

- 如果有对话历史，从中提取：用户在做什么、试过什么、卡在哪里
- 核心怀疑：用户最担心自己哪里搞错了？模糊的不安是什么？
- 这一步是 questioner 的核心价值——帮用户把「总觉得哪里不对」转化为具体的自我怀疑

### 3. 生成初稿

按以下结构生成：

```
主题：[一句话概括核心怀疑]

[称呼]，

[为什么找你]：你在 [领域] 的工作让我觉得你能帮我审视这个方向。

[背景]：[做了什么，走到哪一步——给够上下文，但不流水账]

[核心怀疑]：
1. [我做了/认为 X，但可能是错的，因为我不确定 Y]
2. [另一个不确定的点]

[收尾]：不预设答案，降低回复门槛——让对方一两句话就能指出关键问题。

谢谢！
[署名]
```

**约束**：
- 暴露不确定性——让对方知道你哪里不确定
- 不预设答案——不暗示「我觉得 A 更好」
- 降低回复门槛——一句话就能指出问题，而非需要长篇论证才能反驳

### 4. 自审轮 1 → 修订

用 `reason` 逐条检查硬性校验清单。任何一条不通过就修订，直到全部通过。

**硬性校验清单：**

| # | 检查项 | 判定标准 |
|---|--------|---------|
| 1 | 「是不是」优先 | 有至少一个问题在验证前提（「我这样理解对吗」「这里有问题吗」），而非全在问方向 |
| 2 | 暴露不确定性 | 核心段落表达了用户哪里不确定、最担心哪里出错 |
| 3 | 不自大 | 没有「我做了很多研究」「经过深入分析」这类抬高预期的措辞；没有预设自己方案是对的 |
| 4 | 降低回复门槛 | 对方一两句话就能指出关键问题，不需要写长篇论证才能反驳 |
| 5 | 背景不多不少 | 给了对方足够上下文判断，但没有流水账倾泻所有尝试 |
| 6 | 问题不空泛 | 问题具体到「X 方面是否 Y」，而非「你对 X 有什么看法」 |
| 7 | 语气匹配关系 | 陌生人要自我介绍+说明为什么找ta；同事可直入；语气不卑不亢 |

**模拟收件人视角**：站在收件人角度读一遍，问自己：
- 我能快速理解这人在问什么吗？
- 我有没有被冒犯？
- 我回复的成本有多高？能一句话说清吗？

### 5. 用户确认

用 `progress(blocked)` 提交初稿，附简要说明（为什么这样写、用了什么语气）。等待用户反馈。

### 6. 根据反馈修订

用户反馈后，逐条处理。如果反馈涉及语气或前提的重大调整，回到步骤 3 重新生成。

### 7. 自审轮 2 → 修订

修改后再次逐条检查校验清单。全部通过后进入交付。

### 8. 交付

将最终邮件写入 `.temp/<主题>.md`，主题即文件名。用 `progress(completed)` 报告文件路径和简要摘要。

## 反面示例

**× 自大预设**：「我在设计 Agent workflow，用相对判断替代绝对判断。请评审这个方向。」——预设了方向是对的，只求评审。

**√ 暴露怀疑**：「我在设计 Agent workflow，目前的方向是用相对判断替代绝对判断。但我担心这可能是过度设计——对于简单任务，每步都生成候选+比较显然不合理。请问我是不是搞错了什么？这个方向是否有已知的陷阱？」

## 自检

- 校验清单 7 条全部通过了吗？
- 模拟收件人视角读过了吗？
- 最终文件写入了 `.temp/<主题>.md` 吗？
- 文件名就是邮件主题吗？
