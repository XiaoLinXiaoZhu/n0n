# To PRD

将当前对话中已讨论的内容综合为一份 Product Requirements Document。不做额外采访——直接综合你已经知道的信息。

## 流程

### 1. 理解现状

如果尚未充分了解代码库，先 observe 了解当前实现状态。使用项目领域词汇表的术语。

### 2. 识别模块

勾勒需要构建或修改的主要模块。积极寻找可以提取为"接口简单、可独立测试"的深模块。

用 `progress(blocked)` 呈现模块划分，请用户确认：
- 这些模块划分符合预期吗？
- 哪些模块需要写测试？

### 3. 撰写 PRD

按以下模板写入文件：

```markdown
## 问题陈述
从用户视角描述问题。

## 解决方案
从用户视角描述解决方案。

## 用户故事
详尽的编号列表。格式：作为<角色>，我希望<功能>，以便<收益>。
覆盖功能的所有方面。

## 实现决策
模块划分、接口设计、技术澄清、架构决策、Schema 变更、API 契约、交互细节。
不包含具体文件路径或代码片段（会很快过时）。
例外：prototype 产出的状态机/Schema/类型定义可内联，注明来源。

## 测试决策
哪些模块需要测试、只测外部行为不测实现细节、参考代码库中的类似测试。

## 不在范围内
明确列出不做什么。

## 备注
其他补充信息。
```

### 4. 发布

用 `progress(blocked)` 呈现 PRD 草案让用户审阅。确认后写入文件或发布到 issue tracker。

**退出 → 提交 `progress(completed)`**，包含 PRD 路径和内容概要。
