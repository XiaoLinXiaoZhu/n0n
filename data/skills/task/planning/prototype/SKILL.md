# Prototype

原型是**回答问题的一次性代码**。问题决定形态。

## 判断分支

从用户提示、周围代码或直接询问中识别问题类型：

- **"这个逻辑/状态模型对不对？"** → 逻辑原型（见下方"逻辑分支"）
- **"这个应该长什么样？"** → UI 原型（见下方"UI 分支"）

判断后用 `show(progress report)` 声明："问题是 X 类型，走 Y 分支"。

## 通用规则

1. **从第一天起标记为 throwaway**——命名中包含 prototype 或 throwaway
2. **一条命令可运行**——加到项目现有的 task runner 中
3. **不持久化**——状态存在内存中
4. **跳过打磨**——无测试、无错误处理（保持可运行即可）、无抽象
5. **暴露状态**——每次操作后显示完整的相关状态

## 逻辑分支

构建一个可交互的终端应用，用户按键驱动状态变化。

1. **写下问题**——在文件顶部注释中明确"这个原型要回答什么问题"
2. **将逻辑隔离在纯模块中**——reducer / 状态机 / 纯函数，不含 I/O。TUI 只是薄壳
3. **构建最小 TUI**——每个 tick 清屏重绘：当前状态（pretty-print）+ 键盘快捷键列表
4. **交付运行命令**——用 `show(request user assistance)` 请用户运行测试并报告发现

## UI 分支

在同一路由上生成多个截然不同的 UI 变体，通过 `?variant=` 参数切换。

1. **默认 3 个变体**——变体之间必须结构性不同（不同布局、不同信息层级），不只是换颜色
2. **优先嵌入现有页面**——利用真实的 header、sidebar、数据。只有确实没有合适的宿主页面时才建新路由
3. **浮动切换器**——底部固定的小条，左右箭头切换变体。仅开发环境可见
4. **交付 URL 和变体键**——用 `show(request user assistance)` 请用户浏览并选择

## 完成

原型回答了问题后，**答案是唯一值得保留的东西**。

- 用 `show(final report)` 记录：问题是什么、答案是什么、哪个变体胜出（UI）/ 学到了什么（逻辑）
- 提醒用户：删除原型代码或将验证过的决策吸收进真实代码
