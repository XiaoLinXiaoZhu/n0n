# 架构深化

发现架构摩擦点，提出**深化机会**——将浅模块变为深模块的重构。目标是可测试性和可维护性。

执行具体改动时，切换到 [refactor-spec](../spec/SKILL.md) 的步骤 3-6。

---

## 工具使用协议

架构探索遵循 **观察 → 推理 → 行动** 循环：

**observe（观察）**——有机遍历代码库，凭摩擦感定位问题：
- 读模块代码，感受接口与实现的复杂度比
- `rg` 追踪依赖链和调用模式
- 检查测试覆盖和测试质量

**reason（推理）**——将架构判断物化为可检验的结论：
- 对可疑模块应用删除测试：具象化"删掉后复杂度去哪了"
- 将依赖关系写成数据结构，分类（进程内/本地可替代/远程自有/真正外部）
- 推演接口设计方案，对比杠杆和局部性

**act（行动）**——在确定方案后执行：
- 切换到 refactor-spec 的执行流程
- 实验性地尝试重构，git 可撤回

---

## show 协议

**`show(production record)`** — 探索形成可复查的架构结论、改变候选范围或关闭关键不确定性时使用：
- 写明新结论、删除测试或其他证据，以及对后续设计的影响
- 不按 observe 次数汇报例行读取或尚未改变方案的中间观察

**`show(customer decision required)`** — 需要用户决策时使用：
- 候选会改变订单范围，需要客户选择本次要纳入的结果
- 接口方案会改变公共契约、额外授权或客户承担风险
- 与客户已确认的 ADR 或业务约束冲突，需要客户决定是否修订

内部架构、接口和测试方案由生产方依据证据选择。存在多个技术候选本身不构成客户决定。

## 词汇约定

严格使用以下术语（完整定义见 [LANGUAGE.md](LANGUAGE.md)）：

| 术语 | 含义 |
|------|------|
| **模块** | 任何有接口和实现的东西（函数、类、包、切片） |
| **接口** | 调用方必须知道的一切：类型、不变量、错误模式、顺序、配置 |
| **深度** | 接口处的杠杆。**深** = 小接口大行为。**浅** = 接口≈实现 |
| **接缝** | 接口所在的位置；可以改变行为而无需原地编辑的地方 |
| **适配器** | 在接缝处满足接口的具体实体 |
| **杠杆** | 调用方从深度中获得的东西 |
| **局部性** | 维护者从深度中获得的东西：变更/缺陷/知识集中在一处 |

核心原则：
- **删除测试**：删掉该模块后，复杂度消失 → 透传层；散落到 N 个调用方 → 在发挥作用
- **接口就是测试面**
- **一个适配器 = 假设性接缝。两个适配器 = 真实接缝**

## 流程

### 1. 探索

以 `observe` 为主，有机地遍历代码库。不遵循僵化的检查清单——凭摩擦感定位问题。

关注以下摩擦信号：
- 理解一个概念需要在多个小模块间跳转
- 模块是**浅的**——接口几乎和实现一样复杂
- 纯函数被提取只是为了可测试性，但真正的 bug 藏在调用方式中（没有**局部性**）
- 紧耦合模块在接缝处泄漏
- 代码库中未测试或难以通过当前接口测试的部分

对怀疑为浅模块的目标应用**删除测试**（用 `reason` 具象化推演）：删掉它会集中复杂度，还是只是移动复杂度？"集中"是你想要的信号。

**遍历原则**：调查范围必须足以覆盖候选模块、调用方和相关测试；工作日志由新信息触发，不由文件数量触发。

形成探索记录；结论值得客户复查时可按以下结构提交 `show(production record)`：

```
【阶段】架构探索
【已遍历范围】（哪些模块/目录）
【摩擦点】（编号列表，每条一句话描述症状）
【删除测试结果】（对关键可疑模块的判断）
```

---

### 2. 呈现候选

呈现编号的深化机会列表。每个候选项包含：

- **文件** — 涉及哪些文件/模块
- **问题** — 当前架构为什么造成摩擦（用术语表中的概念描述）
- **方案** — 用白话描述会改变什么
- **好处** — 用局部性和杠杆解释，以及测试会如何改善

**不要在此阶段提出具体接口。**

若客户原订单只要求识别机会，候选列表就是 `show(qualified delivery)` 的交付产物。
若订单已经授权生产方选择并实施，生产方应依据证据选择最强候选并继续；
该决定值得客户复查时用 `show(production record)` 说明结论、依据和影响。
只有候选代表不同订单范围且现有订单没有授权生产方决定范围时，才提交 `show(customer decision required)`：

```
【阶段】架构候选
【候选 1】文件 / 问题 / 方案 / 好处
【候选 2】...
【候选 N】...
```

请求客户选择本次订单要纳入的范围，并说明生产方推荐及后果差异。

---

### 3. 深入设计

用户选定候选后，进入深入设计对话。

**工具联动**：
- `observe`：追踪具体依赖链、调用模式、现有测试
- `reason`：推演设计权衡，将抽象讨论落地为具体类型和数据流
- `show(production record)`：设计决定会显著影响公共契约、长期维护或恢复成本时记录结论、证据和影响

设计过程中的关注点：
- 约束、依赖、深化模块的形状
- 接缝后面是什么
- 哪些测试存活，哪些需要重写
- 依赖属于哪个分类（参见 [DEEPENING.md](DEEPENING.md)）

**需要探索替代接口设计？** 参见 [INTERFACE-DESIGN.md](INTERFACE-DESIGN.md)。

**副作用操作**：
- 深化后的模块需要命名新概念 → 记录并提议添加到项目词汇表
- 对话中澄清了模糊术语 → 同步更新
- 用户以实质性理由拒绝候选 → 提议记录为 ADR，避免未来重复建议

---

### 4. 衔接执行

设计确定后，切换到 refactor-spec 的步骤 3-6 执行改动：

```
架构深化设计完成
        ↓
spec 步骤 3（建立安全网）
        ↓
spec 步骤 4（执行重构）
        ↓
spec 步骤 5（验证等价）
        ↓
spec 步骤 6（检查遗漏）
```

架构深化的探索和设计阶段已完成了 spec 步骤 1-2 的工作（理解现状 + 定义目标），因此直接从步骤 3 开始。
