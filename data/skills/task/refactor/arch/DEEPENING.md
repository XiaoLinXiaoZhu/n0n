# 深化

如何在已知依赖的情况下，安全地将一组浅模块深化。假设已熟悉 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**模块**、**接口**、**接缝**、**适配器**。

## 依赖分类

评估深化候选时，对其依赖进行分类。分类决定了深化后的模块如何跨接缝测试。

### 1. 进程内（In-process）

纯计算、内存状态、无 I/O。总是可深化的——合并模块，通过新接口直接测试。无需适配器。

### 2. 本地可替代（Local-substitutable）

有本地测试替身的依赖（如 PGLite 替代 Postgres、内存文件系统）。替身存在时可深化。深化后的模块用测试套件中运行的替身进行测试。接缝是内部的；不在模块外部接口暴露端口。

### 3. 远程但自有（Ports & Adapters）

跨网络边界的自有服务（微服务、内部 API）。在接缝处定义**端口**（接口）。深模块拥有逻辑；传输层作为**适配器**注入。测试使用内存适配器，生产使用 HTTP/gRPC/队列适配器。

建议格式：*"在接缝处定义端口，为生产实现 HTTP 适配器、为测试实现内存适配器，使逻辑集中在一个深模块中——即便它部署跨越了网络。"*

### 4. 真正的外部（Mock）

不受你控制的第三方服务（Stripe、Twilio 等）。深化后的模块将外部依赖作为注入端口接收；测试提供 mock 适配器。

## 接缝纪律

- **一个适配器 = 假设性接缝。两个适配器 = 真实接缝。** 除非至少两个适配器有理由存在（通常是生产 + 测试），否则不要引入端口。单适配器接缝只是间接层。
- **内部接缝 vs 外部接缝。** 深模块可以有内部接缝（对实现私有，供自身测试使用）和外部接缝（其接口处）。不要仅因测试使用了内部接缝就把它暴露到接口上。

## 测试策略：替换，而非叠加

- 浅模块上的旧单元测试，在深化模块接口处的测试存在后变为废品——删掉它们。
- 在深化模块的接口处编写新测试。**接口就是测试面。**
- 测试断言通过接口观察到的结果，而非内部状态。
- 测试应在内部重构后存活——它们描述行为而非实现。如果实现变了测试就得改，说明测试穿越了接口。
