# 接口设计

当需要为选定的深化候选探索替代接口时使用此方法。基于"Design It Twice"（Ousterhout）——第一个想法不太可能是最好的。

使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**模块**、**接口**、**接缝**、**适配器**、**杠杆**。

## 流程

### 1. 界定问题空间

在展开设计之前，先写出候选项的问题空间说明：

- 任何新接口需要满足的约束
- 它依赖什么，每个依赖属于哪个分类（参见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的示意代码草图来具象化约束——不是提案，只是让约束变得具体

**工具联动**：用 `observe` 收集依赖信息和调用方模式，用 `reason` 将约束结构化为可检验的数据。

→ 提交 `show(production record)`，格式：

```
【阶段】接口设计 - 问题空间
【约束列表】（新接口必须满足什么）
【依赖分类】（每个依赖及其类别）
【示意草图】（代码级的约束具象化）
```

### 2. 生成实质不同的设计方案

存在多个可行方向时，产出两个或更多**根本不同**的接口设计；候选数量由真实的约束取舍决定。
没有第二个实质可行方向时，记录检查过的约束和排除依据，不为满足数量制造方案。可考虑的优化轴包括：

- **最小接口** —— 用尽量小的接口提供主要行为。
- **最大灵活性** —— 支持多种真实用例和扩展。
- **优化主要调用方** —— 让最常见的使用场景变得极简。
- **围绕 Ports & Adapters** —— 在确有跨接缝依赖时使用。

**工具联动**：用 `reason` 独立推演每个方案，将设计写成具体的类型签名和使用示例——不要停留在"大概这样"。

每个方案需包含：

1. 接口（类型、方法、参数——加上不变量、顺序、错误模式）
2. 使用示例：调用方如何使用
3. 接缝之后隐藏了什么
4. 依赖策略和适配器（参见 [DEEPENING.md](DEEPENING.md)）
5. 取舍——杠杆高在哪里，薄弱在哪里

### 3. 对比与推荐

按以下维度对比各方案：

- **深度**（接口处的杠杆）
- **局部性**（变更集中在哪里）
- **接缝位置**（接缝放在哪里最自然）

给出自己的推荐：哪个设计最强、为什么。如果不同设计的元素可以组合，提出混合方案。要有观点——用户需要的是强判断，不是菜单。

生产方依据上述证据选择最强设计。若该选择只影响内部实现，使用 `show(production record)` 记录决定并继续；
只有方案差异会改变公共契约、订单范围、额外授权或客户承担风险时，才提交
`show(customer decision required)`。两种消息均可采用以下结构：

```
【阶段】接口设计 - 方案对比
【方案 A】（名称 + 一句话 + 杠杆/局部性/接缝评估）
【方案 B】...
【方案 C】...
【推荐】（你的判断 + 依据）
```

客户决定请求必须明确需要客户决定的契约或风险差异；不得仅因存在多个技术方案就把选择交给客户。
