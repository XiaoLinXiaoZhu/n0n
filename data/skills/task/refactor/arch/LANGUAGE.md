# 架构语言

所有架构建议共享的词汇表。严格使用以下术语——不要替换为"组件"、"服务"、"API"或"边界"。一致的语言本身就是目标。

## 术语

**模块（Module）**
任何具有接口和实现的东西。刻意与规模无关——适用于函数、类、包或跨层切片。
_避免使用_：单元、组件、服务。

**接口（Interface）**
调用方正确使用模块所需知道的一切。包括类型签名，也包括不变量、顺序约束、错误模式、所需配置和性能特征。
_避免使用_：API、签名（太窄——它们只指类型层面的表面）。

**实现（Implementation）**
模块内部的代码。与**适配器**不同：某个东西可以是小适配器但有大实现（如 Postgres 仓储层），也可以是大适配器但有小实现（如内存假对象）。当话题是接缝时用"适配器"；其他情况用"实现"。

**深度（Depth）**
接口处的杠杆——调用方（或测试）每学习一个单位的接口能触达的行为量。**深模块**：大量行为藏在小接口之后。**浅模块**：接口几乎和实现一样复杂。

**接缝（Seam）** _（来自 Michael Feathers）_
一个可以改变行为而无需在该处编辑的位置。模块接口所在的*位置*。选择把接缝放在哪里是独立于其背后内容的设计决策。
_避免使用_：边界（与 DDD 的限界上下文重载）。

**适配器（Adapter）**
在接缝处满足接口的具体实体。描述*角色*（它填充什么槽位），而非实质（它内部是什么）。

**杠杆（Leverage）**
调用方从深度中获得的东西。每单位接口学习成本换来更多能力。一份实现在 N 个调用点和 M 个测试中回收价值。

**局部性（Locality）**
维护者从深度中获得的东西。变更、缺陷、知识和验证集中在一处，而非散布到各调用方。修复一次，处处生效。

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小的、可模拟的、可替换的部件组成——它们只是不属于接口。模块可以有**内部接缝**（对实现私有，供自身测试使用）和**外部接缝**（其接口处）。
- **删除测试（Deletion test）。** 想象删掉该模块。如果复杂度消失，说明模块没有隐藏任何东西（它是透传层）。如果复杂度重新出现在 N 个调用方中，说明模块在发挥作用。
- **接口就是测试面。** 调用方和测试穿越同一个接缝。如果你想测试接口*之后*的东西，模块的形状可能不对。
- **一个适配器意味着假设性接缝。两个适配器意味着真实接缝。** 除非确实有东西在接缝上变化，否则不要引入接缝。

## 关系

- **模块** 拥有恰好一个 **接口**（呈现给调用方和测试的表面）。
- **深度** 是 **模块** 的属性，相对于其 **接口** 衡量。
- **接缝** 是 **模块** 的 **接口** 所在之处。
- **适配器** 坐落在 **接缝** 处，满足 **接口**。
- **深度** 为调用方产生 **杠杆**，为维护者产生 **局部性**。

## 被拒绝的框架

- **深度等于实现行数与接口行数之比**（Ousterhout 原意）：奖励填充实现。我们改用深度即杠杆。
- **"接口"即 TypeScript `interface` 关键字或类的公共方法**：太窄——这里的接口包括调用方必须知道的每个事实。
- **"边界"**：与 DDD 限界上下文重载。用 **接缝** 或 **接口**。
