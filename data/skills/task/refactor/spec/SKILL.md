# 针对性重构

重构的唯一目标：改善代码结构，不改变外部行为。

本方法论适用于已知目标的代码级重构——你清楚要改什么、改成什么样。

---

## 工具使用协议

重构全程遵循 **观察 → 推理 → 行动** 循环：

**observe（观察）**——收集事实，不做判断：
- `rg "pattern"` 搜索引用和调用方
- 读文件理解当前结构
- `git log` 查历史原因
- 检查测试覆盖情况

**reason（推理）**——将思考物化为可检验的结论：
- 将模块依赖关系写成具体数据结构
- 推演重构步骤，验证每步后类型是否仍然正确
- 应用删除测试：具象化"删掉后会怎样"

**act（行动）**——改变世界，验证结果：
- 使用当前编辑接口和项目口径执行重构
- 运行项目定义的类型检查和测试
- 检查实际差异确认改动范围
- 失败时使用已确认安全、不会覆盖客户其他修改的恢复路径

**关键原则**：存在已确认的隔离或恢复路径时，可以用小规模实验取得实际证据；
不得把“版本控制存在”当作可覆盖客户未提交修改的授权。

---

## show 协议

每一步的完成标志是形成足以支持下一步的质量记录和证据。下面的字段用于内部检查，
不要求机械填满，也不要求每个阶段都单独发送用户可见消息。

当一个阶段形成会改变方案、风险、公共契约或完成状态的新结论时，使用 `show(production record)`，
说明结论、证据和对下一步的影响。例行观察和重复进度不单独记录。

**`show(customer decision required)`** — 遇到需要用户决策的分支点时使用：
- 方案会改变公共契约或订单范围，需要客户决定接受哪个结果
- 发现隐含的客户可见行为变更，需要确认是否修订验收基线
- 安全网不足会把重大且难恢复的风险转给客户，需要客户决定是否接受

多个内部技术方案即使都可行，也由生产方依据证据选择，不因此要求客户代做。

**遍历原则**：调查范围应覆盖目标、调用方、相关契约和验证条件。形成新的架构结论、
发现遗漏范围或改变后续方案时再提交工作日志，不按文件或调用数量触发。

## 流程

### 1. 理解现状

**行动**：
- 读懂当前代码的完整意图和边界（observe：读文件）
- 识别所有调用方（observe：`rg` 搜索所有引用）
- 理解为什么当前代码长这样——可能有历史原因（observe：`git log`）
- 在结论仍依赖未检查的关键调用方时继续调查，不以读取数量代替覆盖判断

形成现状记录；结论值得客户复查时可按以下结构提交 `show(production record)`：

```
【阶段】理解现状
【代码意图】（这段代码在做什么）
【调用方】（N 处引用，列出关键消费者）
【历史原因】（为什么写成现在这样）
【风险点】（重构可能影响的边界 / 隐含耦合）
```

无法取得历史原因时准确记录证据边界，不得猜测。风险判断没有覆盖关键调用方时，继续扩大搜索范围。

---

### 2. 定义目标

**行动**：回答——重构后应该长什么样？好处是什么？用 `reason` 将设计推演写成具体的类型和结构。

有效动机：消除重复（3+ 处相同逻辑）、模块解耦、接口简化、类型安全。
**无效动机**："看起来不够干净"（主观）、"未来可能需要"（投机）、单次使用的代码。

**删除测试**：想象删掉这个模块——复杂度消失（说明它是透传层），还是复杂度散落到 N 个调用方（说明它在发挥作用）？这个检验帮你快速判断"值不值得重构"。

形成目标记录；目标会改变公共契约或客户验收方式时可按以下结构提交 `show(production record)`：

```
【阶段】定义目标
【重构动机】（具体问题是什么——重复/耦合/接口混乱/类型不安全）
【排除的无效动机】（确认不是为了"干净"或"未来需求"）
【删除测试结果】（删掉后复杂度消失还是散落？）
【目标结构】（重构后代码应该长什么样）
【预期好处】（具体的、可验证的改善）
```

只记录实际检查过且会影响是否重构的动机，不为填充字段制造反例。

---

### 3. 建立安全网

**硬约束**：先有测试再重构——没有安全网的重构是赌博。

**行动**：
- 确认测试覆盖情况（observe：查找测试文件、运行覆盖率）
- 判断是否需要先补测试（reason：权衡补测试成本 vs 风险）
- 确认 TypeScript 类型系统能捕获哪些错误

形成安全网记录；测试边界会改变风险判断时可按以下结构提交 `show(production record)`：

```
【阶段】建立安全网
【测试覆盖】（哪些部分有覆盖，哪些没有）
【补测试决策】需要补 / 不需要（依据是什么）
【类型系统保护】（当前项目的类型系统能捕获哪些错误）
```

---

### 4. 执行重构

**硬约束**：
- 客户已授权创建 commit 时，每个 commit 保持单一、可审查的结构变更
- 每个依赖后续步骤的中间状态都通过项目定义的必要检查
- 不混合重构和功能变更

**实验优先**：恢复路径已确认且不会覆盖客户其他修改时，可以直接尝试小规模重构并观察结果；
失败后只恢复本次实验产生的状态。

本步骤可能包含多轮小改动，不需要每轮都提交 production record。在整体改造完成后提交一次。

形成执行记录；整体改造形成可复查结果时可按以下结构提交 `show(production record)`：

```
【阶段】执行重构
【改动概要】（做了哪些结构性调整）
【步骤分解】（拆成了几步，每步做了什么类型的变更）
【中间验证】（每步 typecheck 是否通过）
```

---

### 5. 验证等价

**硬约束**：
- 项目定义的类型检查通过
- 与本次风险和验收条件相关的测试通过
- 检查实际差异确认没有未授权的行为变更
- 公开接口变更时搜索所有消费者确认兼容（observe：`rg`）

形成等价验证记录；验证结论改变完成状态时可按以下结构提交 `show(production record)`：

```
【阶段】验证等价
【typecheck】通过 / 失败
【测试结果】全部通过 / 哪些失败
【diff 检查】确认无行为变更 / 发现疑点（说明）
【消费者兼容】（如涉及公开接口：列出消费者和确认情况）
```

有失败项？→ 回到步骤 4 修正，然后重新提交本步骤报告。

---

### 6. 检查遗漏

**行动**：
- 文档是否需要更新（observe：查相关文档）
- 注释是否仍然准确
- 是否有 TODO 可以顺带清理

**退出 → 提交 `show(qualified delivery)`**，包含：重构动机、改动概要、验证结果、遗留事项。
