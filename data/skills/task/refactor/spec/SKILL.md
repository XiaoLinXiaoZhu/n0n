# 针对性重构

重构的唯一目标：改善代码结构，不改变外部行为。

本方法论适用于已知目标的代码级重构——你清楚要改什么、改成什么样。

---

## 工具使用协议

重构全程遵循 **观察 → 推理 → 行动** 循环：

**observe（观察）**——收集事实，不做判断：
- `rg "pattern"` 搜索引用和调用方
- 读文件理解当前结构
- `git log` 查历史原因
- 检查测试覆盖情况

**reason（推理）**——将思考物化为可检验的结论：
- 将模块依赖关系写成具体数据结构
- 推演重构步骤，验证每步后类型是否仍然正确
- 应用删除测试：具象化"删掉后会怎样"

**act（行动）**——改变世界，验证结果：
- 执行重构操作（write 重写文件）
- `bun run typecheck` 验证类型
- `bun test` 运行测试
- `git diff` 确认改动范围
- `git checkout` 回滚失败的尝试

**关键原则**：在 git 可撤回的前提下，直接尝试（act）再看效果（observe），比纯推演（reason）更高效。出错了回滚重试。

---

## show 协议

每一步的完成标志是：**能提交一份满足该步格式的 `show(working log)`**。

如果你在整理报告时发现某个字段填不上，说明该步骤没做到位——回退继续工作，直到能完整填写后重新提交。

**`show(ask user question)`** — 遇到需要用户决策的分支点时使用：
- 多个等价的重构方案需要用户选择
- 发现隐含的行为变更需要确认
- 安全网不足，需要确认是否继续

**显性遍历原则**：在"理解现状"步骤中，每读 3-4 个文件或每 3-4 次 observe 调用后，提交一个 `show(working log)` 小结。不要读完所有内容后一次性总结——处理视野有限，频繁小结迫使你确认自己真的理解了。

---

## 流程

### 1. 理解现状

**行动**：
- 读懂当前代码的完整意图和边界（observe：读文件）
- 识别所有调用方（observe：`rg` 搜索所有引用）
- 理解为什么当前代码长这样——可能有历史原因（observe：`git log`）
- **每 3-4 次观察提交一次小结**，不要攒到最后

→ 提交 `show(working log)`，格式：

```
【阶段】理解现状
【代码意图】（这段代码在做什么）
【调用方】（N 处引用，列出关键消费者）
【历史原因】（为什么写成现在这样）
【风险点】（重构可能影响的边界 / 隐含耦合）
```

填不上"历史原因"？→ 继续 `git log` 调查。
填不上"风险点"？→ 扩大搜索范围，检查是否遗漏了调用方。

---

### 2. 定义目标

**行动**：回答——重构后应该长什么样？好处是什么？用 `reason` 将设计推演写成具体的类型和结构。

有效动机：消除重复（3+ 处相同逻辑）、模块解耦、接口简化、类型安全。
**无效动机**："看起来不够干净"（主观）、"未来可能需要"（投机）、单次使用的代码。

**删除测试**：想象删掉这个模块——复杂度消失（说明它是透传层），还是复杂度散落到 N 个调用方（说明它在发挥作用）？这个检验帮你快速判断"值不值得重构"。

→ 提交 `show(working log)`，格式：

```
【阶段】定义目标
【重构动机】（具体问题是什么——重复/耦合/接口混乱/类型不安全）
【排除的无效动机】（确认不是为了"干净"或"未来需求"）
【删除测试结果】（删掉后复杂度消失还是散落？）
【目标结构】（重构后代码应该长什么样）
【预期好处】（具体的、可验证的改善）
```

"排除的无效动机"填不上？→ 审视自己的动机是否真的是有效的。

---

### 3. 建立安全网

**硬约束**：先有测试再重构——没有安全网的重构是赌博。

**行动**：
- 确认测试覆盖情况（observe：查找测试文件、运行覆盖率）
- 判断是否需要先补测试（reason：权衡补测试成本 vs 风险）
- 确认 TypeScript 类型系统能捕获哪些错误

→ 提交 `show(working log)`，格式：

```
【阶段】建立安全网
【测试覆盖】（哪些部分有覆盖，哪些没有）
【补测试决策】需要补 / 不需要（依据是什么）
【类型系统保护】（哪些错误能被 tsc 捕获）
```

---

### 4. 执行重构

**硬约束**：
- 每个 commit 只做一种类型的变更（rename、move、extract、inline）
- 每步都能通过 typecheck（act：`bun run typecheck`）
- 不混合重构和功能变更

**实验优先**：直接尝试重构（act），然后看效果（observe）。出错了 `git checkout` 回来重试（act）。比纯 reason 推演更高效。

本步骤可能包含多轮小改动，不需要每轮都提交 working log。在整体改造完成后提交一次。

→ 提交 `show(working log)`，格式：

```
【阶段】执行重构
【改动概要】（做了哪些结构性调整）
【步骤分解】（拆成了几步，每步做了什么类型的变更）
【中间验证】（每步 typecheck 是否通过）
```

---

### 5. 验证等价

**硬约束**：
- typecheck 通过（act：`bun run typecheck`）
- 所有现有测试通过（act：`bun test`）
- 手动检查 git diff 确认没有行为变更（observe：`git diff`）
- 公开接口变更时搜索所有消费者确认兼容（observe：`rg`）

→ 提交 `show(working log)`，格式：

```
【阶段】验证等价
【typecheck】通过 / 失败
【测试结果】全部通过 / 哪些失败
【diff 检查】确认无行为变更 / 发现疑点（说明）
【消费者兼容】（如涉及公开接口：列出消费者和确认情况）
```

有失败项？→ 回到步骤 4 修正，然后重新提交本步骤报告。

---

### 6. 检查遗漏

**行动**：
- 文档是否需要更新（observe：查相关文档）
- 注释是否仍然准确
- 是否有 TODO 可以顺带清理

**退出 → 提交 `show(final report)`**，包含：重构动机、改动概要、验证结果、遗留事项。
