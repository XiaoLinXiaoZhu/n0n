# Plan（质询 + PRD 管线）

将用户的模糊 idea 转化为结构化的 PRD。分两个阶段：

1. **Grill** — 挑战假设、澄清术语、建立领域词汇
2. **PRD** — 综合已知信息为 PRD 文档

参考 `_shared.md` 了解公共概念。

## 前置条件

用户有一个模糊的 idea / feature 需求。

## 流程

### 阶段 1：Grill

参考 `grill-with-docs` 的质询方式，对计划进行穷举式提问。整个质询过程中，能用 `observe` 回答的就不问用户。

**一次一个问题**，每个问题附上你的推荐答案。询问客户掌握的问题定义、用户故事、既有约束或其他事实/要求时用
`show(customer information required)`；需要客户决定业务结果、订单范围、公共契约、授权、重大风险或修订范围时用
`show(customer decision required)`。等待用户反馈后再继续。

#### 质询清单（按优先级）

1. **问题定义**："你想解决什么用户问题？当前是什么行为，期望是什么行为？"
2. **用户故事**："谁会用这个功能？使用场景是什么？"
3. **范围边界**："什么算、什么不算？明确的不在范围内声明。"
4. **领域术语**：用户用到模糊或多义词时，提出精确的规范术语
5. **客户可见契约**："哪些外部行为、兼容性或集成边界必须保持或改变？"
6. **既有约束**："是否有只有客户掌握、且代码和项目文档中无法取得的架构决定或组织约束？"

模块划分、内部接口设计和测试策略由生产方依据代码现状、项目口径和风险形成，
不得要求客户替生产方作这些专业判断。它们只有改变客户可见契约、订单范围或客户承担风险时，
才作为客户决定提交。

**同时内联维护**：
- 领域词汇表：术语确定后用 `write` 将术语写入 AGENTS.md 或 CONTEXT.md
- ADR：用 `reason` 判断是否满足三个条件，满足后用 `write` 写入 docs/adr/（难以逆转 / 无上下文会困惑 / 真正的取舍）

### 阶段 2：PRD

用 `reason` 综合阶段 1 中已讨论的内容为 PRD。不做额外采访——直接综合已知信息。

如果对话中已经有充分的讨论（用户直接给了详细 spec），可以跳过阶段 1，用 `reason` 直接综合为 PRD。

用 `write` 按以下模板写入文件：

```markdown
## 问题陈述
从用户视角描述问题。

## 解决方案
从用户视角描述解决方案。

## 用户故事
详尽的编号列表。格式：作为<角色>，我希望<功能>，以便<收益>。

## 实现决策
模块划分、接口设计、技术澄清、架构决策、Schema 变更、API 契约。
不包含具体文件路径或代码片段。

## 测试决策
哪些模块需要测试、只测外部行为不测实现细节。

## 不在范围内
明确列出不做什么。

## 备注
其他补充信息。
```

### 3. 呈现 PRD

用 `show(customer decision required)` 呈现 PRD 草案让用户审阅。确认后写入文件。

确认后，用 `act` 在上下文中维护 plan 引用（文件路径或内容摘要），供后续 `split` 阶段使用。

作为完整 `@mwf` 管线的一部分时，用 `show(production record)` 提交以下阶段产物并继续 Split。
只有客户直接调用 `@mwf-plan`，且本次订单只要求形成已确认的 PRD 时，才用 `show(qualified delivery)`：

```
【阶段】Plan — 完成
【PRD 路径】<路径>
【领域词汇更新】<新增/更新的术语>
【ADR 记录】<如有>
【下一步】建议进入 split 阶段拆分 issue
```
