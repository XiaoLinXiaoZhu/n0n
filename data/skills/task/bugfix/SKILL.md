# Bugfix 方法论

## 流程总则

每一步的退出条件是：**能提交一份满足该步格式的 `show(progress report)` 报告**。

如果你在整理报告时发现某个字段填不上（比如"排除了什么"想不出来、"依据"不充分），说明该步骤没做到位——回到上一步继续工作，直到能完整填写后重新提交。

回退不是错误，而是质量保障的自然机制。

---

## 1. 格物定位

> 格物致知。物格而后知至。

**硬约束**：不要执行任何修改。不要跳过这一步直接编码。

**行动**：
- 探索代码、日志、复现路径
- 明确问题的实体和边界
- 区分：这是 bug？设计缺陷？还是未满足的需求？

**退出 → 提交 `show(progress report)`，格式：**

```
【阶段】格物定位
【问题定义】（一句话说清问题是什么）
【期望状态】（A₁ 应该是什么）
【实际状态】（A₀ 观察到什么）
【判断依据】（凭什么认为问题是这个）
【排除项】（排除了哪些其他可能，为什么）
```

填不上"排除项"？→ 说明探索不够充分，继续调查。

---

## 2. 构建反馈循环

**这是整个流程的核心。** 所有后续步骤都依赖一个 fast/deterministic/agent-runnable 的 pass/fail 信号。花大量精力在这里。

**目标**：构建一个可重复执行的循环，每次运行给出明确的"通过/失败"信号。

**构建方式——按以下顺序尝试**：

1. **Failing test**——在最近的测试层写一个会失败的测试
2. **CLI 命令**——执行命令，diff 输出与已知正确结果
3. **Replay 捕获的数据**——保存真实请求/事件，在隔离环境中重放
4. **最小化 harness**——只启动涉及 bug 的最小子系统
5. **Bisect harness**——在两个已知状态之间自动二分查找
6. **差分循环**——同一输入跑旧版本和新版本，diff 输出

**迭代循环本身**——把循环当作产品来改进：
- 能更快吗？（缓存 setup、缩小测试范围）
- 信号能更尖锐吗？（断言具体症状，不只是"没崩"）
- 能更确定性吗？（固定时间、seed 随机数、隔离文件系统）

**非确定性 bug**：目标不是稳定复现，而是提高复现率。循环触发 100 次、并行化、加压、缩小时间窗口——把 1% 的 flake 提到可调试的 50%。

**确实无法构建循环时**：停下来明确说。列出尝试过什么。用 `progress(blocked)` 请求用户提供环境访问、日志转储、或临时插桩权限。不要在没有循环的情况下继续推进。

**退出 → 提交 `show(progress report)`，格式：**

```
【阶段】构建反馈循环
【循环类型】（failing test / CLI 命令 / replay / harness / ...）
【运行命令】（一条命令可运行）
【信号描述】（通过时看到什么 / 失败时看到什么）
【循环质量】速度: Xs / 确定性: 高/中/低 / 信号尖锐度: 高/中/低
```

## 3. 对齐标准

**硬约束**：不要在没有评估标准的情况下开始执行。

**行动**：
- 定义验收条件（可验证的 true/false 信号）
- 确定每个条件的观测方式
- 如果涉及用户主观判断，用 `progress(blocked)` 请求确认

**退出 → 提交 `show(progress report)`，格式：**

```
【阶段】对齐标准
【验收条件】
  1. （条件1 — 如何验证）
  2. （条件2 — 如何验证）
  ...
【失败回溯路径】（如果验证不通过，往哪个方向排查）
```

如需用户确认 → 改用 `progress(blocked)`，在 blocked 中完整展示你的问题理解和拟定的验收条件。

---

## 4. 追溯根源

**行动**：
- 生成 **3-5 个排名假设**，每个假设必须可证伪："如果 X 是原因，那么改变 Y 会让 bug 消失 / 改变 Z 会让它加剧"
- `git blame` 追溯引入 bug 的 commit，理解原始意图
- 逐个验证假设——每次只改变一个变量
- 如需插桩，debug log 使用 `[DEBUG-xxxx]` 唯一前缀标记，清理时 grep 即可

**退出 → 提交 `show(progress report)`，格式：**

```
【阶段】追溯根源
【假设列表】（按可能性排名）
  1. 假设A — 预测: ... — 验证结果: 确认/排除
  2. 假设B — 预测: ... — 验证结果: 确认/排除
  ...
【根因判断】（根本原因是什么）
【引入点】（哪个 commit / 什么时候引入的）
【原始意图】（当时为什么这样写）
```

只有一个假设时追问自己：这个假设是否真的没有替代解释？

---

## 5. 尝试修复

**硬约束**：
- 先读后改——不理解上下文不动代码
- 每一轮尽可能批量发出工具调用
- 最小改动原则

**退出 → 提交 `show(progress report)`，格式：**

```
【阶段】尝试修复
【修复方案】（做了什么改动）
【选择依据】（为什么选这个方案）
【排除方案】（考虑过但排除的方案，及原因）
```

只有一种合理修复方式、无需选择？→ 该字段填"无合理替代方案"即可。

---

## 6. 绿灯验证

**硬约束**：
- 运行步骤 2 构建的反馈循环，观察 bug 消失
- 用实际执行验证，不用臆想
- 如实报告——绝不伪造通过或隐藏失败

**退出 → 提交 `show(progress report)`，格式：**

```
【阶段】绿灯验证
【反馈循环结果】通过 / 失败
【验收条件逐项】
  1. ✓/✗ （实际观察）
  2. ✓/✗ （实际观察）
  ...
【失败处理】（如有失败：原因判断 + 下一步方向）
```

有失败项？→ 回到步骤 5 重新修复，然后重新提交本步骤报告。

---

## 7. 横向排查

**硬约束**：横向排查不是可选项——必须执行。

**行动**：
- 项目中相似的位置是否存在同类问题
- 一旦发现一处，逐一排查并修复

**退出 → 提交 `show(progress report)`，格式：**

```
【阶段】横向排查
【搜索范围】（搜了什么、用了什么命令）
【发现】N 处同类问题 / 确认无同类问题
【处理】（逐一说明修复情况，或说明为什么确认不存在）
```

---

## 8. 清理与复盘

**行动**：
- 清除所有 `[DEBUG-xxxx]` 插桩（grep 前缀确认）
- 删除临时 harness 和 throwaway 代码
- 回答：**什么能防止这个 bug？** 如果答案涉及架构变更，记录为 TODO

**退出 → 提交 `show(final report)`**，包含：问题、根因、修复方案、验证结果、横向排查结果、复盘结论。
