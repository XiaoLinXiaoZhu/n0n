# Bugfix 方法论

## 流程总则

每一步的完成标志是形成足以支持下一步的质量记录和证据。下面的字段用于内部检查，不要求机械填满，
也不要求每个阶段都单独发送用户可见消息。

当一个阶段形成会改变方案、风险或完成状态的新结论时，使用 `show(production record)` 提交结论、证据和下一步影响。
没有新信息时不要为了证明流程已执行而汇报。

回退不是错误，而是质量保障的自然机制。

---

## 1. 格物定位

> 格物致知。物格而后知至。

**硬约束**：不要执行任何修改。不要跳过这一步直接编码。

**行动**：
- 探索代码、日志、复现路径
- 明确问题的实体和边界
- 区分：这是 bug？设计缺陷？还是未满足的需求？

形成定位记录；需要向客户公示关键结论时可按以下结构提交 `show(production record)`：

```
【阶段】格物定位
【问题定义】（一句话说清问题是什么）
【期望状态】（A₁ 应该是什么）
【实际状态】（A₀ 观察到什么）
【判断依据】（凭什么认为问题是这个）
【排除项】（实际检查并排除的其他可能及依据；没有实质候选时省略）
```

---

## 2. 构建反馈循环

**这是整个流程的核心。** 所有后续步骤都依赖一个 fast/deterministic/agent-runnable 的 pass/fail 信号。花大量精力在这里。

**目标**：构建一个可重复执行的循环，每次运行给出明确的"通过/失败"信号。

**构建方式——按以下顺序尝试**：

1. **Failing test**——在最近的测试层写一个会失败的测试
2. **CLI 命令**——执行命令，diff 输出与已知正确结果
3. **Replay 捕获的数据**——保存真实请求/事件，在隔离环境中重放
4. **最小化 harness**——只启动涉及 bug 的最小子系统
5. **Bisect harness**——在两个已知状态之间自动二分查找
6. **差分循环**——同一输入跑旧版本和新版本，diff 输出

**迭代循环本身**——把循环当作产品来改进：
- 能更快吗？（缓存 setup、缩小测试范围）
- 信号能更尖锐吗？（断言具体症状，不只是"没崩"）
- 能更确定性吗？（固定时间、seed 随机数、隔离文件系统）

**非确定性 bug**：目标不是假装稳定复现，而是把复现率提高到能够区分候选原因的程度。
可以采用重复运行、并行化、加压或缩小时间窗口；次数由统计信号和成本决定。

**确实无法构建循环时**：停下来明确说。列出尝试过什么。客户参与可用时，
按缺少的客户责任分别处理：需要客户提供已掌握的环境信息时使用 `show(customer information required)`；
需要客户授权临时插桩或接受相应风险时使用 `show(customer decision required)`；
需要客户实际开放访问、导出日志或执行诊断时使用 `show(customer action required)`。一条消息只请求其中一种责任；
客户参与不可用时，按实际条件以 `production suspended` 或 `production failed` 结束。不要在没有有效反馈信号的情况下继续推进。

形成反馈循环记录；该循环会显著改变后续生产方式时可按以下结构提交 `show(production record)`：

```
【阶段】构建反馈循环
【循环类型】（failing test / CLI 命令 / replay / harness / ...）
【运行命令】（一条命令可运行）
【信号描述】（通过时看到什么 / 失败时看到什么）
【循环质量】速度: Xs / 确定性: 高/中/低 / 信号尖锐度: 高/中/低
```

## 3. 对齐标准

**硬约束**：不要在没有评估标准的情况下开始执行。

**行动**：
- 定义验收条件（可验证的 true/false 信号）
- 确定每个条件的观测方式
- 如果涉及用户主观判断，用 `show(customer decision required)` 请求确认

形成验收基线记录；需要客户决定时改用 `show(customer decision required)`，否则只在该结论值得客户复查时提交生产记录：

```
【阶段】对齐标准
【验收条件】
  1. （条件1 — 如何验证）
  2. （条件2 — 如何验证）
  ...
【失败回溯路径】（如果验证不通过，往哪个方向排查）
```

如需用户确认 → 改用 `show(customer decision required)`，在 customer decision required 中完整展示你的问题理解和拟定的验收条件。

## 4. 追溯根源

**行动**：
- 生成由现有证据支持、彼此有实质差异的候选原因；数量由尚未关闭的不确定性决定。
  每个候选必须可证伪："如果 X 是原因，那么改变 Y 会让 bug 消失 / 改变 Z 会让它加剧"
- `git blame` 追溯引入 bug 的 commit，理解原始意图
- 逐个验证假设——每次只改变一个变量
- 如需插桩，debug log 使用 `[DEBUG-xxxx]` 唯一前缀标记，清理时 grep 即可

形成根因记录；根因结论关闭关键不确定性时可按以下结构提交 `show(production record)`：

```
【阶段】追溯根源
【假设列表】（按可能性排名）
  1. 假设A — 预测: ... — 验证结果: 确认/排除
  2. 假设B — 预测: ... — 验证结果: 确认/排除
  ...
【根因判断】（根本原因是什么）
【引入点】（哪个 commit / 什么时候引入的）
【原始意图】（当时为什么这样写）
```

只有一个候选时，核对它是否确实排除了仍与证据相容的替代解释。

---

## 5. 尝试修复

**硬约束**：
- 先读后改——不理解上下文不动代码
- 每一轮尽可能批量发出工具调用
- 最小改动原则

形成修复决策记录；方案选择会显著影响范围、接口或恢复成本时可按以下结构提交 `show(production record)`：

```
【阶段】尝试修复
【修复方案】（做了什么改动）
【选择依据】（为什么选这个方案）
【排除方案】（存在具有实质差异的可行方案时，写明排除理由）
```

---

## 6. 绿灯验证

**硬约束**：
- 运行步骤 2 构建的反馈循环，观察 bug 消失
- 用实际执行验证，不用臆想
- 如实报告——绝不伪造通过或隐藏失败

形成验证记录；验证结论改变完成状态时可按以下结构提交 `show(production record)`：

```
【阶段】绿灯验证
【反馈循环结果】通过 / 失败
【验收条件逐项】
  1. ✓/✗ （实际观察）
  2. ✓/✗ （实际观察）
  ...
【失败处理】（如有失败：原因判断 + 下一步方向）
```

有失败项？→ 回到步骤 5 重新修复，然后重新提交本步骤报告。

---

## 7. 横向排查

**硬约束**：必须做与根因和风险相称的横向排查。

**行动**：
- 项目中相似的位置是否存在同类问题
- 发现同类问题时判断是否属于当前订单范围；范围内逐一处理，范围外记录证据和影响，不静默扩大订单

形成横向排查记录；发现范围或阴性结论值得复查时可按以下结构提交 `show(production record)`：

```
【阶段】横向排查
【搜索范围】（搜了什么、用了什么命令）
【发现】N 处同类问题 / 确认无同类问题
【处理】（逐一说明修复情况，或说明为什么确认不存在）
```

---

## 8. 清理与复盘

**行动**：
- 清除所有 `[DEBUG-xxxx]` 插桩（grep 前缀确认）
- 删除临时 harness 和 throwaway 代码
- 回答：**什么能防止这个 bug？** 如果答案涉及架构变更，记录为 TODO

**退出 → 提交 `show(qualified delivery)`**，包含：问题、根因、修复方案、验证结果、横向排查结果、复盘结论。
