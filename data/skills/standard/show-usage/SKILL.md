show 是你与系统交互的结构化输出工具。四种 type 对应两种截然不同的系统行为：

- **working log** → 记录到日志，系统自动继续循环。用户不会被即时通知。
- **ask user question / request user assistance / final report** → 系统暂停循环，等待用户响应。

选择 type 的核心判据不是"内容是什么性质"，而是"是否需要用户现在看到并响应"。

## 四种 type

### working log — 内部工作日志

你的工作留痕。记录关键判断点的推导过程——做了什么决定、基于什么证据、排除了什么替代方案。系统自动继续循环，不会暂停等待用户。

用户可以事后查阅这些日志来追溯你的决策过程，但不会被即时通知。如果你需要用户现在看到某个信息或做出回应，应该使用 ask user question 或 final report。

判断标准：如果你排除了至少一种合理的替代方案，就值得记录。即使只是一两句话也够——重点是暴露决策点，不是写长文。

### final report — 任务完成

任务已完成并验证。面向用户的正式交付物。系统暂停循环，等待用户响应。

假定用户已失去上下文，内容必须完整自包含：已完成的工作、验证结果、关键决策。

### ask user question — 向用户提问

需要用户做出选择才能继续。系统暂停循环，等待用户响应。

内容必须自包含：先展示推导上下文（你的判断链条和依据），再提出具体问题并提供 2-4 个选项。假定用户没有读过之前的 working log，仅凭这一条就能理解你为什么问这个问题。

选项格式——每个选项以 `## ` 开头作为标题行，下一行写详细说明。

### request user assistance — 请求用户协助

需要用户介入操作或提供无法通过文字传达的信息。系统暂停循环，等待用户响应。

内容必须自包含：说明当前障碍、为什么无法自主解决、需要用户做什么。

## 使用节奏

- show 可以与其他工具调用同批发出——所有工具正常执行，然后循环重启。调用 `show(working log)` 不额外消耗轮次。有有意义的判断就记录。
- 每个独立的推理步骤（提出假设、检查证据、排除/确认、转向）都应该通过 `show(working log)` 声明。不要等整个阶段结束才记录。
- `show(ask user question)` 或 `show(request user assistance)` 之前应该有若干个 `show(working log)`——在请求用户介入之前，先做完所有自己能做的探索。

## 内容质量

- 每一步声明必须有明确依据——具体的文件名、行号、数值、命令输出，而非直觉。
- working log 中说清楚：当前方向是什么、依据是什么、下一步要做什么。
- ask user question 中说清楚：核心结论、自信程度、需要用户确认的具体决策点。
- request user assistance 中说清楚：什么障碍阻止了自主完成、需要用户执行什么操作。
