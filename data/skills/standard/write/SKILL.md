# write 与文件修改

## write — 创建或覆盖文件

用 `write` 创建新文件或完整覆盖已有文件。目录自动创建。确定性工具——始终成功，不需要等待结果。

## 文件修改策略

修改文件时，优先使用 `write` 完整重写。如果文件组织合理（单一职责、短小），修改几乎总是等价于完整重写。

决策树：

1. **文件结构良好且小** → `write` 重写整个文件
2. **文件结构差** → 先重构为良好结构（拆分模块），再 `write` 各部分
3. **外部约束文件**（package.json, tsconfig）→ 领域专用工具（`bun add`, `jq`, etc.）
4. **遗留代码、不值得重构** → unified diff + `git apply` 作为降级方案

## Diff/Patch 降级方案

当确实需要局部修改时（大文件、不值得重构的遗留代码），使用 unified diff：

```
# 写 patch 文件，然后一次性应用
write(.temp/fix.patch, <unified diff 内容>)
act(git apply .temp/fix.patch)
```

单个 diff 文件可以同时完成：修改、创建新文件、删除文件、重命名文件。

## 文件操作选择

- 文件满是问题 → 用 `write` 完整重写。
- 文件过大 → 先问为什么这么大（过耦合？模块化差？），征得用户同意后拆分为定义良好的模块，不要继续维护臃肿文件。
- 使用 `write` 修改较大的文件时：
  - 考虑顺手将其拆分为合适的模块、将函数等提取出来到单独的文件中。
  - 重复内容时不要抛弃必要的注释，比如明确标记为 TODO 等的，或者说明容易混淆的逻辑描述。

## 工具结果中的提示

工具结果可能包含 `<system-hint>...</system-hint>`，是运行时的临时操作建议（如怎么读截断的输出、有哪些恢复选项）。评估是否适用于当前步骤后再行动——这些提示只存在于最近一次工具结果中，会从历史中自动移除。
